# Let a card install a depot pack larger than a card holds

Design yardr-y6gp, proposed 2026-10-30. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

A *card* is an ask a person answers by approving rather than by picking words. This document is about one card: the run ask whose command is `pack apply` (a *run ask* proposes one yardr command of a fixed list, and the operator's approval runs it through the store function the command itself calls). A *pack* is a way of working as one directory: flows, groups, roles, crew members. An *embedded pack* is one yardr ships inside its binary (`packs/packs.go`), named where a directory would be given. A *depot pack* is a pack written for a depot (a git repository or plain directory that beads are worked in), as against a pack of kind `source`, which is imported into the yard itself. A card is *weighty* where approving it widens what reaches outside the yard, whose word or credential counts as a person's, or what runs inside the yard (`internal/store/weight.go`), and *strong* where its weight carries `trust` or `code`, which no paired device may approve (design yardr-2nb1, as built). A *device* is a program of a user that calls the yard from outside it, let in by a token the yard gave it; the operator's phone running the yard's app is one. The *hosted web* is the browser view of a hosted yard behind its gateway, where a strong card is approved under a fresh sign-in. A pack's *digest* is the SHA-256 of the files the pack is made of (`internal/pack/digest.go`), the one thing an operator who has read a pack can name it by. The *plan* is what importing a pack into a depot would do, object by object (`internal/pack/plan.go`). docs/glossary.md has the rest of yardr's words.

## 1. The question

Mckean was asked (ask 17455, 30 Oct): "Should a person without a terminal be able to install the larger packs (starter, contributors, website, design) from a card? Today only the small dir pack fits on a card. The others run 175 to 325 KB, against a limit of 64 KB that exists so a strong card is read whole before approval. yardr-1bas lands with that limit kept, so those packs stay terminal-only." Mckean picked the first option: "Yes, before launch — design a card that shows a summary and links the full text. It adds code, and you'd approve on a summary rather than the whole text." This document is that design. It settles what the approver sees, how the approval is bound to the exact bytes approved, where the full text is read before approving, and how the card's weights stay whole when the text is not on the card. The choices that are the operator's to make are in section 5, and the note that hands this bead on lists them first.

## 2. What exists today

### 2.1 The row as yardr-1bas landed it

The `pack apply` row of the run-ask list stands in `internal/store/runask.go` (the row with words `pack apply`, parsed by `parsePackApply`, checked by `checkPackApply`, carded by `packApplyCard`, held stale by `packApplyStale`, weighed by `packApplyWeight`, and recorded by `runPackApply`, which answers "approved, to be carried out" while the server's carrier in `internal/server/carry.go` does the applying). Yardr-1bas, landed at 249400cd, made a first install askable on this row: beside the pack's name the command may carry `--depot <depot>` and the mappings that answer the plan (`--flow`, `--crew`, `--group`, `--bind`, `--members`, `--open-threads`, `--calls`, in `internal/store/packmappings.go`). Every other flag of the terminal command stays refused. The card is built inside the write that stores the ask, from the server's own reading of the embedded pack (`readEmbeddedPack` in `internal/server/packreader.go`, registered on the store with `SetPackReader`), never from bytes the asker sent. A plan that still asks anything, is refused, or would overwrite a file edited by hand is refused at the ask. A depot that does not stand is refused, and a depot that already holds the pack builds as a re-apply, never as a first install. A pack of kind `source` named with `--depot` refuses pointing at `bead ask --setup`, so the same install never has two routes. Weights are `packApplyWeight` in `internal/store/weight.go`: what the carried sources bring, plus what the mappings give (an update call is `outside`, one that sends a file is `code`, opening a thread is `outside`, a bind is `code`, members are `trust`), plus `code` for a first install whose plan makes files, groups or crew. A credential alone weighs nothing more.

### 2.2 The caps, and what they refuse

Three bounds stand in `internal/store/runask.go` beside the row. `MaxRunPackDeclarations` (256 KiB) bounds the declaration text a pack ask holds together. `MaxRunPackFiles` (128 KiB) bounds what the yard calls the payload: each carried source's command-file texts, each replacement's command-file diffs and removed copies' texts, and each created or changed file object's new text and unified diff, summed in `packApplyCard`. `MaxRunSourceCardLines` (40) bounds the card's sentences (`Does` lines). Past any bound the ask is refused with words naming a terminal: the pack is the operator's to type there, where `yardr pack check` shows its plan.

Yardr-1bas's builder measured the embedded depot packs against these bounds with the real reader and no mappings (note 17450 on yardr-1bas). The payload of starter is 257,801 bytes over 39 plan objects, contributors 325,386 over 40, website 288,213 over 35, and design 175,887 over 23. Only dir, at 33,141 bytes over 23 objects, fits. The text alone of starter's files is 127,463 bytes, so leaving a create's diff off the card would not save any of the four: the bound is met by the texts themselves, not by showing each change twice. The line bound is met the same way, since the card today writes one sentence to a created or changed object. The four packs the question names are therefore refused at the ask today, and an operator with no terminal cannot install any of them.

### 2.3 What the card holds, and who reads the whole of it where

A depot pack's card sentences are written by `packDepotDoes` in `internal/store/runask_pack.go`: one line for the pack with its counts of objects to create, to change, unchanged and dropped; one line to each mapping the plan uses; one line to each created or changed object, a file naming its old and new SHA-256 whole with its insertions and deletions counted from the diff; one line to each dropped object; what governs the depot afterwards; and each declared source as a source card renders it. The full texts stand beside the sentences in the ask itself: each declared source's whole text and command files in `AskRun.Carried`, and each file object's new text and diff in `AskPack.Plan` (`internal/store/packmappings.go`). A terminal reads them whole under the sentences (`carriedLines` and the plan blocks in `internal/store/asks.go`). An operator's device is sent the same ask by the `Bead` and `UserAsks` calls, texts included, and reads the full text one tap behind the card. The hosted web's bead page (`internal/web/beadpage.go`, the card in `internal/web/templates/ask.html`) renders the sentences and nothing behind them: it has no view of a carried text or a plan file today. A device that is no operator's is told none of it: `withoutRunWords` in `internal/rpc/beadview.go` cuts the sentences, the carried texts, the plan and the mappings, keeping the pack's name and depot, and a held command's weight keeps its classes without its lines (`WithoutWeightWords`). The pack's file texts are the operator's configuration, and every surface holds them to that audience today.

A declared source needs its two shapes named, because section 3 treats them differently. A pack declares a source by a declaration file (a `declaration: <file>` entry, held as `Declared` in `internal/pack/pack.go`); the server's reading carries that file's text and its command files, and `packDepotDoes` renders each declared source through `packOneSourceDoes`. None of the four packs the question names declares one: their `sources:` entries are stage maps for sources yardr has in Go (linear, github), which shape the plan and its governs and carry no declaration or command file at all, and design carries not even those. Where a pack does declare a source and none stands in the yard under its name, the card renders the new declaration whole, as a source card does. Where one already stands — or its command-copy directory still holds entries the copy step would replace or remove — the card renders the change from the old side too: a line that it would replace the standing source, `packDeclDiffLines` naming each top-level key of the declaration that differs, old against new, a line for where a standing grant of read widens and for the grants that stand, each changed command file's old and new SHA-256 with its insertions and deletions carried on its command line, and `changedCopyLines` naming each dropped or unnamed copy with its hash, mode and size. The ask carries that old side beside the new text (`AskSource.Old`, `AskSource.Removed` and `AskSource.Inventory` in `internal/store/runask.go`, filled by `packReplacement`), and its diffs and removed texts count in the same payload as the plan's files. Those sentences are the only place the old side is shown: a summary that kept only the new declaration's name and hashes would approve a replacement without ever saying what the standing source stops doing.

### 2.4 The binding that already stands

An approval is already held to bytes the yard re-reads, never to the asker's words. When the ask is written, `packApplyCard` keeps in the ask's `Seen` map the reading's label and build, a fingerprint of the pack's bytes as carded (`packBytesSeen`, over each carried source's text, each command file's SHA-256, and the plan whole), each standing source's fingerprint, and, for a named depot, what the depot, its import record of the pack, and each mapping target stood as (`packTargetsSeen`). At approval the yard writes the card again from the pack as it stands then, and `packApplyStale` refuses where a target moved, where the plan differs at any object, where the pack's bytes or label moved, where a source it would add or replace moved, or where the sentences themselves differ. A build that moved alone, with the same bytes under the same label, is no reason: the approval runs past it. After approval the server's carrier reads the pack a third time (`carryPackApply` in `internal/server/carry.go`), refuses where the pack, its depot or its sources differ from the card, holds each depot object against the carded plan before anything writes, applies with exactly the card's depot and mappings, and verifies what stands. What is missing for a large pack is not a binding. It is room: the binding machinery reads the whole pack at the ask, at approval and at carrying out, and refuses long before size is considered. Size refuses earlier, in the same `packApplyCard`, only because the card would carry the texts it binds.

### 2.5 The digest that already stands, and is not on the card

Every plan carries the pack's digest (`Plan.Digest` in `internal/pack/plan.go`): for each file the pack names, its path, a NUL, its length, a NUL and its bytes, hashed in path order, from the bytes before any placeholder is filled, so one pack has one digest whatever depot it goes into and whatever the import is answered. `yardr pack check` prints it as `digest sha256:<hex>` above the files that run, and `yardr pack apply --sha256` is pinned to it (`Plan.CheckDigest` in `internal/pack/digest.go`): an operator who has read a pack at a terminal names it by this hash, and no other bytes install under that name. The card does not carry it. `PackReading` and `AskPack` hold the name, kind, depot, mappings, label, build, sources and plan, and no digest: the server's reading builds the plan and keeps only the card's form of it (`askPlanOf` in `internal/server/packreader.go`). The hash an operator could compare against a second reading of the pack therefore exists in the yard and is thrown away on the one road where the operator cannot open a terminal.

### 2.6 Weights, and where a strong card is approved

A card's weight is weighed in the write that stores it and again in the approval's write, from the card and the yard's records, never from the asker's words, and an approval whose weight differs from the one the card showed is stale. `StrongWeight` in `internal/store/weight.go` makes a card strong where its weight carries `trust` or `code`, and `strongRefusal` refuses such a card's approval where it arrived through a device, naming the place instead: on a hosted yard the hosted web with a fresh sign-in, elsewhere a terminal on the yard's machine. Nothing runs and the ask stays open. A first install of any of the four large packs weighs `code` for the files, groups and crew its plan makes, so each is strong, and the device refusal is already the rule for the card this design adds a shape to. The weight is computed from the whole reading, from every carried file and every plan object, whether or not a sentence about it fits on the card. Nothing in the caps protects the weight; they protect the reading, and the weight stands whether the pack is refused or not.

That strength is a first install's, not a pack's. `packApplyWeight` adds its `code` for the plan's objects only where `packFirstInstall` says the depot holds no import of the pack; a re-apply is weighed from what it carries (a carried command file new or changed is `code`, and a widened grant of read is `reads`, in `carriedWeight`) and from what its mappings grant (an update call `outside`, one that sends a file `code`, an opened thread `outside`, a bind `code`, named members `trust`). A re-apply that changes only depot files, carries no changed command file and grants nothing through its mappings therefore weighs routine, or `outside` and `reads` alone: not strong, and approved through a device under the gate as it stands. Section 3.4 keeps that exactly, and says so where the summary is weighed.

### 2.7 The two half-true sentences yardr-1bas leaves

Two texts were true when written and are half true since yardr-1bas landed. First, the bare re-apply's refusals call a first install the operator's to type in a terminal: `readEmbeddedPack`, where no depot holds the pack, refuses that "a first install asks what a card cannot answer, and is the operator's to type in a terminal", and `packApplyCard`, where a depot pack has no single depot to re-apply to, refuses the same way. A first install named with its depot and the mappings that answer its plan is now a card, where it fits the caps; only a first install named with nothing, or one whose plan still asks, is a terminal's. Second, `docs/users.md`, in the stolen-device table's row for a first install to a named depot, says a pack of kind source "is installed with `bead ask --setup`, never this row". Only a source pack named with `--depot` is sent to the setup ask; a bare `pack apply <name>` of kind source still builds on this row, as it did before yardr-1bas, and packs whose setup words rely on that still ride it. Section 6 names the bead that corrects both, in code words and in the user docs together, since a refusal and the table that explains it must not disagree.

## 3. The proposal

The smallest change that answers the question keeps the row, the reading, the binding, the weights and the approval exactly as they stand, and changes only what a card must hold to be written. A depot pack whose card fits today's bounds keeps today's card, whole, unchanged. A depot pack named with its depot whose card does not fit, and which replaces no standing source, is written as a summary card instead of refused: its sentences are compressed to a summary that fits the line bound, its full text stays carried in the ask where it already stands, and its approval is bound to the pack's digest and to each file's SHA-256 as well as to the plan fingerprint it is bound to today. Named with its depot covers a first install and a re-apply to that depot alike, which the one builder builds today; a bare `pack apply <name>`, whose depot the reading finds among the depots that already hold the pack, is never written as one (section 4). No new command, no new ask kind, and no new approval: the operator approves the same `pack apply` card, weighed the same, through the same gate. What is new is a second card shape on one row, the digest carried onto the card, and two reading surfaces that open the carried text from the card. Directory, URL and record packs gain nothing: the server's reading refuses them before a card is considered, as today, because a card is written from the binary the yard runs and from nothing else.

### 3.1 What the approver sees

The summary is compressed from the card `packDepotDoes` builds today, and holds nothing the whole card does not. In order, the card shows the weight lines first, as every card does, then the command whole, then these sentences, each one line, all passed through the same one-line keeping (`safeSourceCardLine`) as today:

1. The pack line, widened to name the pack whole: the pack's name and label with its build, its kind, the depot it installs into, the counts of objects to create, to change, unchanged, and dropped and left where they stand, the digest as `digest sha256:<hex>` in the words `pack check` prints, and the files that run once installed, as `pack check` names them under its digest (`Plan.Programs`). Where the install is a first one, the first-install sentence stands next, as today: depot and pack named, so the card never reads as a re-apply.
2. One line to each mapping the plan uses, in the flags that name them, whole as asked, as today. The mappings are part of what is approved and are never summarised away.
3. One line to each file the import would create or change: its name in the pack, its action, its new SHA-256 whole with the old one where a file stands (`sha256 <old> -> sha256 <new>`, `(none)` for a create, as today), its new size in bytes, and its insertions and deletions counted from the diff. A file is the unit the full text is read by (section 3.3), so each is named on the summary itself; no file hides inside a count.
4. The objects that are not files, grouped where grouping loses no name that decides anything: to a kind, its action and its objects' names (`groups to create: builders, reviewers`), with each object's changes in the words the whole card gives them where the change is a value the approval sets, and keeps, shadows and `cmd` settings as their own lines as today, since each is a fact about what the yard will run. A dropped object keeps its own line, as today: what the pack no longer brings and the yard keeps is a decision, not a count.
5. What governs the depot afterwards, as today, and each source the pack declares and the import would add — on a summary card every declared source is an addition, since section 3.5 keeps any that would replace off it — named as added, with its declaration's command files by program and SHA-256, as `pack check` names them; the declarations' whole texts stand in the full text, counted under the declarations bound as today. What a replacement changes from the old side (section 2.3) therefore never has to survive compression: no summary card carries it.
6. The closing counts over the whole plan, as `pack check` prints them, and one line naming the full text: how many files it holds and how many bytes, and that it stands behind the card at the place section 3.3 names, on this bead's page.
7. What takes the change back, as the card's `Back` and `BackBy` already stand beside the sentences on every surface: for a depot pack, no one command, and the terminal command that reads the standing state. The summary changes none of it.

Weights are not in this list because they are not sentences: they stand on the card as its `Weight`, before the question, one line a class, computed as section 3.4 says. For starter into a fresh depot the summary is the pack line with its digest, the first-install line, one line to each of its created and changed files, its grouped groups, flows and routes, and the closing counts: well inside forty lines where the whole card's payload is 257,801 bytes, because a line is paid per file and not per byte. Where even the summary would pass the line bound — a pack with more changed files than lines to name them — section 5, question 2 puts the choice to the operator rather than this section deciding it: the shape above is written to fit forty, and the folding it needs past that is the operator's pick.

A terminal shows the summary card as it shows every card, and behind it the whole carried text, as it does today: a terminal was never the surface the caps protected, and its reading of a summary card loses nothing.

### 3.2 The binding: a digest and each file's hash, both re-read

The approval names the exact bytes in two hashes, because each covers what the other cannot. The pack's digest names the pack as it was read: every file it names, before filling, whatever depot and mappings the plan was built with. It is the name an operator can carry away from the card and check against any other reading of the pack, a terminal's `pack check` included, and it covers files the plan for this depot does not install, such as another flow's stage files, which are part of what approving the pack endorses. Each file's new SHA-256, on the summary line and at the head of its full text (section 3.3), names what this depot will hold: the filled text as the import would install it, which the digest, taken before filling, cannot name. Neither stands alone. A digest alone would approve the same pack filled with another yard's names; a file hash alone would say nothing of the objects that are not files, nor of the pack beyond this depot's plan.

To carry this, the server's reading keeps the digest it already computes: `PackReading` and `AskPack` gain the plan's digest, the card's pack line prints it, and the ask's `Seen` gains it under its own key beside the label, build and bytes that stand there. Everything else of the binding is today's, unchanged, and is restated here because the summary makes it load-bearing: at approval the yard writes the card again from the pack as it then stands, and the approval is stale — nothing runs, and the ask is asked again — where the digest differs, where the plan differs at any object, where any carried source or any mapping target moved, where the sentences differ, or where the weight differs from the one the card showed. After approval the carrier reads the pack a third time and holds the fresh plan to the carded digest before it applies (`Plan.CheckDigest`, the pin `pack apply --sha256` already trusts), so the bytes that install are the bytes the digest named even if the pack moved between approval and carrying out. A build that moved alone still runs past, as today: the digest is of bytes, not of builds, and says so by construction.

The summary itself authorises nothing, and neither does the full text behind it. Both are renderings of a reading the yard re-takes at approval; if a rendering could drift from the pack, the drift refuses the approval, since the re-written card's sentences, hashes and plan are compared whole. That is the property the caps bought by size, bought here by hashing: what stands in for the rest of the pack is not trust in the summary, but a hash the yard re-reads.

### 3.3 Where the full text is read

The full text is the carried text the ask already holds, read one file at a time, from the card itself, in the same sitting, with no terminal. It holds no new bytes and needs no new store: each created file's whole text as the import would install it, each changed file's unified diff with its whole new text behind it, each declared source's declaration and command files whole, and each non-file object's changes whole. A reader who opens every file has read everything the whole card would have shown, because the summary is compressed from exactly this and from nothing else. Because no summary card replaces a source (section 3.5), that full text never has to show an old declaration against its replacement, a changed command file's diff from the copy that stands, or a copy the step would remove: those stand on a whole card or not at all, and a pack that would show them is refused whole, to a terminal.

On the operator's phone the text is already there. The `Bead` and `UserAsks` calls send an operator's device the ask whole, carried texts and plan included, and the card there already reads its full text one tap behind. The summary card changes only the first screen: each file's summary line is the tap that opens that file, headed by its name, its action, and its old and new SHA-256 whole, so the hash on the summary and the hash over the text stand on one screen and a reader can see they are one. No yard call changes for this; the device client draws the summary first instead of the sentences it draws today, over data it already receives.

On the hosted web the text is not there, and this is the one new reading surface. The bead page gains a paged view of the ask's own carried text: from the summary card, each file's line links to a page of that bead, under its ask, showing that one file whole — a create as its text, a change as its diff with its new text behind it, each headed by the file's name and its SHA-256s as they stand on the summary — with the previous and next file beside it and the card one link back. The page is rendered from the stored ask, as the bead page is rendered from the bead, and holds no copy of its own: close the ask and the pages are gone with it. Its audience is the card's: the view shows it only where it acts as the operator the card is asked of, since the texts are the operator's configuration, held from every other device and viewer exactly as `withoutRunWords` holds them today. A hosted yard's operator therefore reads the whole pack in the browser, file by file, and approves under the fresh sign-in the strong gate already demands, without leaving the bead.

No blob is made of the pack. The yard's blob roads (`GET /blobs/{hash}` on the web, `GET /user/blobs/{hash}` on the listener) serve files a note, a mail or a kept delivery names, and a pack's text is none of those: putting a rendering of it there would mint a third hash, of the rendering, which names neither the pack nor any file in it, would need a naming, an audience and a pruning rule of its own, and could sit in the yard after the ask it was made for is gone. The paged view renders from the ask the approval is bound to, so the text a reader opens cannot be a copy that outlived its card. Section 4 keeps the blob road among what was not proposed, with its reason.

### 3.4 How the weights stay whole

The weights do not change at all, and that is the point. `packApplyWeight` weighs what the ask holds — the carried sources, the plan and the mappings — and never the card's sentences, so a summary card is weighed from the same untruncated reading as a whole card: every carried command file that is new or changed, every mapping's grants in their classes, and a first install's files, groups and crew as `code`. The summary's line count is a fact about its sentences; the weight is a fact about the pack, and no line of it is folded, grouped or counted away. The weight lines stand on the summary card first, as on every card, naming what the approval widens: for each of the four large packs a first install is `code`, and `trust` or `outside` beside it where its mappings grant them. The summary itself weighs nothing and hides nothing: it neither adds a class nor drops one. A first install of any of the four is therefore strong, and the strong refusal stands unchanged behind it: an approval that arrives through a device is refused, nothing runs, and the ask stays open, on a hosted yard naming the hosted web with its fresh sign-in and elsewhere a terminal. A re-apply to a named depot keeps the weight its whole card would have carried, and that weight need not be strong (section 2.6): where it carries neither `trust` nor `code`, the gate as it stands lets a device approve it, summary or whole, and this design changes no part of that gate. An operator who wants every large re-apply held to the hosted web or a terminal is asking for a stronger gate, not for a summary shape, and no bead in section 6 builds one. A non-operator's device is told the classes and nothing of the lines, as today, since the lines quote the mappings the summary also holds from it. Approving on a summary therefore widens exactly what approving on the whole card widens, is gated exactly where that is gated, and is refused from exactly the surfaces that are refused today. The caps never carried the weight, and lifting them off the sentences lifts nothing off the gate.

### 3.5 The caps after

The two bounds the bead names part here, because they bounded two different things that one refusal spoke of as one. `MaxRunSourceCardLines` stays at 40 and keeps its meaning, now over the summary's sentences: a card, whole or summary, is read as one screen of sentences, and past forty it is refused as today, under the choice section 5, question 2 puts. `MaxRunPackFiles` stands at 128 KiB where it bounds a whole card (raised from the 64 KiB this design kept, ask 24349) — the source rows, the setup row, a depot pack whose card fits, and every depot-pack apply that would replace a standing source, however large its plan — and stops bounding only the summary row: a depot pack named with its depot, past the whole-card bounds, which replaces no standing source. There it is replaced by a bound on what the ask carries rather than on what the card shows: a new bound beside the old in `internal/store/runask.go`, set at 1 MiB of carried file texts and diffs together. Replaces is read from the yard as the card is written, exactly as `packReplacement` and `packOneSourceDoes` read it: a carried source whose name a standing source already holds, or whose command-copy directory holds entries the import would replace or remove, including copies left by a source since removed. The four packs the question names replace nothing — they declare no source at all (section 2.3) — so the exclusion costs the launch nothing; it bites only a pack that brings a declaration file for a source the yard already holds, and that pack keeps today's whole card or today's refusal. The largest of the four packs carries 325,386 bytes, so the carried bound holds each of them three times over, and a pack past it is still the operator's to apply in a terminal: an ask is a note in the store and a payload on two calls, and neither grows without a bound. `MaxRunPackDeclarations` stays at 256 KiB untouched: a depot pack's declared sources are few, and their texts already stand whole behind the card. What still refuses, unchanged, is everything that is not size: a plan that asks, is refused, or would overwrite an edited file; a changed file whose bytes are not text, which no summary can show and no hash can make readable; an unknown depot; a source pack named with a depot, sent to its setup ask; every flag the row refuses today; and a direct first install by a crew member, which is the operator's approval to propose, never to give.

## 4. Left out

- **Building any of it.** This document is the design. Section 6 lists the build in beads small enough to land one at a time, and nothing here changes a call, a card or a document that stands.
- **A blob of the pack's text.** A copy of the rendering under the yard's blob roads would carry a hash of the copy, not of the pack or of any file, would need its own naming, audience and pruning, and could outlive the ask that made it. The full text is read from the ask itself (section 3.3), which the approval re-reads and which ends with it.
- **Directory, URL and record packs.** A card is written from the binary the yard runs. A pack read from anywhere else is the operator's to apply in a terminal, where `pack check` shows its plan, as today.
- **Approving anything larger than a depot pack's install on a summary.** A source replacement — a `source add` card, a source pack's card, a setup card, or one carried inside a depot pack — keeps today's whole-card rule and its bounds. Its carried bytes are the decision itself: the standing declaration against its replacement, its command files' diffs from the copies that stand, and the copies the step would remove. The pack's digest names the pack's files and says nothing of that old side, which stands in the yard and which today only the card's sentences show; a standalone replacement has no plan to fingerprint either. Its texts are already bounded small by the source rows' own caps. Nothing measured asks for room there, and this design does not invent it.
- **Bare re-applies and source packs on the summary shape.** A `pack apply <name>` with no depot, and a pack of kind source, build exactly as today, whole card or refusal, under either answer to section 5, question 3. The question is a named depot's install, and the named row is where the depot, the mappings and the digest stand together on one card to bind a summary. Question 3 asks only whether a re-apply to that named depot follows a first install there.
- **Proving the reading.** The yard cannot prove a person opened the full text, on any surface, and no part of this design pretends to: it makes the whole text reachable from the card and holds the approval to its hashes. Whether approval should wait on the text being opened where the yard can see it opened is section 5, question 1.
- **A second shape for any other row.** No other run ask gains a summary. Each other row's card fits because its command changes one thing a screen can say; the pack row is the one whose change is a directory of files.

## 5. Open questions

Each question is the operator's to decide. Each gives its options, what each costs, and the one this document would take. Nothing elsewhere in this document decides any of them.

**1. Must the full text be opened before the approval stands?** Option A: no. The card offers the full text from every file line, the approval binds their hashes, and the operator approves when they judge they have read enough, as a terminal operator who has scrolled a plan approves without the yard counting the scroll. Option B: on the hosted web the approve control stands only after each file's page has been opened in that sitting. It costs a record of what was opened, kept per ask and per viewer, and it can hold only the web: a phone's openings are its client's word, so the rule would bind the surface that already demands a fresh sign-in and not the device beside it, while proving an opening and not a reading. This document would take A: the strong gate already places the approval where a second possession is proved, and a proof of opening would add state to every summary card to witness the one act no surface can witness honestly, which is reading.

**2. What happens where even the summary passes forty lines?** A pack with more changed files than a forty-line summary can name one by one meets this: the four measured packs do not, and a larger one would. Option A: keep forty, and fold the files past the line budget into one closing line that names how many files and how many bytes stand in the full text without a line of their own, all under the digest and each under its hash there. The summary then names most files and counts the rest, and the card stays one screen. Option B: raise the line bound for a summary card alone, to eighty. Every file keeps its line, and the card becomes two screens where the whole-card rule said one, on the surface — a phone — where a card is read whole or not at all. This document would take A: the bound exists so the card is read whole, the digest binds the folded files exactly as it binds the named ones, and their hashes stand one tap away on the full text's own pages.

**3. Does the summary shape reach a re-apply to a named depot, or first installs only?** A bare `pack apply <name>` is outside both options: it builds whole or refuses, as today (section 4). What is asked is the named row alone, where one builder writes a first install and a re-apply to that depot. Option A: both, as section 3 has it — the shape turns on the card not fitting and on replacing no standing source, not on whether the depot already holds the pack, so a starter re-applied after the yard moves is approved the same way it was installed. Its cost stands in section 2.6: some such re-applies weigh neither `trust` nor `code`, so the unchanged gate lets a device approve them, where a first install that makes files, groups or crew is strong for that making. Option B: first installs only, and an over-cap re-apply to a named depot stays a terminal's. It costs a second condition on one builder and leaves a large pack's re-apply — the same bytes approved again after the yard moves — on the surface the question exists to free. This document would take A.

**4. One card shape for every depot pack, or two?** Section 3 keeps today's whole card where it fits and summarises only past the bounds, and only where the pack replaces no standing source. Option A: two shapes, as section 3 has it — a small pack like dir keeps the card that has been read whole since the row landed, and only a pack that cannot be read whole is approved on hashes. Option B: the summary shape for every named depot pack, small ones included. One builder and one reading habit, at the cost of retiring the read-whole card where it works and asking every depot pack's approver to trust hashes for files that would have fit on the card. This document would take A.
