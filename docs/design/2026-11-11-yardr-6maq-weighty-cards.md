# File most terminal-only operator commands as weighty cards

Design yardr-6maq, proposed 2026-11-11. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

A *card* is an ask a person answers by approving rather than by picking words: a run ask (`Ask.Run`, one yardr command of a fixed list), a setup ask (`Ask.Setup`, a pack's whole setup), a secret ask (`Ask.Secret`, a value typed unseen) and a mapping ask (`Ask.Identity`). A card is *weighty* where approving it widens what reaches outside the yard, whose word or credential counts as a person's, or what runs inside the yard (`internal/store/weight.go`), and *strong* where its weight carries `trust` or `code`. A *device* is one program of a user that calls the yard from outside it, let in by a token the yard gave it; a paired phone running the yard's app is one. The *operator* is the user the `operator` setting names by default and, for approval, every user whose role is operator. A *hook* is a webhook endpoint `POST /hooks/<name>` that turns an outside system's deliveries into events; its *says*, *makes* and *map* tables and its `--as` crew member are defined under What exists today. A *pack* is a way of working as one directory. The *hosted web* is the browser view of a hosted yard behind its gateway, where a strong card is approved under a fresh sign-in; a *hosted yard* is one the service made and runs, whose operator has no shell on the machine it lives on. docs/glossary.md has the rest of yardr's words.

## 1. The question

Mckean asked, on 11 Nov 2026 (mail 179000): "file most to cards, since we have weighty". The case that showed the gap was a hook replacement (yardr-3fwn) that could not go on a card: six says lines had to be retyped as a 25-line terminal command mailed to an operator on a phone. This design decides, for every operator command that today only a terminal may give, whether it becomes a card, what weight that card carries and what the card shows whole, so that the operator away from the machine is not blocked — and names the rows that stay in a terminal, with the reason for each.

## 2. What exists today

### 2.1 How a command becomes a card today

A run ask proposes one command of the list in `internal/store/runask.go` (`runList`, extended in `runask_call.go`, `runask_crewset.go`, `runask_devicerm.go`, `runask_grouprename.go`, `runask_groupset.go`, `runask_hookrm.go`, `runask_linkmove.go`, `runask_peerset.go` and `runask_sourcemove.go`). Each row carries the same six parts: how its words are read into one stored form, the command's own permission check run as the asker, the card the yard writes from its own records (its `Does` sentences, the command that takes the change back, and a `Seen` fingerprint of everything the effect rests on), why an older card is stale, what weight it carries, and the store function that makes the change on approval. `yardr bead ask --help` prints the list; a test holds the help to the list, so a row without its entry there fails.

An approval re-writes the card from the yard as it then stands and refuses, running nothing, where what the command names or changes is no longer what the card said (`internal/store/weight.go`, `weightStale`). The yard runs the command stored on the ask and takes no word of it from the approving call, once for one ask. A card's weight is weighed in the write that stores it and again in the approval's write, never from the asker's words. The six classes are `credential`, `as-user`, `outside`, `code`, `trust` and `reads`; a card that narrows carries none. A weighty approval must say `weighed` — the client's word that its person saw the weight and passed the client's gate — and a client that has never heard of weight cannot approve one by accident. A strong card (weight `trust` or `code`, `StrongWeight`) is approved from a paired device as any weighty card is, with `weighed`; the hosted web approves it only under a fresh sign-in (a gateway authentication for a strong card no more than fifteen minutes earlier), and on the yard's socket a terminal approves it as any card is (docs/api.md, Weighty cards; docs/users.md, Strong cards). What such an approval made stands after `yardr user device rm`; each approval through a device is marked `via <device>` on its answer and its event.

An approval has no transient channel today, which section 3.4 must add for one row. `ApproveAsk` (`internal/store/runask.go`, `ApproveAsk` and the `wtx.approveAsk` it runs inside `Store.writeVia`) returns `AskApproved` — bead, ask, asker, argv, the card's `Does` sentences and one string, `Result`. That string is the run function's return, and the same write that runs the command marshals it into the bead's answer (`Answer{Ask, Ran: &AskRan{Argv, Result}}`, `AskRan` in `internal/store/askran.go`) and records that answer with `addWitnessed`; every later read of the bead (`ResolveAsks`, the bead views in `internal/rpc/beadview.go`) therefore carries the code a pairing answers with if it were put in `Result`, and putting it nowhere in `Result` leaves the approval's caller with nothing to show. The callers that would have to carry such a channel are already enumerable: the generated socket client (`internal/rpc/client_gen.go`, from `store.API` in `internal/store/api.go`; `go generate ./internal/rpc` rewrites it), the listener's serving of `ApproveAsk` to an operator's device alone (`internal/rpc/user.go`, `operatorCall`, with a user's own `GiveSecret` as the one body-judged exception in `internal/rpc/usersecret.go`), the terminal (`internal/cli/bead_answer.go`, which prints `done.Result`), the hosted web (`internal/web/approve.go`: `approveNow` returns only an error, and `beadApprove`, `approveStrong` and `handleFresh` each end in a redirect to the bead page, so an approval's return is discarded there today), chat (`internal/chat/answer.go`, `approveWith`) and MCP (`internal/mcp/tools.go`, whose answer tool appends `done.Result` to what its client reads). No approval is recorded in phases for this either: the phased approvals that exist (a hook the yard registers, a source check) carry their secret between their own writes in a job struct the store keeps nowhere (`hookRegisterJob` in `internal/store/runask_hook.go`), which is a precedent for carrying a secret through a call without storing it, not for returning one.

What no card may propose is marked at the check itself. An operator-only check carries an `AskClass`: `Askable` where a run ask may propose it, `Alone` where it may not, and an unmarked refusal reads as `Alone`, so a new operator-only check lands in a terminal until its site says otherwise (`internal/store/policy.go`, `internal/store/settings.go` `settingAsk`, `internal/store/sources.go` `sourceSetAsk`, `internal/store/define.go`). `internal/store/runask_alone.go` (`aloneList`, `checkAlone`) refuses the commands no row carries — among them `user device add`, `user device pair`, `pack apply` in its general form and `source key` — with the words "it is the operator's alone, typed in a terminal and never proposed as a run ask". A delegated run (the yardmaster running a command on the operator's cited local mail, `internal/store/delegation.go`) is a separate door with its own list in docs/users.md, What it runs; it approves nothing and every form this design adds stays refused there unless a row below says otherwise.

### 2.2 The hook rows

A hook stands as `Hook` in `internal/store/hooks.go`: its source, the file its signing secret is read from (`SecretFile`, read on every delivery; the file the yard owns for a hook is `HookSecretFile`, `<home>/hooks/<name>.secret`, mode 0600), what an unmapped sender is (`Unknown`), the crew member its issue moves are made as and its says outcomes are reported as (`As`), which issue status a bead's stage moves to (`Map`, `<bead type>:<stage>` to a state or a label; a map needs `--as`), what the source's events say of the bead they are about (`Says`, ordered lines of `<key>=<value> ... -> <outcome>`; the first line an event matches counts), and what they make where no open bead tracks the thread (`Makes`, ordered lines to `<type>:<stage>` in a depot). `yardr hook add` replaces the definition whole: the whole map and every says and makes line are given again to change one line.

The run list carries one hook add shape, in `internal/store/runask_hook.go` (`parseHookAdd`, `hookAddCard`, `hookAddStale`, `runHookAdd`, weighed `trust` by `hookAddWeight` in `internal/store/weight.go`): `hook add <name> --source <declared source> [--unknown <word>]` for a new hook whose name is free, verified with a signing secret given beforehand on the hook's own secret card (`--secret-hook`) into the file the yard owns for it. A replacement, `--says`, `--makes`, `--map`, `--as` and a secret file of the operator's own are each refused, naming a terminal (`yardr hook add <name> --source <source> --secret-file <file>` in the refusal). Removing a hook is a strong `trust` card already (`internal/store/runask_hookrm.go`). Yardr-xw5j, decided directly by mckean as this design's first slice, extends the row to a replacement and to a new hook carrying those four flags; section 3.2 takes it as decided and decides only what it leaves open.

### 2.3 The pack rows

The terminal command is `yardr pack apply <pack>` (internal/cli/pack.go). `<pack>` is a bare name (a pack yardr embeds in `packs/packs.go`, or one the yard has imported, read again from where it was imported from), a directory where it has a path separator in it, or a URL fetched when the command runs; plain http is refused except for a server on this machine. Beside `--depot`, the terminal's flags answer what importing would ask and shape the import: `--flow`, `--crew`, `--group`, `--bind`, `--members`, `--open-threads` and `--calls` (the *mappings*), `--sha256` (apply only the pack whose digest this is), `--yes` (apply without asking for confirmation, and overwrite an installed file that was edited by hand), `--prune` (remove what an earlier import brought and the pack has dropped since), `--depot-roles` and `--pack-roles` (whose role text wins where a depot has its own), `--source-env`, `--source-base` and `--notify` (for a source the pack declares, the file its credential is read from, which region base its calls go to, and which user is told through it), and `--auth` (send the header in a file with every fetch of a pack at a URL). Without a terminal the import asks nothing: a missing answer is an error naming every missing flag at once, and `--yes` is needed to apply.

The run row (`internal/store/runask_pack.go` `packApplyCard`, parsed by `parsePackApply` in `internal/store/packmappings.go`, weighed by `packApplyWeight`) takes an embedded pack by name only, with `--depot` and the mappings and no other flag. The card is built inside the write that stores the ask from the server's own reading of the embedded pack (`internal/server/packreader.go` `readEmbeddedPack`, registered with `SetPackReader`), never from bytes the asker sent: each declared source whole with its command files, and for a depot pack the plan object by object with each file's diff whole, or its summary shape where the whole card passes its bounds and replaces no standing source (`internal/store/runask_packcard.go`, design yardr-y6gp). Three bounds refuse the ask to a terminal: declaration text together (`MaxRunPackDeclarations`, 256 KiB), carried file texts and diffs together (`MaxRunPackFiles`, 64 KiB; 1 MiB carried on a summary card), and the card's sentences (`MaxRunSourceCardLines`, 40). A plan that still asks anything after the mappings, is refused, would overwrite a file edited by hand (its `Edited` list), or holds a changed file whose bytes are not text is refused whole at the ask, naming `yardr pack check`. A directory, a URL or an earlier import's record is refused in the reader itself: a card is written from the binary the yard runs and from nothing else.

Two neighbouring doors already apply packs without this row. A setup ask (`yardr bead ask --setup <pack>`) installs a pack of kind source as one decision — the apply, the account and the grants — for an embedded pack, or for one the operator applied from a directory in a terminal and left as it was, refused where that directory is at another commit or has uncommitted changes. A delegated pack apply (docs/users.md, What it runs) applies an embedded pack, or a pack of the packs repository by its URL pinned with `--sha256`, on the operator's cited mail and told after: the repository is the one address in `internal/pack/repository.go` (`RepositoryPack`, `LoadRepository`), which holds the fetched pack to its digest before anything is read of it and reads every file from the first answer. The store fetches such a pack through `PackFetcher` (`internal/store/delegation_repo.go`, `internal/server/packrepo.go` `packFetcherFor`), outside a write, and no other URL is fetched for a delegated run. A delegated run takes no `--prune` and answers no plan question.

Yardr-vdh6, shaped and waiting in backlog, proposes the directory half of this gap: `pack apply <dir>` for a directory inside a registered depot's main checkout, read at ask time into the same carried card under the same caps, pinned by a digest over the directory's files in path order, weighed strong for the code it brings. Section 3.3 reckons with it.

### 2.4 Definitions: free args and where a session's environment comes from

What a group or a crew member runs is held to the operator at the store (`internal/store/define.go` `checkGroupDefine`, `checkCrewDefine`): a group's `cmd`, `dir`, `env_file`, `kind`, `args`, `prompt`, `worktrees` and `effort`, and a crew member's `env_file`, `env_command`, `kind`, `model`, `args` and `prompt`, each `Alone` except where a row below carries it. `args` is the list of arguments the harness is started with (`internal/store/configkeys.go`); a permission *preset* is a named flag set of the kind (`yardr harness show <kind>` lists them), some of which skip the agent's permission prompts and are marked strong for that. `env_file` is a file of `KEY=VALUE` lines, a regular file of mode 0600 or stricter, read at each session start and joined to the session's environment; a crew member's `env_command` is a command run for that environment instead. Neither file's values nor a command's output stand in the store.

Cards already carry the bounded forms. Adding a group (`internal/store/runask_groupadd.go`) takes `cmd`, `dir`, `kind`, `args`, `prompt` and `worktrees` as `--set key=value` — `args` as one plain-text word, since a run ask splits at spaces and quotes nothing, refuses what reads as JSON, and refuses `env_file`, `env_command` and `log` naming the terminal instead — and is weighed `code` for the command or agent it starts. Adding a crew member (`internal/store/runask_crewadd.go`) takes `kind`, `model`, `preset`, `dir` and its role text whole and refuses free `args` in words that say to name a preset instead, and refuses `env_file` and `env_command` as the operator's alone. Changing a standing group or crew member carries only its grants (`crew set` of `open_threads`, `set_state`, `peers`) and, on a second row sharing the strong few (`internal/store/runask_groupset.go`, `runask_crewset.go`, `runask_strong.go`), its `prompt`, an exec group's `cmd`, a permission `preset` and a group's `effort`, each shown now and after, whole, and weighed `code`; the yardmaster's own entry alone also carries its `kind`, `model` and `dir` there. Free `args` on a standing group or member — `group set <name> args=<words>` or `crew set <name> args=<words>` with words no preset names, including `--unset args` — is refused as the operator's alone (`aloneGroupKeys` in `internal/store/runask_alone.go`, `crewAloneKeys` in `internal/store/runask_crewgrant.go`), as are `env_file` and `env_command` on every row. A delegated run names a preset and never free args, and never a preset that skips permission prompts (`presetOnly` in `internal/store/delegation.go`).

### 2.5 Where a credential or an address is read from

A declared source names, in its declaration (`internal/source/declaration.go` `Credential`), the variable its credential is held in, the one an update call uses instead where it names one, the variables that together select a minted credential, and optionally a mint command the declaration itself brings. Where the yard reads them is the source's record (`internal/store/sources.go` `Source`): `env_file`, the path of the file those variables are read from at each call, and `mint_command`, the operator's one-line command (split on spaces, without a shell) that turns the mint's inputs into a short-lived token, which wins over the declaration's own. `yardr source set <source> env_file=<file>`, `mint_command=<command>`, `calls_per_hour=<n>`, `updates_per_hour=<n>` and `base=<name>` set them; the run row for `source set` takes the two hourly limits alone, and `sourceSetAsk` marks where a credential comes from and where it is sent — `env_file` and `base` — and the command that mints one as `Alone`. Giving a value is a different act and already has its doors: `yardr source key` at a terminal, and a secret ask (`--secret <source>`, with `--as <user>`, `--for-crew <member>` and `--for-user <user>` for the other files a value can go to), which has the value typed unseen and written by the server into the file the credential or address is read from — the source's standing `env_file` or, with none set, the yard's own file for it, which is then set. No call reads a credential or an address back.

A user's address in a source that tells people is the same shape on the user's record (`internal/store/users.go` `User`): `notify`, the source that tells them outside the yard, and `env_file`, the file the variable its `notify` key names is read from at each send. `yardr user set <user> notify=<source>`, `env_file=<file>`, `tell=<parts>` and `role=<role>` set them at a terminal. Cards carry `tell` and `role` (the second weighed `trust` in both directions, `internal/store/runask_userrole.go`), `user key <user> <source>` carries the address value itself into the standing or default file, and a secret ask with `--for-user` does the same for one variable; `notify` is carried by a delegated run alone, and `env_file` by no card and no delegated run. The files and commands of this configuration are told to a device of the operator alone; a user's own device is sent their record without `env_file` (docs/api.md).

A hook's secret file is the same pointer a third time (section 2.2): at a terminal the operator names any file with `--secret-file`; on a card the hook names the file the yard owns for it and the value arrives on the hook's secret card.

### 2.6 Pairing a device, the operator setting, and where the yard reads and serves from

`yardr user device add <user> <device>` makes a device and prints its token once; the store keeps the token's hash and never the token. `yardr user device pair <user> <device> [--url <address>] [--qr]` instead opens a *pairing*: the yard shows a short code, good for ten minutes and for one device, and the device that calls with it is answered with its token, so nobody types or pastes the token (`internal/store/devicepair.go`). One pairing stands at a time, in the server's memory and nowhere else; five wrong codes end it, and `yardr user device pair --end` ends it without a device. Both commands stand under `ActAddDevice` — only an operator adds a device, and never from an agent's pane, whoever the command says it is — and both are `Alone` as run asks, so no card proposes either. Over the socket API, `DevicePairOpen` is the operator's alone and a device token is answered as for a method the yard does not have, on the listener and down the edge link alike; `DevicePairOpenSelf` opens a pairing for the signed-in user themselves with no such check, and the web view's pairing page once served it — it does so no longer for an app that calls through the edge, because the edge could read or rewrite any code or QR code the page showed and a device paired from it would pin a key the edge chose (`internal/web/pairing.go`). The sealed form of a pairing, where the device pins the yard's channel key from a QR code shown on the yard's own screen and redeems the code inside a handshake to it, therefore has no self-service page today; the plain form, where whoever has the code within its minutes gets the token and the connection is what protects it, is the only one a page or a card could offer away from that screen. Removing a device is already a card (`user device rm <user> <device>`, asked of the user whose it is or of the operator, either approving), which says how many devices the user keeps.

Opening a pairing cannot be called from inside an approval's write as it stands, which section 3.4 must also add. An ordinary run row's `run` function executes inside that write — one Bolt batch transaction (`internal/store/store.go`, `Store.write`; `internal/store/via.go`, `writeVia`) — while `openDevicePairing`, the shared body of `DevicePairOpen` and `DevicePairOpenSelf`, first does its own `s.read`, then takes the pairing lock (`s.devPair.mu`, whose comment fixes its order: taken before any of the store's locks, never after), then calls `s.LogEvent` — itself a separate `s.write` (`internal/store/events.go`) — and only then assigns the in-memory `s.devPair.cur`. Called from a run function it would attempt nested store access under a lock the write may already be waiting behind, and its event would commit apart from the approval's answer or not at all. The transaction's own event writer already exists for the atomic half: `w.event` (`internal/store/store.go`) appends an event in the caller's transaction, as `addWitnessed` records the answer there, so a pairing opened in the approval's transaction needs its event written that way and its in-memory publication deferred until the batch commits, in the pattern of what `Store.write` already does after commit with the work a transaction queued for it. Its leave also differs by caller in a way a card must reproduce, not flatten: `DevicePairOpen`'s check is `may(ActAddDevice)` against the named user, while `DevicePairOpenSelf` takes no `may` at all and is safe only because its caller passes the signed-in user as both user and actor; a run row approved by the named user needs the second leg judged in the transaction, and one approved by anyone else the first.

The `operator` setting names the user an ask with no `--to` goes to and whose login and inbox the yard uses where it needs one person's; who may administer and approve is each user's role, and naming a user in the setting makes them an operator. `settingAsk` marks it `Alone`, with the settings of where the yard reads and serves from: the addresses its servers bind (`hook_addr`, `web_addr`, `web_pages_addr`, `web_pages_host`, `bdp_addr`), the edge it is connected to and the key it pins there (`edge`, written by `yardr edge connect`), whether it is hosted (`hosted`, which decides whether secrets cross the edge's link), the address of its router (`router_addr`), and who the web view acts as and what it trusts (`web_as`, `web_jwt_issuer`, `web_jwt_audience`, `web_jwt_jwks`, `web_jwt_header`, `web_jwt_users`). The one serving-adjacent setting a card already carries is `hook_public_url`, marked askable precisely because it binds nothing and serves nothing: it only says where the yard is reached from outside, and its card shows the whole URL each hook is registered at. A new setting defaults to `Alone` until marked askable.

### 2.7 The two beads this design must reckon with

Yardr-xw5j (hook replacement, in `new`) and yardr-vdh6 (directory pack, in backlog) are both shaped. Neither depends on the other, and neither depends on this bead: mckean decided the hook slice directly, and the directory slice was shaped against the embedded card that has since landed. This design therefore does not re-decide either. It takes yardr-xw5j's row, weight and refusal split as the decision for the hook's tables, constrains yardr-vdh6 where what it cites has moved since it was shaped, and decides everything around them. What has moved is the strong gate: yardr-vdh6 as written has its card approved under a fresh sign-in or at a terminal and never from a device, citing the gate as it stood when it was shaped. As built today (section 2.1), a strong card is approved from a paired device as any weighty card is, and the fresh sign-in and the terminal are the other doors, not further conditions on a device's approval. Any build of either bead follows the gate as it stands at landing, and this design builds no second gate for any row. One ordering this design does add is for shared files alone: yardr-xw5j and every yard bead in section 6 all edit the stolen-device table and the "What it still cannot have run" sentence in docs/users.md, and the `--run` help in `internal/cli/bead_ask_runlist.go` that the run-list test holds to the list, so section 6 lands its yard beads in one chain after yardr-xw5j — a dependency for those edits, not for what any row does.

## 3. The proposal

The smallest change that answers the question adds rows to the one list. Every new card below is a run ask on the existing row machinery: the yard writes the card from its own records, the approval re-writes it and refuses as stale where it differs, the approving call says `weighed` where the card is weighty, a strong card takes the standing doors (a paired device with `weighed`, the hosted web under a fresh sign-in, a terminal on the yard's socket), and the change runs once, as the approver, through the store function the terminal command calls. One row is the exception that proves the machinery's edge, and this design says so rather than claiming no approval changes: pairing (section 3.4) cannot ride an unchanged approval, because its effect is a secret that must reach the approver and rest nowhere, and because opening a pairing cannot be called from inside the approval's transaction as that call stands today (section 2.6). It therefore adds exactly two things to the approval itself — a transient field on its return that is never the stored answer, and a transaction-aware way to open a pairing in the approval's own write — both used by that row alone. No new ask kind, no new weight class and no new gate is built for any row; a witness on the device is left out on purpose (section 4). A crew member or a user files each new ask by mail to the yardmaster as run asks are filed today, and an agent working a bead still files none. The delegated door gains none of these forms: what is told after it runs is a shorter list than what is approved before, and each row below that a delegated run could otherwise reach keeps refusing there in its own words.

A person at a terminal files and approves the new cards exactly as the existing ones, for example:

```text
$ yardr bead ask yardr-example - --run "pack apply ./packs/team --depot web --sha256 sha256:<digest>" <<'ASK'
Q: Apply the team pack from the depot checkout?
C: The pack in the web depot's checkout changed its reviewers group.
ASK
$ yardr bead answer yardr-example 7 --approve
```

and on the phone the same card stands among the person's decisions with its `WEIGHTY` lines first, its command whole and the yard's sentences for what approval does. What differs per row is only the command the row takes, the weight the yard gives it and the sentences its card carries. The decisions are these; section 3.5 lists the stolen-device rows they add, and section 4 the rows that stay in a terminal.

### 3.1 The decision per row

| the terminal-only row today | the decision | the card's weight |
|---|---|---|
| Replacing a hook; a hook add carrying `--says`, `--makes`, `--map` or `--as` | A card (yardr-xw5j, as decided; section 3.2) | `trust`; strong |
| A hook add naming a secret file of its own (`--secret-file <file>`) | No card; the card's hook keeps the file the yard owns for it (section 4) | — |
| A pack from a directory | A card, constrained from yardr-vdh6 (section 3.3) | As an embedded pack's: `code` where it brings or changes a program, a file, a group or a crew member, with `outside`, `trust` and `reads` where its plan and mappings bring them; strong wherever `code` or `trust` stands |
| A pack from a URL | A card for the packs repository's URL pinned with `--sha256` alone; any other URL stays in a terminal (section 3.3) | As an embedded pack's |
| `pack apply --yes` | A card only over the hand-edited files it overwrites, shown whole; `--yes` as bare confirmation is refused on a card, whose approval is that confirmation (section 3.3) | The pack's, over the edited files as changed files |
| `pack apply --prune`, `--depot-roles`, `--pack-roles`, `--auth`, `--source-env`, `--source-base`, `--notify` | No card; each stays in a terminal, for the reason in section 4 | — |
| A pack plan that still asks after its mappings | No card; refused at the ask as today (section 4) | — |
| Free `args` of a standing group or crew member; free `args` on `crew add` | No card; a named preset rides the cards that already carry one, and free words stay in a terminal (section 4). A new group's one-word `args` already rides its add card and does not change | — |
| `env_file` of a group or a crew member; `env_command` of a crew member | No card (section 4) | — |
| Where a source's credential is read from (`source set <source> env_file=<file>`, and clearing it) | No card (section 4). Giving the value itself already rides a secret ask | — |
| The command that mints a source's credential (`source set <source> mint_command=<command>`, and clearing it) | No card (section 4). A mint command the declaration brings already rides the card that carries the declaration | — |
| Where a user's address is read from (`user set <user> env_file=<file>`, and clearing it) | No card (section 4). Giving the address itself already rides `user key` and a secret ask | — |
| Pairing a device (`user device pair <user> <device>`) | A card, for every user (section 3.4) | `trust`; strong |
| Adding a device (`user device add <user> <device>`) | No card; its token is printed once and no approval carries one (section 4) | — |
| The `operator` setting | No card (section 4) | — |
| The settings of where the yard reads and serves from | No card (section 4). `hook_public_url`, which binds nothing, already rides its card and does not change | — |

"Most" is therefore the outcome, and "any" is not: of the rows the bead names, the ones whose whole effect a card can show — a hook's tables, a pack read whole and pinned, and the opening of a pairing — move, and the ones whose effect is a file's contents, a program's future output, an unbounded word's meaning, or the yard's own root pointers stay where the operator types them. The yardmaster's candidates to keep off cards were pairing, the operator setting, and reading or redirecting a credential or its mint. This design moves the first, on mckean's later word recorded on the bead (mail 179042: "pairing needs a card, every user needs to be able to pair their device to a yards user"), and keeps the other two, for the reasons section 4 gives per row rather than as a class slogan: in each case the card could quote the words whole and still not show the effect whole, which is the one thing a weighty approval is for.

### 3.2 The hook's tables (yardr-xw5j, taken as decided)

This design creates no bead for this row and changes nothing yardr-xw5j specifies: the run ask takes `hook add <name>` with the full table, for a hook that stands (a replacement) and for a new one alike; the card is weighed `trust` and shows the hook now and after — each says, makes and map line added, removed or moved, with order counted because the first matching line is the one that counts, the `--as` crew member now and proposed, the source now and proposed where it changes, the `--unknown` word where the source hears by identity, and the secret file the hook names — whole, under the same caps the pack and source cards use, refused rather than summarised where the table is too long for the card. The secret file a replacement keeps is the one that stands; a card proposes no other (section 4). The same refusals the terminal makes — an outcome no flow edge has, a map without the crew member it acts as, a crew member without an identity in the source — are made when the ask is written and again when it runs, the delegated run still refuses these forms, and approval runs `putHook` exactly as the card showed. Because the row is decided and in flight, no bead in section 6 repeats it; for what the rows do, none of them needs it either. They do wait for its landing for one file reason alone: yardr-xw5j edits the help's hook row, the stolen-device table and the "What it still cannot have run" sentence, and every yard bead in section 6 edits the same table, sentence and help file for its own row, so the chain in section 6 starts after yardr-xw5j lands and each bead leaves its words standing and adds only its own. That is an ordering of landings, stated as dependencies there, not a dependency of any row's behaviour on the hook row.

### 3.3 Packs read whole and pinned: a directory, the repository's URL, and `--yes`

**A directory.** The build bead is yardr-vdh6, constrained in two respects and otherwise as shaped. First, its approval gate is the standing strong gate of section 2.1 — a device approves with `weighed`, the hosted web under a fresh sign-in, a terminal on the socket — and its text is corrected wherever it still says a device never approves; no bead builds the older refusal again. Second, what it shows is stated against the caps as they stand, so the hard case the bead names has an answer: the directory is read at ask time into the same carried card an embedded pack builds — `pack.yaml`, each declaration whole, each program file's content or hash, the plan and the mappings as the kind asks — under the same three bounds, and past any bound no card is written: the ask is refused in the embedded row's words, naming `yardr pack check <dir>` at a terminal, where the plan is shown there. No summary shape is proposed for a directory (section 4). Eligibility, pinning and stale are yardr-vdh6's as shaped: only a directory inside a registered depot's main checkout, the path resolved with symlinks followed and judged against the depot's root (a worktree is not its main checkout), any other path refused at the ask naming the rule and the terminal road; the content pinned in the card's `Seen` as a digest over the directory's files (relative path and bytes, in path order), so a file changed, added or removed since the ask makes the approval stale and nothing runs; approval applies through `ActApplyPack` exactly what the card carried. URL and record packs gain nothing from this row, and pack flags gain nothing except as the next paragraphs say: the command a card takes is `pack apply <dir> [--depot <depot> [mappings]] [--sha256 <digest>]`, where a `--sha256` the asker names from `pack check` must name the directory as read and refuses the ask where it names another, and with none named the card still pins what it read — the digest over its files stands in its `Seen` and is printed whole on the card as `digest sha256:<hex>`, so approval is held to those bytes either way.

**The repository's URL.** The same row takes `pack apply <url> --sha256 <digest>` where `<url>` is the packs repository's alone — the origin and one pack's name, as `RepositoryPack` holds it, and no other host, scheme, ref, sub-path, query or user — and refuses every other URL at the ask, naming the terminal. The server fetches the pack through the standing `PackFetcher` outside the ask's write, holds it to the digest before anything is read of it, and reads the card from those bytes once, never from a second answer; the card is then the embedded card's, with the URL whole where the label stands, the pack's name held to its directory's, and the digest printed whole. Its weight, caps, stale and carrying out are the embedded row's. This is the URL case whose provenance a card can show whole: the repository's owner vouches for what its branch serves and the digest names the bytes, as the delegated door already trusts it. A pack at any other URL — fetched from an address the asker chose, with no owner the yard names and, for `--auth`, a header in a file the card cannot show — stays in a terminal, where `pack check <url>` shows its plan before it is applied. On an embedded pack named bare, `--sha256` alone still refuses as it does today: the card already pins the reading it was written from in its `Seen` and prints the digest where the reading carries one, so the flag would name a second pin for the same bytes and approve nothing more.

**`--yes` over hand-edited files.** At a terminal `--yes` does two things: it answers confirmation without asking, and it lets the import overwrite a copy under `<home>/packs/<pack>/` that was edited by hand. On a card the first is the approval itself, so a `--yes` that overwrites nothing is refused at the ask in words that say to propose the apply without it. Where the plan's `Edited` list names files, the row takes `--yes` and the card shows each such file whole: its path, the SHA-256 of the copy that stands (the hand edit) and of the pack's bytes, and the unified diff from the one to the other, counted in the same payload bound as any changed file and refused past it. The card says in its own sentence that approval overwrites the edited copy and keeps no other copy of it. Approval is then held to those hashes as it is held to the plan: an edited file changed again since the ask, or a new one edited since, is stale and nothing runs. A plan that asks, is refused or holds non-text bytes still refuses with or without `--yes`; `--yes` answers the edited files and nothing else. The card's weight is the pack's weight over the edited files as changed files — `code` where an edited file is a program, a role or a script the yard will run, as `packApplyWeight` already weighs a changed file — so the overwrite of a hand-edited program is strong and takes the strong doors.

What a person types for the two pack rows is the one command on the ask, for example `--run "pack apply https://raw.githubusercontent.com/yardr-dev/yardr-packs/main/team/ --depot web --sha256 sha256:<digest>"`; the yard splits it at spaces and nowhere else, as every run ask, and the card shows the URL, the digest and the plan whole. Nothing is fetched for a card the yard refuses: a URL outside the repository, a digest that names other bytes, a directory outside every depot checkout and a plan that asks each refuse before any reading the operator has not already been shown at a terminal by `pack check`.

### 3.4 Pairing a device, for every user

The new row is `user device pair <user> <device> [--url <address>]`, filed and approved as a run ask whose command is the user's own, in the way `user key` and `user device rm` already are: it is asked of the user it names or of the operator (`--to` names that user, defaulting as a user's own ask does), and either of them approves it — the user from a device or session they already hold, the operator from any door. An operator pairing their own device, and an operator pairing a member's, are the same row with the approver the ask names. There is no `--qr` flag on the row: showing the QR code is the approving client's work on approval (below), and `yardr user device pair --qr` on the yard's own screen keeps the terminal form it has.

Asking opens nothing. The card the yard writes names the user and the device whole, the address the device will reach the yard at (the `--url` where the command names one, whole; otherwise that the yard gives the pairing its listener's address, or the edge's where the yard listens nowhere and its link is up, as the terminal command does), every device the user then has by name with when each was last used, and in its own sentences: that approval opens a pairing for that device alone, good for ten minutes and for one device, that whoever has its code within those minutes is answered with that device's token and nothing in the yard keeps the code after it is used or runs out, that the new device then calls as that user until `yardr user device rm <user> <device>`, and how many devices the user will then have. The code itself stands on no card, in no note and in no event, as it stands in none today. The card is weighed `trust` — a new device speaks as its user from then on — and is therefore strong: the hosted web approves it under a fresh sign-in, and a device approves it only as the user's own device is newly served `ApproveAsk` for this row, with `weighed`, as a device is already served `GiveSecret` for that user's own address. That serving is the listener's work, judged from the call's body as `ownSecret` already judges a giving (`internal/rpc/usersecret.go`, called from `UserServer.call` in `internal/rpc/user.go` before the call is made): a check in that pattern reads the bead and ask the body names, reads the ask from the yard's notes, and serves the approval only where the run ask it names is this row and the user its argv names is the device's own user; an operator's device is served it as every `ApproveAsk` already is, and every other device — another user's, and a device naming another user's pairing — is answered as for a method the yard does not have, its body otherwise unread in that judgement. Who may approve is still the store's to decide in the write; the listener only decides whether the call is there at all. Approval through a peer's reach is refused, as it is for every link-widening row, and a device of any other user is served neither the card's held words nor the approval.

Approval answers once, to the approver alone, with everything the new device needs and nothing that may rest — and the approval itself gains the channel for that answer, since none exists today (section 2.1). `AskApproved` gains one field, `Pairing *AskPairing`, holding a pairing just opened: the user and device, the code in the form it is shown (`XXXX-XXXX`, as `displayCode` leaves it), the address the device reaches the yard at, the yard's name there where the address is the edge's, when the code runs out, the yard's channel public key where it has one, and the QR string those fields make in the form `DevicePairingState` already defines (`<address>#<code>`, with `#<yard>` where the address is the edge's, and `#<channel public key>` as its fourth field where the yard has one). It is set by this row alone and is absent (`omitempty`, nil) on every other approval, whose return is otherwise unchanged. It is a return value and nothing else: the run function for this row returns as its `Result` only the safe sentence the bead keeps — that a pairing was opened for the named device of the named user, when it runs out and that the code was shown to the approver alone and is kept nowhere — and that sentence, with the command, is all that `approveAsk` marshals into `Answer.Ran` and records with `addWitnessed`. The transient is copied into the `AskApproved` the write returns beside that record, never into the record: not into any note, answer, event's data, mail, log line or store bucket, and no later read can return it, because no later read returns `AskApproved` at all — the bead, its notes and its views carry only the stored answer, and a second approval is refused as already approved before it could answer again. The server logs no approval return, on the socket or the listener; a client that logs its calls must drop this field as it drops a secret's values, and the field's own documentation in the API contract says so in those words. Delivery is scoped to the approving call by construction: the only value that ever holds the code besides the server's in-memory pairing is the direct return of the one `ApproveAsk` call that opened it, addressed to the actor that call was made as, over the door that call came through. Each surface that approves therefore has named work, and no other surface gains the code by accident: the generated socket client carries the new field with the struct it already returns (`go generate ./internal/rpc`, and the `ApproveAsk` place in docs/api.md moves by its golden test, never by hand); the terminal (`yardr bead answer --approve`) prints the code, the address and the expiry once, as `device add` prints a token once, with the sentence below about showing it to the device and nobody else; chat's approval message shows the same once in its sitting, which is a terminal's; the hosted web shows it in the approval's own response as the paragraph after next specifies; footplate and its kin show it as section 6's client beads specify. MCP is the one approving surface refused this row: its answer tool returns what the yard ran to a client whose transcript rests, so it refuses a pairing approval in plain words naming footplate, the hosted web or a terminal, and never calls `ApproveAsk` for this row — the yard runs nothing and the ask stays open. A device of another user is served neither the transient nor the approval that makes it, as the card paragraph above already holds.

The pairing is opened inside the approval's own write, by a transaction-aware path this design adds for the row rather than by calling `DevicePairOpen` there (section 2.6). Before the write, `ApproveAsk` recognises the pairing row as it already recognises a hook registration or a source check before theirs (`hookRegisterTarget`, `sourceCheckTarget`): it takes the pairing lock first — before the ask lock and before any store lock, in the order `devicePairings` fixes — and holds it until the write has committed and the pairing is published, so no terminal opening, redemption or close can interleave with an approval's opening. The code, the pairing's id and its expiry (ten minutes from the pairing clock, as today) are made once, before the write, as a paired device's token is made before its write, so the Bolt batch's possible second run of the transaction ends the same and publishes the same pairing. Inside the write, the row's run function does in the transaction what `openDevicePairing` does across three: it judges the busy state from the in-memory pairing under the lock it already holds — an open one not yet run out refuses in the pairing's own words (the holder's yard user alone, never the device, the code or when it runs out) and is not stale, so nothing is written and the ask stays open; one whose time has run out is ended there, its `device_pair_refused` event written in this transaction by `w.event` rather than by a nested `LogEvent`. It then takes its leave in the transaction: where the approver is the user the pairing is for, the self leg of `DevicePairOpenSelf` — no `ActAddDevice`, the actor already proved to be that user by the approval's own `whose` gate — and where the approver is anyone else, `w.may(ActAddDevice)` against the named user as `DevicePairOpen` checks it; either refusal writes nothing. It checks the device name and that the name is still free in the transaction (`checkDeviceName`, `deviceFree` against the transaction, not a prior read), writes `device_pair_opened` by `w.event` with the pairing's id, user, device and expiry and never the code, and leaves the pairing itself — code included — in a pending value on the transaction beside the queued work `Store.write` already discharges after commit. Only when the batch commits does `ApproveAsk` publish it, still under the pairing lock: `s.devPair.cur` takes the pending pairing, and the transient is filled from that same value for the return. A write that fails for any reason — the card gone stale, the busy refusal, a leave refused, the event or the answer failing — commits neither the answer nor the event, publishes no pairing, answers no code, and leaves the ask open; the approver is simply refused, as any refused approval is. Publication after commit cannot itself fail, being one assignment under a held lock; the one window it cannot close is the server stopping between commit and publication, which ends every pairing anyway, since a pairing lives in the server's memory and ends with it — the stored answer then says a pairing was opened where none stands, the code was never answered to anyone, and approving again is refused as approved, so the person files the ask again once the yard is back, exactly as they would for a pairing whose server restarted inside its ten minutes.

The approving client shows the transient at once, in that sitting and nowhere else: footplate on a device the user already holds renders a QR code from it and prints the code itself beside it for a device that must type it, holding both only in that screen's memory and dropping them when the person leaves it or the code runs out. The new device scanning that QR code pins the yard's channel key from it and redeems the code inside the sealed handshake, so whoever carries the connection after the scan reads neither the code nor the token it is answered with; a code typed or read aloud pairs plainly, and the connection is then what protects it, as today. The QR code is drawn by the app the person already trusts on a device already paired, from an answer that came to that device; no page the edge serves before approval draws one, and the withdrawal of the standing web pairing page (`internal/web/pairing.go`) stands for that reason. In the hosted web the same rule takes a new shape, because its approval today discards the return and redirects to the bead: `approveNow` in `internal/web/approve.go` must return the `AskApproved` it now throws away, and where that return carries a pairing, both the routine path in `beadApprove` and the fresh-sign-in paths (`approveStrong`'s immediate approval and `handleFresh`'s return from the gateway, whose one-use state already binds the return to this card alone) answer with a pairing page in that response instead of the redirect — the QR code rendered from the transient, the code beside it, its minutes counted, the code in no URL, form or redirect target, the response marked never to be stored (`Cache-Control: no-store`), and nothing of it read from the bead on any later visit, where the bead shows only its stored safe sentence. That page is an approval's answer, not a standing pairing page: it exists only as the response to the approval that opened the pairing, is served by no route a visitor can open first, and the withdrawn page's refusal stands untouched beside it. At a terminal the approval prints the transient once as above, and the person shows or reads it where they stand. Where the yard has neither a listener address nor an edge link up, asking is refused as the terminal refuses, naming that a yard with neither opens no pairing.

What crosses the edge for such an approval depends on the door it is approved through, and the doors differ in kind, not in degree. At a terminal on the yard's socket, and in chat's sitting on that machine, no edge carries anything. From a device that pinned a channel key — paired from a QR code, or a key it registered in place and now calls sealed with — the approval comes and goes inside the device's channel: the listener opens the enveloped call and seals its whole answer (`e2eCall` in `internal/rpc/usere2e.go`), so the transient crosses the edge as ciphertext the edge cannot open, and the edge is handed neither the code nor, on such a call, the device's token (docs/api.md, A registration voucher). From a device that pinned no key — a plain token call — and in the hosted web, whose gateway answers the approval, the same transient crosses in readable form: whoever carries it there, the edge included, can read the code, and could spend it first and be paired as the named user, a device that then stands until `yardr user device rm`, even if the approver's own device is removed first. Only those two readable doors raise the trust question, and whether that reading is accepted there is not this design's to settle quietly: it is open question 5, and the proposal here is written under its recommended answer.

The stored card's sentences are the same through every door, since the yard writes the card before any approver is known; the door's sentence is the approving surface's, shown with the card before the approval is given, in the same place the surface shows the card's weight. A sealed device is told that its answer comes back sealed to that device and that the edge carries it unread. A plain device and the hosted web are told, in the card's hearing before `weighed` is sent, to show the code to the device and to nobody else, since whoever has it within its minutes, the carrier of that approval included, could spend it first — and a person who does not accept that for a given pairing approves at a terminal, on a direct connection, or from a sealed device instead. The bounds that make the readable doors' acceptance a weighed one are the code's own: ten minutes, one device, five wrong tries ending it, `yardr user device pair --end` while it stands, and the `device_pair_opened` and redemption events naming the user and device (never the code) as the record that a pairing was opened and spent.

A user with no device yet cannot approve from one, and the row answers that without a second mechanism: their first pairing is asked of the operator by default, as any ask with no `--to` is, and the operator approves it from any door and shows its QR code or reads its code to the person, exactly as the operator shows a pairing today. On a hosted yard the same person, signed in to the hosted web as that user through the address the yard's `web_jwt_users` maps to them, is the user the card is asked of and approves their own first pairing there under the fresh sign-in a strong card already demands; the gateway's signed-in identity is the possession proved, and the code and QR code are the approval's transient in that sitting alone — rendered in the approval's own response from that return, held in no standing page and served by no pairing page before approval, so the withdrawal recorded in `internal/web/pairing.go` stands. A member with a device already pairs the next one themselves, scanning nothing: their held device shows the QR code and the new one scans it. While a pairing stands for anyone, an approval that would open another is refused — not as stale, since the card is still true, but in the pairing's own words naming whose pairing stands (the holder's yard user alone, never the device, the code or when it runs out, as `DevicePairOpen` refuses today) — and the ask stays open to be approved once it ends or is used. A device name taken since the ask, or the user removed since, is stale as any card: declined and asked again. Taking it back is `yardr user device pair --end`, which the pairing card names as its `Back` — at a terminal on the yard's machine while the pairing stands, by the operator or by the user whose it is from their own yard screen — and `yardr user device rm <user> <device>` on its own card once the code is used, which the pairing card's sentences name beside it.

### 3.5 What a holder of a stolen device gains: the rows added

Each new card adds its row to the stolen-device table in docs/users.md, in that table's form — the command, and what a holder of the token gains with one agent's help, the holder having first had the card proposed by mail as every run ask from a device is reached today. The hook row is yardr-xw5j's and stands there when it lands; this design adds the rest and no other. A card weighed neither `trust` nor `code` in a particular case (a directory or repository pack whose plan brings neither, an edited file that is neither program nor role) is approved as any weighty or routine card is, and its row below is read with its weight in that case.

| the command | what a holder of the token gains |
|---|---|
| `pack apply <dir>`, a directory inside a depot's main checkout, pinned by its digest: a pack applied from files that stand in that checkout | The pack the card showed stands in its depot: its flows, groups, roles and scripts, and each source it declares, as an embedded pack's approval leaves them. The holder must first have those files standing in the checkout — a stolen token writes no depot file, so this is the applying of a pack a depot already holds, not the writing of one — and what it made stands after the device is removed. Only the operator takes it back, by applying what stood before or by hand from the card's plan |
| `pack apply <url> --sha256 <digest>`, the packs repository's URL alone: a pack fetched and held to its digest | The pack the card showed, fetched from the repository, stands as an embedded pack's approval leaves it, and stands after the device is removed. No other URL is applied this way. Only the operator takes it back as above |
| `pack apply <name> --yes`, over the hand-edited files the card named: a pack whose edited copies are overwritten | The pack stands with the holder's bytes where the operator's hand edits stood; each edited file the card named is overwritten and no other copy of the edit is kept. It stands after the device is removed, and only the operator restores an edit, from outside the yard |
| `user device pair <user> <device>`: a pairing opened for one device of the user | A second device of that user is paired once its code is used, and calls as that user from then on. Removing the holder's device leaves the new one standing, and removing the new one leaves the holder's: the holder keeps a way in until both are removed, which the card names by listing the devices the user then has. Only the operator or that user pairs another, and either removes one |

The sentence in docs/users.md, "What it still cannot have run", loses the hook's tables, a pack from a directory in a depot's checkout, the packs repository's URL pinned, and pairing a device, and keeps the rest of section 4 in their place. Each build bead in section 6 moves its own row and its own words of that sentence, with `yardr bead ask --help`'s row, in the same commit, so the table, the help and the refusal never disagree.

## 4. Left out

What follows was considered for a card and is not proposed. Each row names the door the operator away from the machine already has, where there is one, so that staying in a terminal is a stated cost and not an oversight. Nothing here is built by section 6.

- **A witness on the device for a weighty card** — a fresh biometric or sign-in on the device itself, as the hosted web's fifteen minutes witness a strong card there. The bead leaves this out on purpose and mckean chose to go by weight as it stands, so no row in this design asks for it and no bead builds it. If it is ever wanted it is a second design of its own, over the `weighed` word and the client's gate, not a flag on these rows.
- **A hook's own secret file, where a source's credential is read from, and where a user's address is read from** — `hook add --secret-file <file>`, `source set <source> env_file=<file>` and `user set <user> env_file=<file>`, each with its clearing form. A card could quote the path whole — and hold it to the operator's audience as it already holds a setting's or a pack's typed words — and still not show the effect whole: the yard reads the file on every delivery, call or send, its values stand in no record, and rotating a credential *is* rewriting the file, so an approval either pins the bytes it cannot show (and goes stale on a routine rotation) or pins only the path (and approves whatever the file holds from then on). A holder who had one approved could point a source, a hook or a user at a file outside the yard's own files and have the yard read its credential or address from there on every use, pairing it with a new host where the declaration moves, and it would stand after the device is removed with no card to take it back. The values themselves already travel from the phone: a secret ask writes what the person types, unseen, into the file that stands (or the yard's own file for it, which is then set), and `user key` does the same for an address. What stays at a terminal is only the choice of a different file, and on a hosted yard that choice is the hosting service's, as the operator's other file choices already are.
- **The command that mints a source's credential** — `source set <source> mint_command=<command>` and clearing it. The command line could be quoted whole, split on spaces without a shell, and weighed `code`; what approval would run is not those words but a program found by them — absolute or on the daemon's path — whose bytes the yard neither copies nor pins, run with the mint's inputs (secrets among them) on its standard input each time a token is minted. A declaration that brings its own mint command already has the stronger form: its program files are carried whole on the source or pack card that carries the declaration, installed as the yard's copies and held to their hashes. The operator's override to a program outside that carrying stays where the operator can name the program by its whole path and see it refused where it is not there.
- **Free `args` of a standing group or crew member, and free `args` on `crew add`.** The words could be quoted whole and weighed `code`, and the yard would still have no sentence for what they do: they are flags of a harness the yard did not write, whose meaning changes with its version, and the dangerous ones are dangerous precisely by not being in any table the yard holds. The yard's answer already exists and this design extends it not at all: a named preset of the kind, listed by `yardr harness show <kind>`, rides the add and set cards (a preset that skips permission prompts only on a card, never on a delegated run), a group's `effort` rides its set card, and a new group's single plain-text word already rides its add card because a run ask can carry one word without quoting. Widening any of these is a harness-table change — a new preset in `harnesses/<kind>.yaml` — not a card for unbounded words. Multi-word and JSON forms of `args` stay where they already are for the same reason: a run ask splits at spaces and quotes nothing, by design.
- **`env_file` of a group or crew member, and `env_command` of a crew member.** These are the credential pointers of section 4's second item for a session instead of a call, and they stay for the same reason, with one addition: an `env_command`'s output is a set of values no card can show (they are the session's secrets), produced by a program approval cannot pin, in an environment of the daemon's that the card cannot show either. What a session needs by value already has its doors — a source credential for a crew member on a secret ask, written into the file that stands — and what it needs is therefore not blocked away from the machine; the choice of a different file or command is the operator's at a terminal, or the hosting service's on a hosted yard.
- **The pack flags that shape more than one apply** — `--prune`, `--depot-roles` and `--pack-roles`, `--auth`, `--source-env`, `--source-base` and `--notify`, each on any pack row including the two new ones. `--prune` removes what an earlier import brought and the pack has dropped: the plan already names each dropped object as left where it stands, and a card that removed them would have to show what still points at them — beads standing in a dropped flow's stages, sessions of a dropped group, subscriptions to a dropped crew member — which the plan does not carry, and no one command takes the removal back. `--depot-roles` and `--pack-roles` choose whose role text wins and are recorded as the import's choice, repeated by the next import without being asked again; a card approving one apply would silently govern the next, and showing both texts whole for every shadowed group and crew member is the whole-card bound spent on a preference. `--auth` names a file whose header value is a secret the card cannot show. `--source-env` and `--notify`'s file half are the credential and address pointers above under pack spellings, and `--source-base` is where a credential is sent, marked `Alone` with them; a pack of kind source already answers its base on a setup card where one is chosen, and no pack card smuggles the three past that. Each stays in a terminal, and a run ask naming one refuses in words that name it.
- **A pack plan that still asks, a summary for a directory pack, and a pack at a general URL.** A plan that still asks after the mappings it was given needs a dialogue — which group takes a group, exposed to which peer, granted for which source the yard has no hook or credential for — and a card is one approval of one fixed command; the mappings already answer every question one word answers, and the rest refuse at the ask naming `yardr pack check`, as they do today. A directory pack past the whole-card bounds refuses for the same reason a general URL does: what would stand in for the rest is a hash over bytes the approver cannot open from the card in the yard's own reading, and the summary shape built for embedded depot packs (design yardr-y6gp) is bound to a reading from the binary the yard runs, replacing no standing source. Extending it is open question 1, not this proposal. A general URL adds that the yard would fetch from an address the asker chose before the operator approves anything.
- **Adding a device by token, and a standing pairing page.** `user device add` prints a bearer token that never runs out and that no store record, answer, note or event may hold; an approval's bead answer is kept in those places, so the token has nowhere lawful to be shown except a terminal that prints it once. (The pairing code is different precisely because it is spent in ten minutes on one device and rests nowhere: section 3.4 answers with it once, to the approver alone, in a transient return that is never that stored answer.) A page that stands ready showing a pairing — the withdrawn web pairing page — stays withdrawn: it would serve a code and a channel key the edge in front of it could rewrite before any approval, and the device would pin the edge's key. What section 3.4 builds instead is a QR code drawn after approval, by the app on a device already paired or in the approval's own response in the hosted web in its sitting — a response to an approval already given, at no standing route, holding the code in no URL and marked never to be stored — from an answer addressed to the approver; `yardr user device pair --qr` on the yard's own screen keeps its form beside it.
- **The `operator` setting and the settings of where the yard reads and serves from.** Changing who the yard takes as its operator could be shown whole — the name now and the name proposed, weighed `trust` — and is still not proposed: the setting names the default approver every other card is asked of and the person whose login and inbox the yard itself uses, a yard with no operator has no one to approve the card that would give it one, and on a hosted yard the operator is the hosting service's record. The bind addresses, the edge and its pinned key, `hosted`, `router_addr` and the web view's acting user and trust settings stay together for the further reason that a card cannot show their effect whole: whether a new address binds, what proxy or terminator stands in front of it, and whether secrets cross the link after `hosted` flips are facts outside the yard's records that the approval cannot be held to, and approving `hosted` from a device would widen the very channel that device's secrets cross. Their door away from the machine is the hosting service on a hosted yard and a terminal on the yard's own screen elsewhere, as docs/users.md already has it; `hook_public_url`, which binds nothing, keeps the card it already has, and a new setting keeps defaulting to `Alone` until a design marks it askable.
- **Reading a credential or an address back, and any card for a value.** No call reads one back today for any caller, and none is proposed: values move toward the yard typed unseen (a secret ask, `source key`, `user key`) and never away from it. A design that wanted the operator to inspect a standing credential from a phone would be a design about a new disclosure, not about these rows.

## 5. Open questions

Each question is the operator's to decide at the decide stage. Each gives its options, what each costs, and the one this document would take. The proposal above is written under the recommended answer to each; where the other answer is taken, the bead it changes says how it grows, and no other part of the proposal moves.

**1. Should a directory pack past the whole-card bounds ever ride a summary card?** Section 3.3 refuses it to a terminal, as yardr-vdh6 is shaped. Option A: keep the refusal. A directory's bytes live outside the binary and outside the yard's copies; the approver who cannot open a terminal also cannot open the directory, so the full text behind a summary would be reachable only as the ask carries it, and the card would approve a mutable place by its digest alone. Option B: extend the embedded summary shape (design yardr-y6gp) to a directory reading — the digest and each file's hash on the card, the carried texts behind it, replacing no standing source, under the carried bound. It costs a second reading surface for bytes that are neither the binary's nor yet the yard's, and approving on hashes for the one pack kind whose files the operator most likely edited by hand minutes earlier. This document would take A: `pack check <dir>` at a terminal, or shrinking the pack, is an honest road for the rare pack that passes 64 KiB of carried files, and the digest already tells the operator which pack a terminal applied.

**2. Should the repository-URL card ever widen to any pinned URL?** Section 3.3 takes the packs repository's origin alone. Option A: keep it. Provenance is the repository owner's branch plus the digest, and the yard fetches nothing for any other address before approval. Option B: take any https URL (plain http only on this machine, as the terminal does) where the asker names the digest from `pack check <url>`, fetched through the same hold-to-digest reading. It costs the yard a fetch of an asker-chosen address at ask time — before the operator has approved anything — and a card whose provenance is a hash the asker supplied, with no owner the yard names vouching for what the address serves next time. This document would take A: an operator who wants a pack from elsewhere puts it in a depot checkout, where the directory row reads it under yardr-vdh6's rule, and the bytes gain a place the yard already trusts.

**3. Should a hosted yard's first pairing for a user need the operator at all?** Section 3.4 lets the signed-in user approve their own first pairing in the hosted web, under the fresh sign-in every strong card there already takes, and otherwise asks the operator. Option A: keep both doors as proposed. The gateway has already proved who the visitor is as that yard user, and the operator of a hosted yard is often the same person at another screen. Option B: operator approval for every first device, the member's own approvals only from a device they already hold. It costs a hosted member with no device a wait for the operator for the one act that gives them a device, and buys a second person's eyes on an act whose whole effect — one more device of that user, named on the card with the devices they then have — the signed-in approval already shows. This document would take A, and notes that it builds no standing pairing page either way: the code remains an approval's one-time transient, never a page the edge serves before approval. (Under open question 5's second answer this hosted door falls, whichever way this question is answered; a sealed device's approval stands under either.)

**4. Should `--prune` get a card once its dropped objects can be shown with what points at them?** Section 4 keeps it in a terminal because the plan names the dropped objects and not their dependents. Option A: keep it there. Removal is the one pack effect with no take-back command, and the terminal that runs it shows the import's own output naming what was removed. Option B: a later bead first teaches the plan to carry, for each dropped object, the beads, sessions and subscriptions that name it, and only then proposes `--prune` over that whole showing, weighed as the objects weigh. It costs plan work no other row needs, for a flag an operator uses rarely and usually beside the pack edit that caused the drop, at the same terminal. This document would take A for this design's beads, and B only if pruning from a phone turns out to be a real errand rather than a tidy symmetry.

**5. Is the edge an accepted reader of a pairing code on the doors where it can read one?** Section 3.4's doors divide before this question begins. A sealed device's approval never gives the edge the code: the call and its sealed answer cross as ciphertext, and the edge is not handed that device's token either. A terminal and chat give it nothing. What remains is two readable doors — a device that pinned no channel key, calling with its token in the clear, and the hosted web, whose gateway answers the approval — where whoever carries the transient can read the code inside its ten minutes, spend it first and be paired as the named user, a device that then stands until `yardr user device rm` removes it, even if the approver's own device is removed first. The QR code's channel key protects the token after a sealed redemption of the new device; it does not keep the code itself from a carrier that delivered the approval in readable form. Option A: accept that reading on those two doors alone. The code is bounded by its own life (ten minutes, one device, five wrong tries, ended at will by `yardr user device pair --end`), the approving surface says before approval that its carrier could spend the code first, the opened and redeemed events record the pairing without the code, and a person who does not accept it for a given pairing approves at a terminal, on a direct connection, or from a sealed device — a plainly paired device can also register a channel key in place and call sealed from then on, though that one registration call is itself carried plain and an edge active at it could substitute a key (docs/api.md, A channel key registered in place), so re-pairing by QR code is the clean way to change doors. Option B: refuse pairing approvals on the readable doors — a plain device is refused this approval until it calls sealed or its person approves elsewhere, and no code is answered in the hosted web at all. It costs a plainly paired device the phone approval until it has pinned a key, and it closes question 3's hosted first-pairing door under either of that question's answers; the sealed device approval that is the ordinary case for a device paired from a QR code, and the terminal, stand either way. Option C: seal the transient to the approving device before it crosses, as a new step beyond the doors above. For a sealed device that sealing already exists — it is the device's channel, not new work — so C's real scope is the remainder: it cannot serve a plain device, which pins no key to seal to (serving it means first pinning one, which is B's road to the sealed door), and it cannot serve a browser in the hosted web, which has no yard channel key, so the hosted door still needs A or B under C. As a standalone answer C therefore buys nothing the sealed door does not already have, and is kept here only so the decider can see why it collapses. This document would take A, rescoped: no acceptance is asked for the sealed, terminal or chat doors, where there is nothing to accept; on the plain and hosted doors the exposure is one short-lived, single-use code crossing a carrier the approver can be told about before approving and can avoid by door, and B would refuse the hosted first pairing that question 3 exists to allow while pushing plain devices through a key registration whose own first call is the readable one. Under B the pairing bead in section 6 refuses plain-device approvals of this row and drops its hosted-web approval, and says so in its done-when, and question 3 is then answered by it for hosted yards; under C that bead does no sealing work for sealed devices, refuses or accepts the plain and hosted doors exactly as A or B says, and names that collapse in its done-when.
