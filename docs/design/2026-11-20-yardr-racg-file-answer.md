# Let a declared source call answer with a file in the caller's working directory

Design yardr-racg, proposed 2026-11-20. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

A *declared source* is an outside service the yard speaks to through one YAML file that names its address, its credential and the requests the yard may make of it, with no Go written for the service (`internal/source/declaration.go`, and docs/integrations.md, "A declared source"). One such request is a *call*, made with `yardr call <source> <call>`; a call is a *read*, which changes nothing in the service, or an *update*, which does. Who may make a call is a *grant*, given by the operator to a group (every session it starts) or to a crew member; a *preset* is a pack's named suggestion of grants. A *session* is one agent working one bead, in a worktree the yard made for the bead; a *crew member* is an always-on agent tied to no bead, working in a directory of its own. The *operator* is the person who runs the yard. A *blob* is a file the yard keeps under the SHA-256 of its bytes below its home, capped by the yard's `blob_max_bytes` setting. The *pack API* is the numbered contract between a yard and a pack built outside this repository (docs/pack-api.md).

## 1. The question

The bead asks: settle how `yardr call` hands an agent a file, so a Word or PDF document in SharePoint can be read; the declared-source format downloads no file's bytes (the team-server design, sections 2.7 and 3.5), Microsoft was the pack picked when the question was asked, and this is the gap that pack needs for contents. Large files and context safety are the design's reason: the google-mail `attachment` call already returns a small file's bytes inside its JSON answer, capped at about 750 KB, and names this bead for the rest, so a file answer must neither pass large bytes through an agent's context nor be refused at the JSON answer's bound. Uploads, sync and any write to the service are left out from the start.

## 2. What exists today

### 2.1 A declared call, and what its answer may be

A declaration (`Declaration` in `internal/source/declaration.go`) names a base address, a credential and its calls. A call (`Call` at `internal/source/declaration.go:241`) names its kind, its parameters, the request it sends — or a `build` command that prints the request's body, or a `run` command that answers the call instead of a request — and its answer. An answer (`Answer` at `internal/source/declaration.go:301`) holds exactly three things: `select`, the top-level keys or dotted paths kept of the service's JSON; `errors`, the paths kept of a refused answer; and `max`, the most the call returns after `select`, 64 KB by default (`AnswerMax` in `internal/source/call.go`) and never above 1 MiB. The reader enforces that list: under `answer` it admits `select`, `errors` and `max` and no other key (`internal/source/callread.go`, the `answer` case of `reader.call`). A parameter may be of type `file` or `secret-file`, but those carry bytes the other way, into a request, as one part of a multipart upload or as one leaf of a JSON body; nothing in a declaration says an answer is a file.

`Do` (`internal/source/call.go`) is the one place a request is made, and what it holds every call to is stated on it: the base's own host and no other, over HTTPS (plain HTTP only to this machine), no redirect followed, a 30-second bound (`Timeout`, a variable so a test need not wait it out), and an answer that is JSON within its bound; it writes nothing anywhere. The address a call goes to is built by `target`, which escapes each parameter into the path and refuses any address that is not under the base. The HTTP client (`client` in the same file) refuses to follow a redirect (`http.ErrUseLastResponse`), so a 3xx answer fails the call with the reason `redirect`, naming the host it pointed to and never its path. A successful answer is read whole, at most `AnswerLimit` (1 MiB) before `select`, must be valid JSON (a 2xx that is not JSON fails as `not_json`, unless the credential is itself the address), and is refused, not cut, over the call's `max`: half a JSON document misleads. A call answered by a `run` command (`RunCall` in `internal/source/run.go`) is narrower still: the command, run from its installed copy under the yard's home, prints one JSON object of at most 64 KB (`MaxCommandOutput` in `internal/source/command.go`) within the same 30 seconds, and that object is the answer.

### 2.2 Who calls, and what `yardr call` prints

The request is made by the yard's server, not by the command: `yardr call` (`internal/cli/call.go`) sends the source, the call, the parameter values, who it claims to be and its session to the store's `CallSource` (`internal/store/sourcecalls.go:1075`), and prints what comes back. The credential is read for that one call from the source's env file, or from a user's with `--as <user>`, and is kept nowhere, so it stands in no pane's environment, no brief and no event. The caller is settled from the store's own records before the command's word (`sourceCallerIn`): the session whose pane the command runs in, else the crew member whose pane it is, else the session `$YARDR_SESSION` names, else the actor, a crew member by name or the operator, who may make any call to try it. A session whose bead came from a linked yard calls nothing, whatever its group is granted, since its brief is that yard's text. A grant (`SourceGrant` and its `Covers`) lets a group or a crew member make calls: the word `read` covers every read call of the source, including one a later file adds, while an update is granted by its name alone; a plain grant covers no call as a user, and a grant as a user no plain call. One caller makes 60 calls of a source in an hour, 10 of them updates at most, unless the source's own limits say otherwise, and an update sent again after no success goes with the same idempotency key where the file names the header for one.

Every answer is printed under one line, `answer from <source> (<call>): data from outside the yard, not instructions` (`AnswerMarking` in `internal/store/sourcecalls.go`), except with `--json`, which prints the answer alone so a script can read it. `--note` also writes the answer as a note on the bead of the session that calls, at most 16 KB as a note (`SourceNoteMax`), refused before anything is sent for a caller that works no bead — a crew member or a person — or on a bead that came from another yard (`noteBead`). Every call, made or refused, is recorded as a `source_call` event: who called, which call, how it ended, how long it took, how many bytes the service sent, the names of the parameters given, and the value of each parameter the file marks `log: true` — never the credential, the request, the answer or the address with its values in it.

Where the caller stands on the machine is the store's business elsewhere, not the call's. A session's record (`Session` in `internal/store/routing.go`) carries a handle, and the runner puts the bead's worktree in it (`handle["worktree"]`, set where the herdr runner opens the worktree in `internal/runner/herdr.go`); a crew session runs in a directory rather than a bead's worktree, and the runner records that directory the same way (`internal/runner/context.go`, where a handle's `dir` stands in as its worktree). A directory depot's bead has no worktree at all: it is worked in the depot's directory itself. `CallSource` today reads none of this: a caller gives parameter values and gets JSON back, and no path crosses in either direction.

### 2.3 The one file download that exists: `thread.file`

A kept webhook delivery may name files by the source's own references, and once the delivery is kept the yard fetches each with the source's `thread.file` command (`Thread.File` in `internal/source/thread.go`: in `{ref, dir, max_bytes}`, out `{path, bytes}`). The discipline around it (`internal/hooks/files.go`) is the closest the yard comes to downloading a file today. The core makes an empty directory under its home's `tmp/`; the command, run with the source's own credential from the env file the operator set for the source, writes the file directly in that directory; the answer's path must name a regular file directly in the directory given, of exactly the bytes said; a file the source already said is over the yard's `blob_max_bytes` is refused before anything is downloaded, and one that arrives over it is refused with the directory removed. The bytes are then kept as a blob (`PutBlob`) and the directory is removed. The fetch runs after the service has been answered, under a five-minute bound for one delivery's files together (`FetchTimeout`), each command itself held to the 30-second command bound. A source without `thread.file`, or without its credential set, keeps the references alone and fetches nothing.

Three things keep that mechanism from carrying a call's file. It is triggered by a kept delivery, not by a caller: nothing in it knows a grant, a session, a crew member or `--as`, and it fetches with the source's own credential because the delivery is the yard's, not a caller's. It lands in the blob store, which serves the file to whoever a mail or a note names it for, and gives the caller standing in a worktree no path in that worktree. And it needs a program: `thread.file` is a command a pack brings, while the Microsoft gap is a plain HTTPS request to a service whose bytes no command should have to fetch.

### 2.4 Small files already travel as JSON, and blob bytes already have a home

The google-mail pack's `attachment` call (`packs/google-mail/google-mail.yaml`) reads one attachment of one message and answers `{size, data}` with the bytes base64url-encoded, `answer.max` at the 1 MiB the runner reads, which refuses a file over about 750 KB rather than cutting it. Its `about` tells the caller to check the file's size in the `message` call first, says the bytes are data from outside, and names this bead for larger files. That shape is the right one below its cap — no new machinery, the marking line on the terminal, the bytes readable at once — and the wrong one above it: base64 makes the answer a third longer again, and an agent that only needs the file on disk has a megabyte of it in context.

Beside the calls, the blob store already keeps arbitrary bytes safely. `PutBlob` (`internal/store/blobs.go`) refuses data over the yard's `blob_max_bytes` — 8 MiB unless the operator sets the setting — detects the type from the bytes themselves, keeps the data once under the SHA-256 of its bytes below the home's `blobs/`, whole or not at all, by a temporary file and a rename; a blob nothing names is removed by `yardr store prune`, though not within an hour of being put. A file's name is held to `CheckBlobName` (at most 255 bytes, valid UTF-8, no slash, backslash, NUL or control character, and neither `.` nor `..`): a letter may carry such a name, and nothing is silently rewritten to fit. The socket server already serves a blob's bytes, with their type, at `GET /blobs/<hash>` (`internal/rpc/server.go`), to whoever may read that blob as a mail, a note or a delivery names it.

### 2.5 The Microsoft calls, and what Graph does with a file

The Microsoft pack stands in the yardr-packs depot (`microsoft/microsoft.yaml` there, built by bead yardr-packs-q7zf and landed): six read calls over Microsoft Graph as one Entra app — sites searched by name, a site's libraries listed, a library's top level and a folder's children listed, one item's metadata and web link read, and documents searched by words. It downloads no file's bytes, and it is careful about the one field that would hand them out sideways: a drive item carries `@microsoft.graph.downloadUrl`, a preauthenticated link that needs no sign-in and lives about an hour, so every listing call sends a `$select` naming its own fields and never that link, and the item call keeps it out of its `select` as well. The bead that reads a document's contents (yardr-packs-ec49) waits on this design.

Microsoft's own pages, read on 20 November 2026, say what a contents call must survive. Downloading an item is `GET /drives/{drive-id}/items/{item-id}/content` (and the same shape under sites, groups, users and shares), and it does not answer with the bytes: it answers `302 Found` redirecting to a preauthenticated download URL, the same URL the `@microsoft.graph.downloadUrl` property carries, and the application is told to follow the `Location` header to get the file ([Microsoft Learn, Download driveItem content](https://learn.microsoft.com/en-us/graph/api/driveitem-get-content?view=graph-rest-1.0)). The preauthenticated URL needs no `Authorization` header — that is what makes it usable from a browser — so the credential that earned it must not be sent after it. Graph can also convert while downloading: `GET .../content?format=pdf` (also `jpg` and, for a few sources, `html`) answers with the same 302 to a converted file; conversion accepts a source file of at most 2 MB, PDF accepts among others `doc`, `docx`, `dotx`, `odt`, `rtf`, `xls`, `xlsx`, `ppt` and `pptx`, and its least privileged application permission is `Files.ReadWrite.All`, a wider permission than the `Files.Read.All` a plain download takes ([Microsoft Learn, Convert to other formats](https://learn.microsoft.com/en-us/graph/api/driveitem-get-content-format?view=graph-rest-1.0)). A partial download with a `Range` header is documented against the preauthenticated URL, not against `/content`.

### 2.6 Grants shown to a person, and the pack API

A grant is proposed to the operator whole. A run ask for one names each call with its method and path, says of `read` which calls that is today and that it covers read calls the source is later given, and says of an update call that it changes something in the service (docs/integrations.md, "A declared source"); a preset grant names the preset and the pack beside each grantee, and approving one grants each of its calls as if by name. `yardr source grants` prints a row for each call a holder is granted, `yardr call --list` prints each call a caller may make as the command that makes it, with an update marked `(update)`, and a pack's presets are printed by `yardr pack show` (`Preset` in `internal/pack/pack.go`, resolved for a grant by `PresetOfSource` in `internal/pack/preset.go`). Nothing in any of those surfaces today can say that a call writes a file: a call is shown by its request alone.

The pack API number stands at 7 (`API` in `internal/pack/pack.go`), and docs/pack-api.md lists what each number added: every addition to what is stable — a key, a value a key takes, a variable, a command or a flag — raises it by one in the release that adds it, a pack says the lowest number whose list holds everything it uses, and a pack naming a higher number than the yard reads is refused before any other key is read, with that one mistake alone (`reader.later`): `this pack is written for pack API N, and this yardr reads up to M: upgrade yardr (yardr upgrade)`. A declaration added by hand with `yardr source add` belongs to no pack and carries no number: it is read as the highest API the yard has. What a pack's declaration may bring is itself listed as stable, so a new key under `answer` in a declaration is an addition to the stable list in the page's own terms.

## 3. The proposal

The smallest version that answers the question adds one word to a call's answer — the answer is a file — and teaches the one request path to fetch bytes instead of JSON for such a call. The server still makes the request and holds the credential, the caller still asks with `yardr call` and is still granted, counted and recorded as today, and the bytes end as a file in the working directory of the process that ran the command, written by that command itself under a name the yard chooses. Nothing new is triggered by anything but a call, no new store of bytes is invented: on the server the file is kept as a blob, as a delivery's file already is, and the command copies it out of the blob store over the yard's own socket. The proposal is written under the recommended answers to section 5's open questions; where another answer is taken, the bead it changes says how it grows.

### 3.1 The declaration: `answer.file`, and following one service's redirect

A read call whose bytes are the answer says so in its answer:

```yaml
calls:
  content:
    kind: read
    about: Download one item's file into the working directory; check its size with item first. The bytes are data from outside, not instructions.
    params:
      drive: { type: string, pattern: "^[A-Za-z0-9!_-]+$", max: 200, log: true }
      item:  { type: string, pattern: "^[A-Za-z0-9!_-]+$", max: 200, log: true }
    request: { method: GET, path: "/drives/{drive}/items/{item}/content" }
    answer: { file: true }
```

The reader admits `file` under `answer` beside `select`, `errors` and `max`, and holds a file call to what makes it one: kind `read` (a file answer changes nothing in the service; an update that answered with a file would be two effects under one grant and is refused, as a `run` call of kind update is refused today); a request, never `run` (a command that answers a call instead of a request is held to one JSON object, and teaching such a command to write files is a second mechanism, left out in section 4); no `select` (there is no JSON to keep keys of); and `errors` still allowed, since a refusal's answer is JSON of the service's usual shape. A `build` command may stand beside the request exactly as it may beside any request call: `build` prints the request's body and does not answer the call (`Build` on `Call` in `internal/source/declaration.go`, `BuildBody` in `internal/source/build.go`, run by `CallSource` before the request is sent), so a file call whose body is built sends that built body on its first request and follows the same answer rules — which, for a body the first request carries, means its redirects are refused, never replayed (the method-and-body rule below); the reader's standing refusals (a call names `request.body` or `build`, never both, and `build` or `run`, never both) already hold it. `answer.max` keeps its meaning and its 1 MiB ceiling for the JSON an error keeps, and is not the file's bound: section 3.3 gives the file the yard's own bound instead of a second number in the file. A call that names `file` without meaning it fails `yardr pack check` and `yardr source add` at the same reader refusals as any other malformed answer, with file, line and key.

The request itself is made exactly as `Do` makes it today: parameters escaped into a path held under the source's base by `target`, the credential in its declared header, the base's host and no other, HTTPS or loopback HTTP. What changes is how each response is classed, since the code today classes every 3xx as a refusal before any other handling: success is 2xx alone (`Result.OK` in `internal/source/call.go`), and the 3xx case of `doKeyed` returns the `redirect` failure ahead of its non-success and success handling in that same file. A JSON call keeps today's rule whole: every 3xx fails the call, whether or not it carries a `Location`. A file call classes each response it receives, first and redirected alike, in exactly this order:

1. A 2xx response is the final answer: its body is the file's bytes, and the `not_json` refusal does not apply to it. A service that answers 200 and a file with no redirect is accepted this way.
2. A 3xx response with a usable `Location` — one that parses, names a host, and passes the hop rules below, the method-and-body rule among them — is an intermediate response, neither a success nor a refusal: the yard follows it by hand under those rules and classes the next response the same way. Graph's `302 Found` from `/content` (section 2.5) is this case, and it is the only way the bytes behind it are ever reached. `answer.errors` is not applied to an intermediate response and its body, if any, is not kept.
3. Any other response is a terminal refusal, handled as a JSON call's non-success is handled today: a 3xx with no usable `Location` fails the call as `redirect`, as a JSON call's first redirect does today; a 3xx whose following the method-and-body rule forbids — any 3xx answered to a first request that carried a body or used a method other than GET, a 307 or 308 among them — fails the call as `redirect` on the same terms, with no second request made; and any other non-success (a 4xx or 5xx, from the base or from a download host alike) keeps at most the call's `answer.errors` where the call names them, within the same bounds a refusal's JSON is kept under today, and is no success whatever its body says.

A file call follows its intermediate responses under five further rules that mirror why the credential travels no further today than the base:

1. At most five redirects are followed, each by a fresh bodyless GET to its `Location` under rule 2; a sixth fails the call as `redirect`.
2. The credential is sent on the first request and never again: no redirected request carries the credential's header or any header the first request carried for the yard, on any hop, even back to the base's own host. A preauthenticated URL needs no credential, and a same-host redirect that demands one again fails rather than being handed it. The first request's body goes no further either, and this is a rule of its own, since neither the no-credential rule nor the public-address rule of rule 4 covers it: a body is built three ways in `doKeyed` (`internal/source/call.go`) — a `build` command's printed JSON sent unchanged, a `request.body` template filled as JSON (a leaf that is exactly a secret-file parameter becoming that file's secret in `fill`, in the same file), or that template sent as a multipart upload where it names a file parameter (`hasFileParam` and `multipart`, in the same file) — and a client that reuses the first request, or that obeys a 307 or 308 by preserving method and body, would carry any of those, secret and file bytes included, to a host the service chose. A redirect is therefore followed only where the first request was a bodyless GET: the request the yard makes to a `Location` is always a fresh GET with no body, no `Content-Type`, no `Content-Length` and no other entity header, in place of whatever the first request was, and where the first request carried any body — built, templated or multipart, however small — or used any method other than GET (a read call may be GET or POST, `internal/source/callread.go`), no redirect from it is followed at all: the 3xx is the terminal refusal of case 3 above and no second request is made, so no byte of the body leaves the first host. There is no exception for 307 or 308: preserving the method and the body is exactly what those codes mean, so answering a body-bearing request with one fails the call rather than being obeyed, and a service that wants its file behind a redirect asks for it with a bodyless GET, as Graph does. Every hop after the first is that same bodyless GET again, so a chain of redirects from a bodyless GET is followed hop by hop under the same rules, and a chain from a body-bearing request never starts. A body-bearing file call that answers 2xx without redirecting is untouched by this rule and succeeds as any file call does; only its redirects refuse.
3. Every hop is held to what a base is held to, and to the destination policy of rule 4: HTTPS, or plain HTTP only to this machine; a redirect down from HTTPS, or to a name with userinfo, fails the call as `redirect`.
4. A redirected request may be dialled only to a public address, checked where the connection is made. Today's checks do not give this: `checkAddress` (`internal/source/declaration.go`) judges the address as written — HTTPS to any host named, plain HTTP only to a loopback name or address (`LoopbackHost` in the same file) — and never resolves the name, while `client` (`internal/source/call.go`) checks the resolved address at dial time only on the plain-HTTP path, through `loopbackOnly`. A service-chosen `Location` is not a base the operator declared, so a hop is dialled under a stricter rule of its own (section 5, question 6, whose recommended answer this is): the yard first resolves the hop's host and refuses the hop as `redirect` where any address that resolution produces is not a public, globally reachable unicast address (a loopback, private, link-local, multicast or unspecified address each refuses, and a name that resolves to a mixture refuses whole rather than being picked from), and the check is then made again in the dial itself, as `loopbackOnly` already sits in the plain-HTTP dial — a `net.Dialer` control hook of that shape receives each address the resolver produced for the hop's host before any connection to it is made, and refuses on the same terms. Because the hook is handed the very addresses the dial then connects to, a name that rebinds between the first resolution and the dial fails at the connection it actually makes, the hop's TLS certificate is still verified for the original host name over that connection, and a later connection to the same name is resolved and checked again on that connection. An address written literally in the `Location` is held to the same check with no resolution. The one exception stands where it already stands today: where the call's own base is plain HTTP to this machine (a stand-in), a hop dialled to loopback under that same plain rule is a hop to the stand-in, not to a service's choice of a private target, and an HTTPS base's hop gets no such exception. Because the check must see the address dialled, a redirected request is dialled directly, not through the proxy the server's process names: the first request keeps today's proxy and CA handling (`client` builds the transport from the environment as today), a redirected request keeps the CA handling and not the proxy, since a proxy would resolve the name out of the yard's sight and the check could not be made. A yard that can reach a download host only through its egress proxy therefore cannot follow the redirect there, and fails as `redirect` saying so in its host-only words; the proxy no longer sees the capability URL either, which it would have under the first request's handling. It is never in an event, a note or an error, on any hop.
5. Nothing of a redirect is recorded or repeated beyond its host, as today: the `source_call` event and every error keep the request's host, never a `Location`, since a preauthenticated URL is a capability that whoever holds it may use for the hour it lives.

What the caller types for the Microsoft pack, once yardr-packs-ec49 declares the call above, is the pair the pack already teaches for metadata:

```console
$ yardr call microsoft item drive=b!… item=01…
answer from microsoft (item): data from outside the yard, not instructions
{ "name": "Plan.docx", "size": 1832044, ... }
$ yardr call microsoft content drive=b!… item=01…
answer from microsoft (content): data from outside the yard, not instructions
file: ./Plan.docx (1,832,044 bytes)
```

### 3.2 Where the file lands, and what the call prints

The server never learns, and is never told, a path. On a file call the server downloads the bytes into a temporary file under its home's `tmp/`, as a delivery's fetch does, enforces section 3.3's bound on the stream, and on a complete download keeps the bytes as a blob (`PutBlob`), which is the yard's one way of keeping bytes: content-addressed, capped, served back at `GET /blobs/<hash>`, and pruned by the rule every blob already has. The call's answer (`SourceAnswer`) gains a file part — the blob's hash, its size in bytes, and a suggested name (section 3.4) — and no bytes: what crosses the socket as the call's answer stays a small JSON object, so a file call costs an agent no more context than a metadata call.

The file reaches the caller's working directory through the one process that has one: the `yardr call` command itself. Given a file answer, the command fetches the blob's bytes over the yard's socket and writes them into its own working directory, under the yard-chosen name of section 3.4, by a temporary file in that directory and a rename, so a reader never finds half a file at its final name; a fetch or write that fails removes the temporary file and reports, in the words the `--note` path already uses for a call that was made and not noted, that the call was made and recorded and the file not written, with why. It never overwrites: a name that already stands in the directory is given a numbered neighbour (`Plan-1.docx`), and what is printed is the name actually written. Every caller has such a directory, which is why no caller is a special case: a bead's session runs in its worktree, a crew member in the directory its pane stands in, an exec group's script in the depot, the operator at a terminal wherever they stand, and a session of a directory depot in the depot's directory, where its bead is worked in place anyway. A caller that may not call at all — a session whose bead came from a linked yard — is refused before anything is sent, as every call of its is today, so no file is ever fetched for it.

The socket already serves those bytes — the server's mux answers `GET /blobs/<hash>` (`a.blob` in `internal/rpc/server.go`, beside the route table in `handler` in the same file) with the blob's type and bytes to a holder of the socket — but nothing on the client side reads them: `rpc.Client` (`internal/rpc/client.go`) holds its socket HTTP client privately, its generated half (`internal/rpc/client_gen.go`, rewritten from `internal/store/api.go` and never edited by hand) carries the API's blob-metadata calls (`NoteBlob`, `MailBlob`, `DeliveryBlob`) and `PutBlob` and no byte-reading call, and its hand-written half offers only `Ping`, `Owner` and the event streams beside them. The command holds a `store.API` (set by `a.store` in `internal/cli/root.go`), not a socket path, so it cannot make that GET itself. The fetch therefore needs one small hand-written helper on `rpc.Client` in `internal/rpc/client.go` — not in the generated file, and not a new method on `store.API`, since no other implementer of that interface keeps blobs behind a socket: `BlobBytes(ctx, hash)` makes the `GET /blobs/<hash>` request over the client's own transport, returns the bytes and the content type the server set, and answers any non-200 (an unknown or malformed hash among them) as an error saying no more than the status, as `Ping` and `Owner` in the same file already speak for the raw routes beside the generated calls. The command reaches it by asserting the client it already holds to that one method, the shape `internal/cli/root.go` already uses to set the client's session; a store held directly, as in a test, reads the same blob through the store's own record and path, so the command's write is tested whole without a socket and the helper is tested over one. The bytes are checked against the answer's recorded size before anything is written: a short or long fetch is the failed fetch above, and leaves no file.

What the call prints, in each of the shapes `yardr call` already has:

- At a terminal, the marking line first, as for every answer, then one line: `file: ./Plan.docx (1,832,044 bytes)`. The marking is the only claim made about the bytes, and it stands in front of the path an agent will open.
- With `--json`, the answer alone, as today, now an object naming the file and nothing of its bytes: `{"file":{"name":"Plan.docx","bytes":1832044}}` — a script learns where the file is without the yard putting bytes in its output, and the marking line's absence is the known one of every `--json` answer, answered in the pack's `about` and the service's docs as the google-mail attachment already answers it.
- With `--note`, the note on the caller's bead carries the marking line and the file line, and no bytes; the blob on the server is the durable copy, named by its hash in the answer the socket returned, and attaching the blob to the note as a file is left out (section 4).
- A failure — refused, over the bound, timed out on the download, a redirect that breaks the rules — prints and records exactly what a failed JSON call does, with the same reasons plus the download's own (section 3.3), and leaves no file in the working directory and no blob on the server.

The file in the working directory is then an ordinary file of that directory's life: in a git depot's worktree it is an untracked file, which the bead's `done` already names and refuses over until the agent moves, reads or removes it — the agent that fetched a document to read it deletes or notes it as it would any scratch file, and the design adds no hiding place inside the worktree to spare it that. Its mode is 0600, as a blob's file is, never executable: the yard writes data, and nothing in the yard ever opens, runs or renders it.

### 3.3 Bounds: the yard's file bound, a download's own clock, and no partial files

The file's size bound is the yard's `blob_max_bytes`, 8 MiB unless the operator sets it, not a number in the declaration. The reasons are the ones that bound a delivery's file the same way: the operator, not the pack author, decides what one file may cost this yard's disk, and one bound already guards the blob store the file is kept in, the mail a file rides on and the fetch of section 2.3 — a declaration that named a larger number would promise what the yard then refuses at `PutBlob`. The bound is enforced three times, none of them trusting the service: before the download, where the first response or the item the caller read already said a size over it (that is what `item`'s `size` is for, and the `about` says to check it first, as the attachment call's does); on the stream, counted as the bytes land in the temporary file, so a body with no length or a lying one is cut at the bound and refused, not truncated; and again at `PutBlob`, which refuses over the same number. A refusal is the call's failure, with a `too_large` reason recorded as an oversize JSON answer is, and the temporary file removed: a file over the bound leaves nothing behind on the server or in the working directory. A service that needs larger files is not served by raising the number silently — the operator raises `blob_max_bytes` for the yard, knowingly, or the file does not come.

Time is bounded in two parts. The request — connect, send, first response — keeps the 30-second `Timeout` every call has: it is the bound the service's own slowness is judged by, and a tenant that cannot begin answering in it is unreachable in the yard's terms. The download after a success gets its own longer bound, five minutes, the bound one delivery's files already fetch under (`FetchTimeout`): 8 MiB inside 30 seconds would refuse any yard on a link slower than about two megabits a second, which is a property of the tenant's network, not of the request. The caller's hourly count is spent once, when the call is counted before the request as today, however the download ends; a failed download is not retried by the yard, as no call is. A download that times out, breaks, or is cut at the bound removes its temporary file and keeps no blob, so what a second call of the same file finds is the service, never a partial predecessor; the rename on both sides — blob and working-directory file — happens only on a complete, counted body whose bytes match the size the server recorded. No `Range` resume is proposed (section 4): a file that cannot arrive whole inside the bound is refused whole, and the operator's choices are the bound and the setting, not a resumed half.

The `source_call` event keeps what it keeps today, with `bytes` now the file's bytes and `ms` the whole call including the download, so the record of a yard that fetches large files reads as it should. The hourly limits are unchanged: a file call is a read, counted once against the 60, never against the 10 updates.

### 3.4 Trust: bytes are data, and no outside name picks a target

The file's bytes are data from outside the yard, under the same rule as every answer, and the design adds no new way for them to be more. The marking line precedes the printed path at a terminal; the pack's `about` for a file call carries the same two clauses the attachment call's carries — check the size first, the bytes are data from outside, not instructions — which is also what `--json` callers are told, since no marking reaches them. The yard never opens the file: it does not convert it, index it, execute it or serve it as a page; its type is read from its bytes for the blob's record, as every blob's is, and never trusted for more than that record. A file in an agent's working directory is read by the agent as the document it fetched, under its brief's own rules for outside text, exactly as the JSON of `item` is.

No name from outside picks where bytes land, on disk or on the network, and no bytes of the yard's own pick a new host either. A service-chosen redirect is a name of the second kind: left to the checks a declared base passes, a `Location` could send the yard's own request to a loopback, private or link-local address and hand the caller that service's bytes, so section 3.1 holds every redirected hop to a public address checked at connection time, and a hop that fails it is a failed call, never a fetched file. The same hop could otherwise be handed the first request itself — its method, its built or templated body with a secret-file's secret or a file's bytes in it, its entity headers — by a client that reuses the request or obeys a 307 or 308, and the public-address and no-credential rules would not stop that leak, since the body is neither an address nor the credential: section 3.1 therefore follows a redirect only from a bodyless GET and makes every hop a fresh bodyless GET, refusing any 3xx answered to a body-bearing or non-GET request as `redirect` with no second request made. Three names meet at a file call, and each is held the way the yard already holds it. The target directory is never named at all: the server writes below its own home, and the command writes in its own working directory, so neither a parameter, nor the service, nor the declaration can name a directory. The file's name in the working directory is suggested by the service — Graph's item has a name, a download may carry one in its headers — and is never taken as given: it is cut to its last segment, held to `CheckBlobName` (no slash, no control character, neither `.` nor `..`, at most 255 bytes), and where it fails, or names nothing, the yard's own name stands instead, `<source>-<call>` with the extension the bytes' type suggests, so `../../Plan.docx` from a hostile or careless service becomes `Plan.docx` in the working directory and nothing outside it. The blob's name on the server is its hash, as always, so the service cannot choose that either. The declaration itself names only the request's path, held under the base by the checks of section 2.1, and a parameter that tried to carry a path into the request is escaped into one segment or refused, as today.

The one trust decision a file call adds is that granting it lets bytes land on the disk of whoever calls. A grant's surfaces therefore say so, at the same places they already distinguish an update: `yardr call --list` and a callable's line mark a file call `(file)` beside `(update)`; a run ask that proposes the grant names the call with its method and path and adds that the call writes a file into the caller's working directory; a preset that grants one names the call by its name, so its `about` can say what it fetches; and `yardr source grants` prints it as its own row, as every granted call is printed. Section 5 asks whether `read` should cover a file call as it covers every read; the proposal takes the update's answer — a file call is granted by its name alone, so an existing grant of `read` does not silently widen to writing files the day a declaration grows one, and `yardr source add` says, of a new or changed file call, who is not granted it until the operator grants it, as it says of an update. A call made as a user (`--as`) downloads with that user's credential on the first request and no other: the redirect discipline of section 3.1 does not change with whose credential opened it.

### 3.5 Text: conversion is the pack's declaration or the agent's work, never the yard's

Turning a document into text is not the yard's part, for the reason the yard converts nothing today: it keeps bytes as blobs without reading them into meaning, and a `.docx` is a zip of XML whose text extraction is one tool among the many an agent in a pane already has. The file lands in the agent's working directory precisely so the agent's own tools — the harness's file reading, a converter the depot carries, a script of the pack's — can do with it what the bead asks, and a design that put one converter in the core would choose for every service and every format at once.

What a pack may do without any new yard machinery is declare conversion as a second file call. Graph's conversion is a query parameter on the same `/content` request, so the declaration already expresses it:

```yaml
  content-pdf:
    kind: read
    about: Download one item converted to PDF by the service, into the working directory; the source file must be at most 2 MB for the service to convert it.
    params:
      drive: { type: string, pattern: "^[A-Za-z0-9!_-]+$", max: 200, log: true }
      item:  { type: string, pattern: "^[A-Za-z0-9!_-]+$", max: 200, log: true }
    request:
      method: GET
      path: "/drives/{drive}/items/{item}/content"
      query: { format: pdf }
    answer: { file: true }
```

The pack, not the yard, then owns the costs Graph names: conversion takes the wider application permission (`Files.ReadWrite.All` where a plain download takes `Files.Read.All`), refuses a source over 2 MB, and answers a PDF, which an agent reads as a PDF or not at all. A pack whose service extracts text server-side into JSON needs no file call at all, as Confluence's pages already answer as JSON within the format as it stands. The Microsoft pack's first contents call is the plain download; whether it also declares the conversion is the pack bead's choice with its tenant's permission in front of it (section 6), not this design's.

### 3.6 The pack API number, and what an older yard says

`answer.file` is a new key in a declaration, a new mark in a callable's line and a new field in the `yardr call --json` answer: each is an addition to what docs/pack-api.md marks stable, so the number rises by one where it lands, to 8, with an API 8 entry naming the key, the mark and the fields, and `pack.API` in `internal/pack/pack.go` becomes 8 in the same commit. A pack that declares a file call says `api: 8`, the lowest number whose list holds it.

An older yard's answers are the ones the number exists to give. Given the pack whole, saying `api: 8`, a yard that reads up to 7 refuses it before any other key is read, with the single line `reader.later` already prints — this pack is written for pack API 8, and this yardr reads up to 7: upgrade yardr — and never reaches the new key to call it unknown. Given the same pack with the number forgotten, the older yard reaches the declaration and refuses the `file` key under `answer` at its reader, with file, line and key, as it refuses any key it does not know: safe, if less kind, and the new yard's check does not need to enforce the pairing, since `pack check` on the new yard reads the call whole either way. A declaration added by hand belongs to no pack and carries no number, so `yardr source add` of a file call on a new yard simply works, and on an old yard fails at the same reader refusal. Nothing is taken away: a yard that reads 8 reads every pack of 1 to 7 as today, a declaration without a file call parses to the same calls, and a JSON call's refusal of every redirect stands untouched beside the file call's following of one.

The socket's answer grows the same way, additively: `SourceAnswer` gains its file part beside `answer`, the generated client is rewritten from `internal/store/api.go` as always, and docs/api.md's golden moves by its test, never by hand.

## 4. Left out

What follows was considered and is not proposed. Each names what stands instead.

- **Uploads, sync, and any write to the service.** The bead leaves them out, and the design adds none: a file call is a read, granted and counted as one, and a call that wrote a file to SharePoint would be an update with its own grant, idempotency and card questions, none of which this answers. A declaration's `file` parameter already uploads a file as a request's body where a service takes one; that is a JSON call's shape and is unchanged.
- **Reusing `thread.file` as the call mechanism.** Its trigger is a kept delivery and its credential the source's own, so carrying calls on it would either fetch every call's file outside the caller's grant and `--as`, or grow a second caller path inside a hook mechanism. Its disciplines are reused — a yard-made directory, a bound enforced on what arrives, nothing partial kept — its command is not: a service with no program, Graph among them, gets its file from its own HTTPS answer.
- **The server writing into a caller-named or worktree directory.** The server is told no path, ever: a session's worktree is not its pane's working directory in every runner, a crew member has no worktree, and a server that wrote where a caller pointed would let any granted agent choose a target on the yard's disk. The command writes in its own working directory instead, which is the directory every caller actually stands in.
- **Bytes in the JSON answer, larger.** The attachment call's shape, raised: base64 in JSON is a third longer, is refused at the runner's 1 MiB read whatever `max` says, and puts the bytes in the caller's context to be carried, which is the cost this design exists to remove. Below about 750 KB the attachment shape stands as it is, and the pack's `about` already steers a caller between the two by size.
- **A `run` command answering with a file.** A `run` command's answer is one JSON object, and the pack that needs bytes from outside HTTPS is not a declared source's call at all. Letting a pack's program write the file would run pack code on the server for what the request path now does with none, under a new output contract of its own. A `build` command is not left out and needs nothing new: it prints a request's body, the request path sends that body as it sends any built body today, and the answer that comes back is the file, so a file call may name `build` beside its request as any request call may (section 3.1) — with the one consequence the method-and-body rule states there: that body's redirects are refused, never replayed to a service-chosen host.
- **Resuming a download, ranges, and several files in one call.** Graph documents ranges against the preauthenticated URL, and a resumed download is a real saving on a slow tenant; it is also state — a partial file kept, matched to a later call, expired — where the design now keeps none. One call downloads one file whole or refuses it, and a caller that needs ten files makes ten calls, counted as ten.
- **Yard-side conversion or text extraction.** No converter enters the core (section 3.5): no `.docx` reader, no PDF text layer, no format table. The pack may declare the service's own conversion, and the agent extracts text with its depot's tools.
- **Attaching the file to a `--note` note as a note file.** A note can carry blobs, and the blob is on the server; the first version's note names the file and its hash, and whoever works the bead next fetches the document with the same call the first caller made, under their own grant. Attaching it would make the note a second distribution of the bytes, past the grant that fetched them.
- **A file answer for an update call, and paging a file.** An update is granted by name for what it changes in the service; letting it also write the caller's disk joins two side effects under one name. A file has no pages in this design: the bound refuses, and the service's own listing calls, which page as JSON today, remain how a caller walks to the item it wants.

## 5. Open questions

The proposal above is written under the recommended answer to each question below. Each gives its options, what each costs, and the one this document would take; no other part of the proposal moves where another answer is taken, except as the question itself says.

**1. Where the file lands: written by the command in its working directory, kept only as a blob with its path printed, or written by the server into the session's worktree?** Option A, the proposal: the server keeps a blob and the `yardr call` command fetches it over the socket and writes it in its own working directory under a yard-chosen name. It satisfies the bead's words — the caller's working directory — for every caller including a crew member, the server is told no path, and both lifetimes already exist: the blob under the prune, the written file as any file of the caller's. Its cost is the command's fetch and write, and an untracked file in a worktree that `done` then names. Option B: no working-directory file at all; the call prints the blob's path below the yard's home and the agent reads it there. It is the smaller change — nothing in the command — and it fails the bead as titled, couples every agent to the home's layout, and gives a caller no file of its own to keep past the prune. Option C: the server writes into the calling session's worktree, refusing a caller with none. It puts the file where a git bead works and can be committed with it, which a fetched document should not be by default; it refuses the yardmaster and every crew member, the callers likeliest to fetch a document for a person; and it teaches the server to write in a tree the bead's own session may be editing. This document would take A.

**2. Is a file call covered by a grant of `read`, or granted by its name alone?** Option A, the proposal: by name alone, as an update is. A file call's side effect is on the yard's side — bytes on the caller's disk — and `read` is granted once and covers read calls a declaration is later given, so covering file calls would widen every standing grant the day the Microsoft declaration grows one, with no operator decision in between. Its cost is one more name for an operator to grant, and a preset that must list the call. Option B: `read` covers it, as it covers every read. It is the consistent reading of kind `read`, and a preset of `read` then fetches documents the day it lands; nothing on a grant card written before the call existed said a file would be written, and the card is where such a thing must be said. This document would take A, and notes the same question was answered for updates on exactly these grounds: what changes something is named.

**3. What bounds a file: the yard's `blob_max_bytes`, a size in the declaration, or a new setting?** Option A, the proposal: `blob_max_bytes`, the yard's one bound for a file it keeps, enforced on the stream as on a delivery's fetch. The operator already sets it knowing it prices mail, blobs and fetches at once. Option B: `answer.file_max` in the declaration, capped by the yard. It lets a pack author say a document is expected large, and gives the yard two numbers to reconcile at every refusal, with the pack's promise failing where the operator set the smaller. Option C: a new `file_max_bytes` setting beside the old one. It prices downloads apart from mail, at the cost of a second knob an operator must learn and a test must hold. This document would take A: one bound, already understood, already the blob's.

**4. How long may a download take: the 30 seconds every call has, or a longer bound of its own?** Option A, the proposal: 30 seconds to the first response, five minutes for the download, the bound a delivery's files fetch under. At the bound's largest file that is a slow tenant answered rather than refused for its network. Option B: the one 30-second bound for the whole call, as every command and request is held today. It is the simpler rule and the one a test waits out least, and it refuses the largest files on any link under about two megabits a second, which is common on the networks a team server is reached over. This document would take A, with the five minutes named as one constant beside `Timeout`, not a setting: no operator has a reason to tune it apart from the bound it serves.

**5. Does the Microsoft pack declare Graph's conversion (`?format=pdf`) beside the plain download?** The operator's to settle with whoever grants the tenant's app permissions, and asked here because the design makes it free to declare. Option A: the pack's first contents bead declares the plain download alone, and conversion is a later call if a tenant's documents need it. Option B: both calls at once. It costs the tenant the wider application permission for the conversion call — `Files.ReadWrite.All` where the download takes `Files.Read.All` — before anyone has read a document, and converts only sources under 2 MB in any case. This document would take A for the pack's first bead, and leaves the call shape ready in section 3.5 either way. It is no part of the core either way: the core learns no format.

**6. Where may a service-chosen redirect send the yard: to any HTTPS host, to declared download hosts, or to public addresses only, checked at connection time?** A file call must follow a host the declaration never named — Graph's preauthenticated download URL — and the checks a base passes give no protection there: `checkAddress` judges a name as written and never resolves it, and the only dial-time address check today (`loopbackOnly`, on the plain-HTTP path) guards the opposite direction. Option A, the proposal: public addresses only, checked where the connection is made — the yard resolves the hop's host and refuses any resolved address that is loopback, private, link-local, multicast or unspecified (a mixed answer refuses whole), then checks the addresses the dial actually connects to in the dial's own control hook, with the certificate verified for the original name, re-checked on every hop and every new connection (section 3.1, rule 4 of the hop rules). It permits Graph's download hosts, which are public addresses, and refuses a service that would send the yard at a metadata address, a home router or its own machine, whether it names that address or a name that resolves to it, and a rebinding name gains nothing between check and dial. Its costs are two: a redirected request is dialled directly, so a yard that reaches download hosts only through its egress proxy fails those calls as `redirect` rather than fetching through the proxy (the first request keeps the proxy; a proxy would resolve the hop's name out of sight of the check), and a service whose files genuinely live at a private address — an intranet file host — cannot be fetched until a later design declares such hosts on purpose. Option B: an allowlist of download hosts, in the declaration or as yard settings, dialled under the same connection-time check within the list. It is tighter still and reaches a named intranet host, at the cost of a new declaration key (and a further pack API question) holding host patterns that Graph's tenants spread across hosts no pack author can enumerate once — the preauthenticated host follows the tenant's own SharePoint host — so the list would be written per tenant, by the operator, for a risk option A already closes. Option C: any HTTPS host, as the first version of this design had it. It is the smallest rule and the one a proxied yard reaches furthest under, and it lets any granted source's service — or anything that can make it answer a redirect — turn the yard into a client of the yard's own network, with the answer handed to the caller as a file: the server-side request forgery this design may not ship. This document would take A, and names B as the later shape if a tenant's files ever live at a private address: declared then, by the operator, never widened by a service's answer.
