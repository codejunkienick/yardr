# See and edit a depot's line in footplate: its stages, what serves each, and the agents' prompts

Design yardr-y1cn, proposed 2026-11-16. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

A *line* is what a bead travels in a depot: its flow's stages, the groups the routes put at them, and the agents and people bound to those groups (docs/glossary.md). A *flow* is the stages a bead of some type goes through and the moves allowed between them; a *stage* is one step of it. A *group* is who works a stage, and its *runner* is how that work starts: `herdr` (an agent), `exec` (a command), `manual` (people) or `peer` (another yard). A *role prompt* is the text that says how a group works in any stage; a *stage file* is the text that says what one stage is for and what must hold before a bead leaves it (docs/groups.md, Role file or stage file). A *card* is an ask a person answers by approving: a run ask holds one yardr command of the store's fixed list, the yard writes the card from its own records showing the change whole, and approval runs exactly that command once (docs/chat.md, Questions for you). A card is *weighty* where approving it widens what runs inside the yard, and *strong* where its weight is `code` or `trust`. A *device* is one program of a user that calls the yard from outside it, let in by a token; footplate on another machine is one, and a device that pinned the yard's channel key from a pairing QR code calls *sealed*, as ciphertext the edge cannot read. The *operator* is the user the yard takes as its operator. *footplate* is the yard's desktop app, an interface over yardr's socket API. *brakeman* is the yard's crew member that reviews what changes what runs, before it runs.

## 1. The question

The ask is a way, in footplate, to edit a line: to edit its stages, to view and adjust the prompts for its agents, and to add and remove stages and choose what serves each — an agent, a script, or a person. Read plainly, that is three asks in one window, per depot: see the flow's stages in order with what serves each and whether that is an agent, a script or a person; read and change the prompt each agent gets; and add, remove and reorder stages, choosing what serves each. The window is footplate's, on the desktop: footplate on a phone (footplate-ios, footplate-android) is out of the first version, and no phone layout is sketched (section 4). This design decides where that window stands, which door each edit takes on the yard's own machine and over the edge from another machine, where each edit lands, what a wrong edit costs and how it is undone, and what the first version leaves out. It builds nothing: each slice below is a bead in section 6, and none of them leaves backlog until brakeman has read this design, because it changes what runs.

## 2. What exists today

### 2.1 The line as data

A depot is one of two kinds, and which kind it is decides where an edit can land before where the flow stands is even asked (docs/configuration.md, Depot kinds: git and dir). A *git depot* is a repository: beads work on branches in worktrees and land on its base. A *dir depot* is a plain directory: there is no repository, no branch and no base, beads are worked in the directory itself, and nothing reviews a change to its `.yardr/` before it applies (docs/dir-depots.md). Depot yardr and depot footplate are git depots; a folder of documents or invoices is the dir kind's worked example.

A depot's flow then comes from one of three places (docs/configuration.md, What lives where; docs/flows.md, Repo flows and Named flows and pointers). A git depot may keep its flows in its repository under `.yardr/flows/` (`default.flow`, `type/<type>.flow`, `<name>.flow`, with one stage file per stage beside each), read from the tip of the depot's base branch and never from a bead's branch or the working tree. A dir depot may keep the same files in its directory instead, read from the directory as it is on disk, so an edit to one applies at once, as soon as the file's mtime or size changes (`RepoFlows` and its directory load in `internal/store/repoflows.go`, where a dir depot's `RepoFlows.Dir` names the directory and its `Base` and `Commit` stand empty). Either way the yard calls the source a repository flow; only its address differs, `repo@<commit>` at a git depot's base against `repo (directory)` in a dir depot's directory (`FlowSource` and its `String` in `internal/store/flows.go`: kind `repo` with a commit, against kind `repo` with none). A flow may instead stand in the store under a name (`yardr flow set <name>`, then `yardr depot flow <depot> <name>`), with its stage files as plain files in the yard's home at `~/.yardr/flows/<name>/<stage>.md`; the store holds no prose. That is a dir depot's usual flow too: the pack that sets one up puts its flows in the store and its stage files in the home, and the directory itself holds no flow file until the operator keeps one there (docs/dir-depots.md, step 1 and A dir depot's own flows and roles). Or a pack's import may have put the flow in the store and its stage files and roles in the yard's home, reviewed where the pack is kept and changed on this yard when the operator applies the pack again, on either depot kind. A flow a bead pins for itself (`--meta flow=`) governs that bead alone; it is no depot's line, and the read below lists a depot's governing flows pins aside, as `DepotFlows` contracts to (`DepotFlows` in `internal/store/flows.go`), so a pin is never one of its sources. A flow's stages are ordered as its rules first name them; a rule names the stage's outcomes and where each takes a bead, and a `<stage> terminal` line ends a bead that enters it (docs/flows.md, Stage order and Terminal stages).

Who works a stage is not in the flow. A route sends beads of a stage to a group, and the group's runner says how work starts (docs/groups.md, Runners): `herdr` starts an agent of the group's `kind` and `model` with its `prompt` and `args`; `exec` runs `sh -c` on the group's `cmd` in the depot; `manual` starts nothing and the bead waits on the group's members; `peer` sends the bead to a linked yard. A route's depot scope comes first, and it is the scope this design most needs to show. A route that names a depot is that depot's own; a route that names none is a yard default, serving every depot that states no route of its own for the same beads (`Route` in `internal/store/routing.go`, on its `Depot`; `yardr route add --help` says the same in words). Which beads those are is the route's match key — its stage, type, labels, bead priority and originator together — and a depot's own route sets a yard default aside only for the beads of that key, and only in that depot; a depot that states no route for a key keeps the default for that key's beads (`EffectiveRoutesByKey` in `internal/store/match.go`). So the yard-wide rule standing behind one depot's stage may also be standing behind the same stage in every other depot that has not set it aside, and changing it where it stands moves all of them at once. Besides its scope, a route matches on more than the stage: besides the bead's type it may filter by labels (`Label` and `AndLabels`), by bead priority (`BeadPriority`, a bead at that priority or more urgent) and by originator (`Originator`: nobody named takes only the operator's beads, a name takes that user's, `any` takes every originator's), so one stage may be served by several routes for different beads (`Route` in `internal/store/routing.go`; `Matches` in `internal/store/match.go`). A route also names a chain: its first group, then further groups in `Else`, each optionally carrying a quota condition (`When`, as `name@Weekly<80`), tried in order when the dispatcher chooses (`Route.Groups` and `Route.Choose`); which group of a chain works a given bead is decided at claim time, and every view that names one group of it names the first (`Route.Worker`). The group stands in the store as `Group` (`internal/store/routing.go`): name, runner, config map, limit, members. A crew member stands the same way (`CrewMember` in `internal/store/crew.go`), with its own `prompt`, `kind` and `model`, tied to no stage. Routes, groups and crew are store state: live, changed with yardr commands, no commit needed, because they name one installation's machines, scripts and trust decisions (docs/configuration.md, Why the store holds who, where and how).

Two texts that are not about the bead go into every agent brief (docs/groups.md, Role file or stage file). The role prompt follows the group: `prompt` is a file, read when a session starts by `readPrompt` (`internal/runner/runner.go`), which resolves `roles/<name>.md` first to the depot's `.yardr/roles/<name>.md` at the tip of its base — in a dir depot's directory, as the file stands there — then to the yard's home, and an absolute path as it stands (a pack's installed copy is one). The stage file follows the flow: for a repository flow it is read with the flow, from the base at a git depot and from the directory at a dir depot, for a store flow from the yard's home. If a sentence would still be true after another group took over the stage it belongs in the stage file; if it would still be true after the group was routed to another stage, in the role file. Stages no agent works have only a stage file.

### 2.2 The read doors

Three read surfaces already carry most of a read-only window, and they do not carry the same things.

The terminal's map is drawn by `yardr prime --bead <id>`: before the stage block it prints the whole flow, one line per stage with who works it (`agents`, `script`, `people`, `end`, `nobody`, from the routed group's runner, groups not named), the first sentence of the stage's file, the bead's place and its path (docs/flows.md, The map of the flow). As JSON, `prime --json` carries that map as `flow{name, stages[name, who, summary, current], path}`, the bead's own stage in full as `next.stage_file{path, text}`, and the flow's rules as `next.flow`. `yardr flow show <depot> --json` carries more of the line and less of the text: per flow its stages in order with the routed group, any further groups (`else`), the stage's next stages, its open count and its stage file's *path* — never the file's text — plus the flow's transitions and outcomes and its source (`repo@<commit>`, or the store). `yardr group show <name>` shows one group's runner, kind, model, `cmd`, `prompt` path, args and env file, and its routes; `yardr crew show <name>` shows a crew member's prompt path, env file and env command the same way. In every case the prompt itself is named by path and never quoted: the store holds no prose, and no read returns a role's text.

The web view draws the line twice over. `/flows` shows per depot each flow as a column of stages with the routed group, its members for a manual group, its stage file's presence and its open beads as cards (docs/web.md, Flows). `/flows?panel=1`, the yard panel, draws every depot's flows as one line plan per flow from `flow draw --mini`: a thin track, each stage a section of it with its name and count, a manual stage as a siding above, the open beads standing on it as lights, and a tap on a section opens that stage on `/flows` (docs/flows.md, Drawing a flow; docs/web.md, The yard panel). Both pages are server-rendered for a browser; footplate renders neither.

Footplate's door is the socket API, and only that. Its client (`src/api.rs` in the footplate repository, at 23c2c90) calls the yard with `POST /call/<Method>` over the local socket, over TLS to a yard at an address, or down the edge link, sealed where the device pinned a channel key and plain where it did not. The methods a program outside yardr may rely on are the named-argument calls in `Calls` (`internal/rpc/api.go`); the listener serves those, the operator's calls in `OperatorCalls`, and nothing else — any other method is answered as one the yard does not have (`UserServer.call` in `internal/rpc/user.go`). For the line, the one call footplate has is `Flows`, which it already draws as its panel and its line view: per depot, per flow, the stages in travel order with the routed group's name, whether it is manual, the stage's lamp, its terminal flag, the group's seats and the open beads on it (`FlowsBoard` in `internal/store/flowsboard.go`; `FlowStage` and `Flow` in footplate's `src/api.rs`). That is a timetable, not a line editor. A stage there carries no runner (only `human` tells people from the rest, so an agent stage and a script stage read alike), no kind, model or `cmd`, no prompt path or text, no stage file path or text, and no next stages; the flow carries its source but not its rules. The yard-side reads that do carry those things — `DepotFlows`, `Groups`, `GetGroup`, `Crew` (`internal/store/api.go`) — are socket reads (`internal/rpc/access.go`) that stand in neither `Calls` nor `OperatorCalls`, so no device can make them. The prime map's markers have no match in footplate either: footplate draws its own track from `Flows`, and neither the map, the SVG nor the mini drawing is a surface it consumes. So the read-only slice stands on reads the yard has, but through no door a device may use today: one new operator read carries it (section 3.1), and no yard write path is needed for that slice.

### 2.3 The edit doors

What names what runs is the operator's to set, and the store holds it so. A group's `cmd`, `dir`, `env_file`, `kind`, `args`, `prompt`, `worktrees` and `effort`, a change of runner to or from `exec`, and a crew member's `env_file`, `env_command`, `prompt` and free `args` are refused from anyone but the operator, a crew member's pane included (`checkGroupDefine` and `checkCrewDefine` in `internal/store/define.go`; docs/groups.md). At a terminal the operator changes them whole: `yardr group set`, `yardr group add` (which writes a group whole and so can change its runner), `yardr route add` and `route set` for what serves a stage, and `yardr flow set` for a store flow's stages and rules. A repository flow has no such command at all: at a git depot it changes as any file in the depot changes, by a bead whose branch lands on the base through the depot's review (docs/configuration.md, Why the repo holds what the work is); at a dir depot its directory flow changes the plainer way, by the file in the directory being edited, the operator's own act at a terminal (section 3.3).

Away from a terminal, the one door is a card. A run ask proposes one command of the fixed list (docs/chat.md, Questions for you, the whole table), the yard writes the card from its own records, an approval re-writes the card and refuses as stale where what it names has moved, and the yard then runs the stored command once, as the approver. The cards that already touch a line are these: `group add` for a new group, showing the runner and limit, the `cmd` of an exec group or the kind and arguments of a herdr one, and the whole text of its prompt; `group set <name> prompt=<file> | cmd=<command> | preset=<preset> | effort=<level>` and `crew set <name> prompt=<file> | preset=<preset>`, each showing what stands and what would stand, whole. A prompt a card carries is read from a file under the yard's home that the ask names; approval is refused if that file holds other text by then, and on approval the yard writes the carried text to a new read-only file of its own, `roles/<name>.<digest>.md` under the home, whose digest is the text's SHA-256, and that becomes the prompt — so a new prompt is a new file, and the file asked from is never the file sessions read. These cards are weighty `code` and therefore strong: a paired device approves one with `weighed`, the hosted web only under a fresh sign-in, a terminal on the yard's socket as any card (docs/api.md, Weighty cards). A delegated run — the yardmaster running a command on the operator's cited local mail — is a narrower door with its own list, and it never carries a `prompt`, a `cmd`, a change of runner or free `args` (docs/users.md, The yardmaster for the operator).

Three gaps stand between that list and the question. No card proposes a flow: `flow set` is terminal-only, so a store flow's stages cannot be added, removed or reordered away from a terminal at all. No card proposes a route: `route add`, `route set` and `route rm` are terminal-only, so what serves a stage cannot be changed from a device except by changing the group itself. And no card changes a runner, a group's `kind` or free `args` on a standing group: those stay with `group add` whole at a terminal, or beside it, for the reasons section 4 keeps. There is also no API write for any of this, and this design adds none: a device never names a command the yard runs except by approving a card the yard wrote (section 3.4).

### 2.4 What history already keeps

A wrong edit is undone from what the change left behind, and each home for a line keeps a different amount. A git depot's repository flow, its stage files and the depot's own roles are files on the base branch: git keeps every landed version, and undoing one is a revert commit that goes through the depot's review like the edit did. A dir depot's directory flow and roles are files in a plain directory: the yard keeps no version of them at all, and what takes an edit back is only a copy of the text that stood kept somewhere else — a mail, a note, the operator's own version control of the folder, where they keep one. A prompt a card set is a digest-named file the yard wrote and never rewrites: the text that stood before stands on disk beside the new one, the group's `prompt` names one file or the other, and putting the old one back is one more card naming it. A store flow keeps the least: `PutFlow` (`internal/store/flows.go`) replaces the named flow where it stands and records a `flow_set` event naming the flow and nothing of what it replaced, so the text that stood is kept only where a card showed it. The routing events split the same way, and the split decides where a take-back can come from. A route's edits are kept whole: `route_added` and `route_removed` carry the route as `routeEvent` builds it (its id, stage, first group, every group with its condition where the route is quotaed, and the type, depot, label, priority and originator filters it sets), and `route_set` carries that shape twice, as `was` and `is` (`routeEvent` and `SetRoute` in `internal/store/routing.go`), so the route that stood can be read back from the event alone. A group's edits are not: `group_set` carries only `name`, `runner`, `limit` and `members` where it has any, and the runner's config is omitted on purpose (docs/groups.md, the events table; `putGroup` in `internal/store/routing.go`, which writes exactly those fields; the held-fields table in `internal/store/eventtold.go` says the same). A `cmd`, a `prompt`, a `kind`, a `model`, `args` and an env file therefore survive nowhere in the event: the event proves the group changed, and when and by whom — the run ask machinery reads the last `group_set` for exactly that, to refuse a stale approval (`internal/store/runask_groupset.go`) — but it cannot say what the old command or prompt was. For those settings the take-back lives where section 2.3 put it: on the card itself, which shows the text that stands and the text proposed whole and names the command that takes its change back, and, for a prompt, in the old digest file standing on disk beside the new one. An undo of a group setting is therefore a second card quoting the first, never a restore from the event, and section 3.5 holds the window to saying so. Every card carries that take-back command in its own sentences, so an undo is a second card the operator approves, not a restore of a record. A card approval is also held to what the card showed: where the flow, group or file moved since the ask, approval refuses as stale and runs nothing. What no surface offers today is a version list per save to pick a revert from; section 3.5 says what the window shows instead, and section 4 leaves a history view out.

### 2.5 The sealed door, before and after yardr-dz5e

An approval is an operator call, and the listener holds it to its transport rule (`inTheClear` in `internal/rpc/userclear.go`). `ApproveAsk` is served to a device of the operator alone (`operatorCall` in `internal/rpc/user.go`), it crosses the edge link from a paired device plain or sealed alike — pairing is the grant, and the command it runs is fixed on the ask — and it is refused where the proxy in front of the yard says the device reached it in plain HTTP. The device's token crosses with a plain call, where the edge can read it; what a holder of a stolen token can then have run is the stolen-device table's question, answered per card in docs/users.md, and the prompt and `cmd` cards stand in it already.

Footplate stands in two places, and the door differs by place (docs/users.md, Footplate on another machine). On the yard's own machine it talks to the yard over its socket and nothing needs pairing: the read, the filing mail and the approvals of this design all travel that socket. On another machine footplate is a device: it calls the yard's listener at an https address the operator makes reachable, paired by a code the operator opens, or it comes down the edge link, sealed where it pinned the yard's channel key and plain where it did not.

yardr-dz5e, shaped and held in backlog, changes the plain half of the second place. From its release, a device call that reaches the yard down its edge link unsealed is refused, judged on link calls alone, with the one plain exception of a pre-release device's one-time migration registration; a client older than the sealed releases keeps only its direct paths. Before it lands, a desktop that paired plainly can read the line and approve its cards over the edge, with its token readable on the way. After it lands, that same desktop loses both down the link until it calls sealed — paired again from a QR code, or with its key registered in place by `RegisterChannelKey`, the weaker of the two — while footplate on the yard's own machine, over the socket, and footplate at the yard's own https address notice no change. Every slice below is written to that second world and merely works sooner in the first; no slice asks for a plain-call exception.

### 2.6 Footplate today

Footplate's window puts the yard's decisions in front of the person as cards in Decide, with the weighty words first and `ApproveAsk` behind the approval (docs/window.md in the footplate repository), and its panel and line views draw the `Flows` timetable above. Where the window runs as the yard's operator on the yard's own machine it already carries operator rows of the same shape this window needs — the Grants row read through `SourceGrants`, the Teammates row — and one editing precedent: the Pair a phone row, which opens a pairing from the window on the yard's own machine and is absent on a yard at an address. It renders no line editor, no stage detail and no prompt text, and no match for the prime map's markers stands in it (checked at 23c2c90). The yardr design system (the yardr-design repository beside this one) rules the drawing where a bead is labelled `eyes`, as this one is: yard, depot, stage, route, group and runner keep their railway names, there is one accent, and targets and contrast follow its brief. The sketches in section 3 are word sketches in that vocabulary, not new colours or words.

## 3. The proposal

The smallest version that answers the question is one new window in footplate, the Line window, opened per depot from the line the panel already draws, in three slices that each stand alone. Slice A shows the line and its prompts and changes nothing. Slice B changes a prompt through the card door that already exists, so its only new machinery is an editor and a way for footplate to file the card. Slice C changes stages and what serves them: choosing a server rides a new route card (a depot's own rule changed where it stands, a yard-wide rule set aside for this depot alone), adding, removing and reordering stages rides a new flow card for a store flow and the depot's own review for a git depot's repository flow — a dir depot's directory flow keeps its terminal door and gains no window edit in the first version (section 4) — and choosing a runner rides the group cards that already exist. Nothing in any slice is a plain API write: a device sends words and approvals, and the yard runs only a command a card holds or a change a bead lands. The slices are written under the recommended answers to section 5's open questions; where the other answer is taken, the bead it changes says how it grows.

### 3.1 Slice A: the line, read-only

The window is new, and the drawings that exist are not made tappable. The yard panel's mini plan and footplate's own track are timetables: they draw stages and beads, and the data under them (`Flows`) has no runner, prompt or rule to tap through to, so there is nothing for a tap to open. Nor does footplate take the web's pages or the SVG: its one door is the socket API, and the window below stands on a read through that door, drawn natively as its panel is. What A adds on the yard is one read, in `OperatorCalls` beside `SessionScreen`, whose shape is the precedent: it changes nothing but is the operator's to read, because a `cmd` and a prompt are told to a device of the operator alone. The call is `Line`, with one argument, `depot`; it answers every flow that governs the depot, the depot's own first and then one per type, each as `flow show` names it:

- the flow's name, type and source, and its stages in the flow's order with each stage's next stages, its outcomes (`name`, `to`, and `max`/`then` where the flow has them), and whether it is terminal. The source is one of `repo@<commit>` for a git depot's repository flow, `repo (directory)` for a dir depot's directory flow with the directory named beside it, `pack <name>` for a pack-managed flow, and `store` for any other store flow, in the words `FlowSource.String` already prints (`FlowSource` in `internal/store/flows.go`). There is no fifth source for a bead's pin: the read answers the depot's governing flows pins aside, as `DepotFlows` contracts to (section 2.1), so a flow one bead pins never stands in the window as the depot's line. `DepotFlows` alone cannot tell the last two store sources apart: it answers a `FlowSource` whose kind stands as `repo` or `store` for the flows it lists, and a pack's flow stands in the store like any other. The read therefore joins the yard's pack imports, as `depot sources` already does: from `Packs` (`internal/store/api.go`) it takes the imports into this depot (`PackImport.Depot`) and names the pack whose record lists this flow among its objects — an object of kind `flow` whose name is the flow's name (`PackImport.Objects`, `PackObject` in `internal/store/packs.go`; `flowPack` in `internal/cli/depotsources.go` is that join, and its caller marks the line `pack` where it hits and `store` where it does not). A flow so marked is pack-managed wherever this design uses the word, and no other flow is;
- per stage, who serves it, stated as a representative route and the rules behind it. The representative route is deliberate, and it is the one the yard's existing views already pick: a probe bead of the depot, of the flow's type (the default type where the flow has none), at the default priority, with no labels, reading as the operator's — the board builds exactly that probe before `MatchRoute` (`internal/eta/store.go`), and `flow show` probes the same way (`take` in `internal/cli/flowasks.go`). The read answers that route whole: its id, its scope — this depot's own where the route names the depot, yard-wide where it names none, in those words — the filters it sets (its type, labels, bead priority and originator, each named and each shown as unset where it is unset, never silently dropped), its chain in order — the first group and every further group behind it, each with its quota condition (`When`) where it carries one — and, per group in the chain, its runner, and for a herdr group its kind and model, for an exec group its `cmd` whole, for a manual group its members, for a peer group its yard; the first group's limit, the open beads in the stage, and a warning where no route serves it or beads stand stranded in a stage the flow lacks (the two warnings `flow show` already prints). Behind the representative the read lists every other effective route of the depot that serves the stage (`EffectiveRoutes` in `internal/store/routing.go`), each as its id, its scope in the same words, its filters and its chain's first group, so a stage whose urgent beads, labelled beads or another user's beads take a different rule shows that rule rather than hiding it behind the representative, and no rule's reach is left for the reader to guess: a yard-wide rule in either place serves every depot with no own route of its match key (section 2.1), and the window says so on the rule itself before any picker stands under it (section 3.3);
- per stage, its stage file where it has one: the path as `flow show` names it and the text whole;
- per herdr group and per crew member, its prompt: the path the config names, where `readPrompt` finds the text (the depot's file at its base, the yard's home, a pack's installed copy, or the file as it stands), the text whole, its digest where the file is one the yard wrote, and whether a card can carry it and why not where it cannot — judged by the card's own rules (`promptBefore` in `internal/store/runask_strong.go`: beside the path limit of section 3.2, a text longer than the bytes a card shows, or text a card does not show as written, cannot be carried). The window gates a prompt's Edit on that answer, not on the prompt's source alone (section 3.2), so a home prompt a card cannot carry for its length or its text stands behind Read exactly as a depot's own file does.

The server builds the answer from what it already computes — `DepotFlows` for the flows and their stage files' paths, joined with `Packs` for the pack provenance of a store flow as the bullet above states, the depot's effective routes and `Groups` for what serves each stage (the representative route picked by the probe that bullet names, the remaining effective routes listed behind it), the stage file texts it reads for a brief, and `readPrompt`'s own lookup, lifted so the read and the brief can never disagree about which file a session would be given. A prompt file that cannot be read answers with the paths tried, as a session start fails; it does not fail the window. The read is the operator's under the approval's transport rule: over https or from the yard's own machine, and down the edge link from a paired device of the operator, sealed or — before yardr-dz5e — plain, as an approval crosses. Who else may read it is open question 2. Footplate calls it only when the window is opened or the depot is changed, and reads `Flows` again for counts as it does today; a change to the line itself is no bead event, as on `/flows`, so the window says to reopen it after an edit lands rather than pretending to be live.

The window, at the usual width, with one depot open:

```text
yardr · Line
Depot  [yardr            v]   Flow  [default (repo@db57f0c)  v]

It is useful the day it lands: the operator reads in footplate what today takes `flow show`, `group show` and opening three files at a terminal.

### 3.2 Slice B: a prompt, changed on its card

What is shown in A decides what B may change. Of the three texts, two already ride cards and one does not. A group's role prompt rides `group set <name> prompt=<file>`; a crew member's rides `crew set <name> prompt=<file>`; both show the text that stands and the text proposed, whole, are weighty `code`, and on approval write the proposed text to a new digest-named file that becomes the prompt, held to the file the ask read by then. Those two are B's editable texts, with one narrowing this slice takes and adds no yard machinery to widen: Edit stands only on a prompt the existing card can show whole, and the window gates Edit on the `Line` read's answer to exactly that question for the prompt in front of it (section 3.1), not on the prompt's source alone — a prompt under the home that a card cannot carry for its length or its text gets no Edit either, and the window shows the read's reason where Edit would stand. That is a prompt file under the yard's home — named by an absolute path, a digest file the yard wrote, or a pack's installed copy under the home — which is the only text `promptBefore` reads whole for a card (`promptBefore` in `internal/store/runask_strong.go`: a relative path answers that the card cannot show it, read against each depot, and a file that does not stand under the home answers the same). A depot's own role file — a relative `roles/<name>.md` that `readPrompt` resolves in the depot (section 2.1) — is the depot's file, not the yard's: in the window it shows behind Read with no card Edit, and it changes as a repository flow does, by mail that has the yardmaster file a bead in the depot carrying the new text, through that depot's review (section 3.3). The cost is stated plainly: the prompts a depot keeps for itself, which are the ones its own builders read most, take the slower bead door from the window, while a prompt the yard or a pack installed takes the card; widening the card to carry a relative prompt's resolved text is left out (section 4). A stage file rides no card, and B does not add one: a stage file is part of the flow's home (section 3.3), so it changes with the flow, in C — for a git depot's repository flow through the depot's review, where a diff of it is seen whole, and for a store flow not at all in the first version (section 4); a dir depot's directory flow and its stage files change at a terminal, not from the window (section 4). In the window an eligible prompt's Edit opens an editor over the text that stands; a depot's own role file and the stage file stay behind Read.

What footplate sends is words, not a command. It has no file under the yard's home for `yardr bead ask` to read the proposed text from, which is the one thing the card machinery asks of whoever files. The smallest filing door is the one every card already travels by: the yardmaster files run asks on the operator's mail (docs/groups.md, Designing a process in docs/flows.md). So Edit's Send mails the yardmaster one mail whose first lines name the depot, the group or crew member, and the prompt file and digest that stand, and whose body after them is the proposed text whole and nothing else. The yardmaster files a prompt, route or flow card only from the operator's own mail; mail from anyone else gets no filing. The yardmaster writes that text to a file under the yard's home and files the existing card from it; the card stands in Decide with both texts whole, and the operator approves or declines it there as any strong card — a paired device with `weighed`, the hosted web under a fresh sign-in, a terminal on the socket. Approval runs the stored `group set` or `crew set` once, and the next session of that group starts with the new prompt; a session already running keeps the one it started with, as it does today. Where the prompt moved since the window read it, the card's own check refuses the filing or the approval as stale, and the window's answer is to read the line again rather than send twice. A prompt with no group behind it — a stage served by hand or by script — has no Edit: there is no agent to prompt, and the window says so on the stage rather than offering an editor over a stage file.

Two costs ride with B and are stated on the window before Send. The mail is the filing, so the proposed text stands in the mail log as the yard keeps mail, where a terminal filing would keep it only in a file under the home and on the card's bead; and the edit waits on the yardmaster's next pass, not on a call, so the window says the card will stand in Decide rather than that the prompt changed. Both are the price of adding no write path; a filing call of footplate's own is left out until the errand proves frequent (open question 1).

Cost of B: no yard change at all — the cards, the stale check, the digest file and the strong doors stand. In footplate, the editor, the mail it composes and sends through the `Mail` call it already has, and the hand-off words — a small bead on top of A's window. Its usefulness does not wait for C: prompts are the text the operator adjusts most, and they become adjustable from desktop footplate with no new way for a device to name what runs.

### 3.3 Slice C: stages, and what serves them

C is three edits of different weights, and the design keeps them apart rather than giving the window one Save.

Choosing what serves a stage is a route, and it gets the one new card C needs on the yard — with one limit the window's per-depot view forces, stated here as the pick. The window never edits a yard-wide rule where it stands. A depot's window is opened on one depot, and the operator picking a server there means that depot; a yard-wide rule changed from it would silently move the same stage in every other depot that keeps the rule for its key (section 2.1), on screens none of them show. So the picker offers two different cards by the rule's scope, and each card names its scope in its first lines, before it names any group.

For a rule that is this depot's own, a run ask row `route set <id> --group <group>` — and `route add --stage <stage> --group <group>` where a stage has no route — proposes the group that takes a stage's beads, and it proposes it for one named rule, never for a stage in the abstract: `<id>` is the id slice A read for the rule being changed, the representative rule unless the operator picked another rule from the stage's Other rules list first. The card names that id, its scope (this depot's own) and the rule whole as it stands: the depot, the flow and type the route is read for, the stage, every filter the rule sets (its type, its labels, its bead priority and its originator, each shown as unset where it is unset), its chain in order with each group's quota condition, the group that serves it now and the group proposed, each with its runner, its kind and model or its `cmd` whole, the stage's open beads by count, and what takes the change back. It changes the chain's first group and carries every filter and every condition unchanged — editing a filter or a condition is no part of the first version (section 4) — so beads the rule's filters do not select are untouched twice over: this rule never took them, and the further rules that do take them stand as they were. It is weighty `code`, strong, because what it chooses is what runs next on every bead that rule takes; the approval re-reads the route by its id and refuses as stale where that rule's server moved since the ask, and says nothing about any other rule of the stage.

For a yard-wide rule, the picker files the set-aside the yard already has instead: a run ask row `route add --depot <depot> --stage <stage> --group <group>` carrying the yard-wide rule's match key and chain whole, with only the chain's first group changed — the group as it resolves for this depot, since an own route names no depot template (`yardr route add --help`, on `{depot}` templates). The card names the yard-wide rule's id and scope, says in its first lines that it creates this depot's own rule setting that rule aside for the beads of its key in this depot alone, and names what does not move: the yard-wide rule itself, every other depot that keeps it, and this depot's beads of any other key. Filing refuses at ask time where an own rule for the key already stands in the depot — there is nothing to set aside for this window to do, and the store's own tie check (`checkRouteTie` in `internal/store/routing.go`) stays the backstop behind that refusal — and approval refuses as stale where the yard-wide rule moved since the ask, or where an own route for its key has appeared in the depot since, approving then would write a second own rule over one the operator has not seen from this window. The card also says what the set-aside does not follow: if the yard-wide rule's filters change later, this depot's own rule keeps the key it was filed with, as any own route does, and no field on either rule points at the other. Its take-back is the reverse set-aside: deleting the own rule it created (`yardr route rm <id>` at a terminal, named on the card), after which the yard-wide rule serves the depot again as before; no card carries that deletion in the first version, and the card says so. Changing the yard-wide rule itself for every depot stays at a terminal, where `yardr route set <id>` types its scope whole and no depot's window stands in front of it. Choosing among the groups that stand needs nothing else. Choosing a server that does not stand yet rides the cards that stand: a new group rides `group add`, which shows its runner and its prompt or `cmd` whole, and an exec group's `cmd` on a standing group rides `group set … cmd=`. What no card gains is a change of runner, of `kind` or of free `args` on a standing group: `group add` whole at a terminal stays their door (section 4). In the window, the stage detail's Served-by picker stands under the Rule line it edits: it names that rule's id, its scope and its filters first, then lists the yard's groups by name with their runner beside each — agents, script, people, another yard — and picking one files that scope's card for that rule; where the stage has further rules, each stands as its own row under Other rules with its own picker, so no pick is ever ambiguous about which rule, or which scope, it moves. New group… files the `group add` card with the runner chosen first, since the runner is the choice the question names ("agent script etc.") and the card is where its command or prompt is shown whole.

Adding, removing and reordering stages is a flow edit, and where it lands depends on where the flow stands, which the window says on the flow's own row before offering the edit. The pick is: a store flow is edited on a card, on either depot kind; a git depot's repository flow is edited through the depot's own review; a dir depot's directory flow is not edited from the window in the first version — changing it stays at a terminal, in the directory itself, and the window's Stages row for such a flow offers no control and names that door; a pack's flow is edited in neither, since it is reviewed where the pack is kept and reaches this yard by `yardr pack apply`, whose own card already shows its objects whole.

For a store flow, a run ask row `flow set <name>` carries the whole flow as the line format writes it, the stage order first: the card shows the stages added, removed and reordered, each kept stage's outcomes and next stages as they stand and as they would be, the beads standing in a removed stage by id, and the command that takes it back, which is the flow that stands, carried whole the same way. It is weighty `code`, strong: a flow decides what runs on every bead that follows it. One refusal stands before any of that is shown: the `flow set` card refuses a flow a pack manages, by the same Packs join the read uses (section 3.1: `Packs`, `PackImport.Objects` of kind `flow`, as `flowPack` in `internal/cli/depotsources.go` joins them), and names `yardr pack apply` as the door — a pack's flow is changed where the pack is kept and reaches this yard by applying the pack, and a generic `flow set` write would put a local edit where the next apply silently takes it back. That refusal is load-bearing, not a courtesy: nothing underneath it stops such a write today — `packFlowWrite` (`internal/store/delegation_pack.go`) returns nil outside a delegated pack apply, so `PutFlow` (`internal/store/flows.go`) accepts the write — and the card therefore makes the refusal twice, at the ask and again at approval, since a flow may become pack-managed between the two. Two refusals ride with it, both the terminal command's own, made when the ask is written and again at approval: a stage order the rules cannot order is refused as `flow set` refuses it, and a removal that would strand a bead is refused naming the beads, as `flow set` and `depot flow` refuse a change that leaves a bead in a stage the new flow lacks (docs/flows.md, Named flows and pointers). The window is held to the same words before it files: Remove on a stage with open beads names them and files nothing, and says to move them out first, which the flow's own moves do from the bead. Reordering is the same card with the order changed and nothing else; the window's stage rows move by up and down controls, not by dragging, so the order sent is the order seen. A stage added on the card stands in the flow with no stage file: `flow show` warns of that and refuses nothing, the bead in it gets the role prompt and the bead, and giving it a stage file stays a file edit in the yard's home (section 4). A type's flow is shown in A and not edited in C's first version (section 4).

For a git depot's repository flow there is no yard write to propose, and C does not invent one. The window's Edit on such a flow composes the same mail shape as B — the depot, the flow file, and the whole proposed text of the `.flow` file and of any stage file the edit adds or changes — and the yardmaster files a bead in that depot carrying those texts as the change to make. That bead travels the depot's own flow and lands as a commit on the base through its review, which is where a flow is reviewed today; on depot yardr the diff touches `.yardr/**`, which stands in `.yardr/security_paths`, so its reviewer may not call it done-safe and it takes both reviews, as any flow, stage-file or list edit there already does. The same holds in any depot whose list names its flows, and in one that does not, its ordinary review is the gate. Removing a stage that way strands its open beads in the way the base change does today (docs/flows.md, A base change that drops a stage): the yard moves nothing and refuses nothing, `flow show` warns per bead, the bead is not routed, and it rejoins at the flow's first stage by `yardr bead advance` — so the bead the window files says to move the stage's beads out first, and the window names them before the mail is sent, exactly as for a store flow. A flow edit that a person would rather land themselves is unchanged by all of this: the files are the depot's, and a terminal edits them as today.

For a dir depot's directory flow the window offers no edit in the first version, and no mail from the window changes it. There is no repository for a bead's change to land in and no review that reads the directory before it applies (section 2.1), so a window edit there would need either a new unreviewed write path or a card this design does not propose for it — and open question 4, which is the operator's, asks only about the route and store-flow cards. Changing a directory flow therefore stays where it stands today: at a terminal, by editing the `.flow` file — and any stage file beside it — in the directory itself, taking effect on the yard's next read of the directory (docs/dir-depots.md). Slice A still shows such a flow whole: on a `repo (directory)` flow the window names the source and the directory, and its Stages row offers no control, naming the terminal as the door, so the operator reads the line in the window and changes it where the file stands. A store flow on the same dir depot takes the flow card above instead, exactly as on a git depot, and the flow's source on its row — `store` against `repo (directory)` — is what tells the operator which of the two stands in front of them. A dir depot given its flows by its setup pack has the store kind until the operator keeps a flow in the directory (docs/dir-depots.md, A dir depot's own flows and roles), so the card is the dir depot's usual stage door from the window, and the directory flow its terminal-only one. What this costs, and what would widen it, stands in section 4.

Cost of C: on the yard, two run ask rows — `route set` (with `route add` where none stands, and `route add --depot` for the yard-wide set-aside) and `flow set` — each with its card, its stale check, its weight and its stolen-device row, a medium bead; the repository half needs no yard code, only the window's mail and the yardmaster's filing, as in B, and a dir depot's directory flow needs none either, since the window offers it no control. In footplate, the serving picker, the stage add, remove and reorder controls, and the mail shape — a medium bead. C is the slice the question's last clause asks for, and it is deliberately last: it is the only slice that changes what runs on beads already travelling, so it lands after the read window and the prompt door have been used.

### 3.4 Which door, and what yardr-dz5e changes

Every edit above takes an operator's door and no other. Reading the line is an operator call held to the approval's transport rule. Changing a prompt, a server or a store flow is a card: the window sends words (a mail that files it) and an approval (`ApproveAsk` with `weighed`), and the yard runs the one command the card holds, as the approver, once. Changing a git depot's repository flow is a bead and a commit. Changing a dir depot's directory flow takes no window door at all in the first version: it stays the operator's own edit at a terminal, in the folder, as today, and no mail from the window files it. At no point does a device name a runner, a `cmd` or a stage for the yard to write directly, and no new socket method writes a group, a route or a flow: `PutGroup`, `SetRoute` and `PutFlow` stay socket-and-terminal machinery that no device call reaches. That is the line the stolen-device table prices: a holder of a stolen operator token can approve a card that was proposed whole, and can do nothing that was not shown on one.

Which door an edit takes depends on where footplate stands, and both places end at the same cards. On the yard's own machine, footplate's read, its filing mail and its approvals travel the yard's socket: no pairing, no token on a network, no edge in the way, before yardr-dz5e and after it. On another machine, footplate is a paired device calling the listener at the yard's https address or down the edge link (docs/users.md, Footplate on another machine): the same read and the same approvals, held to the operator-call transport rule of section 2.5.

yardr-dz5e moves the plain half of that second door, not its shape. Before it lands, a desktop paired plainly reads the line and approves its cards down the edge link, its token readable by the edge on the way, as an approval crosses today. After it lands, a plain call down the link is refused, so that desktop's Line window and its approvals stop down the link until the device is sealed; the window's answer is the refusal's own words, naming the fix, with no fallback to a plain read of less of the line. Footplate on the yard's own machine and at the yard's own https address are on direct paths before and after, and neither slice B's mail nor slice C's cards gain an exception: a mail that files an edit is a call like any other, and where it cannot cross, the operator sends it from a sealed device or from the machine. The design therefore ships its slices against the sealed world and does not hold any of them for dz5e; a yard with no edge and no remote desktop notices nothing at any point.

### 3.5 What a wrong edit costs, and how it is undone

Each edit's undo is the take-back its door already names, and the window shows it before the edit is filed, in the same place it shows what the edit does. A prompt card's approval writes a new digest file and leaves the old one standing: undoing it is a second card naming the file that stood, which the first card's sentences name, and the window's prompt row offers it as Revert while that file stands. For a depot's own route edit and for a store flow, the route card and the flow card each carry the command that takes the change back — the route or the flow as it stands, whole — so the undo is a card of the same weight, approved the same way, and a flow card approval needs no version store behind it because the text it replaces travels on the card itself. That sentence reaches no further: a yard-wide rule was never moved by the window, so its set-aside's undo is not a card at all but the terminal deletion its card names, `yardr route rm` of the own rule it created, after which the yard-wide rule serves the depot again, as section 3.3 states; until then the depot keeps the server the operator picked from its window, which is the change they approved. A git depot's repository flow's undo is a revert of its landing commit, filed as a bead the same way the edit was. A dir depot's directory flow has no window edit to undo: a change made at a terminal there keeps no version at all — no commit, no digest file, no store record of the text it replaced — so its undo stands only on a copy of the text that stood kept somewhere else, and where no copy was kept the text is gone; that is the sharpest cost of the dir kind's applies-at-once rule, and it is borne at the terminal, not hidden by the window. Where the take-back text comes from differs by door, and the window says which it is standing on rather than implying one history covers all: for a route, the `route_set` event itself keeps the route as it was (`was`) and as it is (`is`) in the `routeEvent` shape, so the take-back can be read from the record; for a prompt, a `cmd` and the rest of a group's runner config, no event keeps what stood — `group_set` holds only the group's name, runner, limit and members (section 2.4) — so the take-back text is the first card's, which showed both texts whole and named the file or command that stood, backed for a prompt by that file still standing on disk under its digest name. A window that offered to revert a `cmd` from the event would have nothing to revert to; it offers the second card the first one names, or nothing. What the store keeps underneath every edit — the event's kind, its day and its actor, and the approval's answer on its bead — is the record of who changed what and when, and the window's stage detail shows the last change to its stage's rule in those words (for a route change the event's `was` group beside its `is` group, since the event carries them; for a group change only that a `group_set` stands, with its day and actor, since the event carries no more), read from the yard's events as the bead's history is. The cost of a wrong edit is bounded by the same doors: a prompt or a `cmd` takes effect at the next session, never in one already running; a route takes effect on the next bead claimed in the stage; a store flow on the next bead routed; a git depot's repository flow only when its bead lands; a dir depot's directory flow on the yard's next read of its folder, which is to say at once, and on the next bead routed under it. Nothing an edit here does reaches a session mid-flight, and nothing is undone by editing a record backwards.

## 4. Left out

What follows was considered and is not proposed in the first version. Each names the door that stands instead, so the omission is a stated cost.

- **A plain write for any of it.** No new socket method sets a group, a route, a flow or a prompt, and `Line` reads and never writes. A write a device names directly is a command a device named, which the yard's doors refuse by construction: the operator sets what runs at a terminal, approves it whole on a strong card, or has it run as a delegated run on their own mail, and the delegated list gains none of these forms either, since a prompt and a `cmd` are never part of one. This is the bead's own rule, kept: the yard running a command a device named is the one thing no slice builds.
- **Editing a yard-wide rule where it stands, from a depot's window.** Section 3.3 files a depot's own set-aside for such a rule and leaves the rule itself to a terminal, where `yardr route set <id>` is typed with its scope in front of the operator and no single depot's window lends it a smaller meaning. A window that rewrote the yard-wide rule would need to name every depot it moves, price a change to depots it is not showing, and take it back for all of them at once; the set-aside already gives the operator the server they picked, in the depot they were looking at, and no other depot is surprised.
- **Editing a route's filters or quota conditions, and listing beads under each further rule.** The window shows every rule of a stage with its id, its filters and its chain (section 3.1), and slice C changes a named rule's first group and nothing else (section 3.3). Retuning which beads a rule takes — its labels, priority, originator or type — or the condition on a group in its chain stays with `yardr route set` and `yardr route add` at a terminal, where the match key the change moves is typed whole; the first version also counts a stage's open beads once, under its representative rule, and does not split that count by rule, since no view the yard has does.
- **Changing a runner, a `kind` or free `args` on a standing group.** The window shows the runner and offers another group, a new group and a new `cmd` on their cards. It does not offer to turn a standing herdr group into an exec one or to retune its arguments: another runner reads another set of config keys, so the honest change is `group add` whole at a terminal, where every key is written again, and free `args` are flags of a harness the yard did not write whose dangerous forms are dangerous by not standing in any table the yard holds — the yard's answer is a named preset of the kind, which already rides the group cards, and this design extends it not at all.
- **A stage file editor for a store flow, and any editing of a type's flow.** A store flow's stage files are plain files in the yard's home, named by no group and held by no digest: a card for one would quote the text whole and still pin nothing, since the file is read as it stands when a brief is written. They stay file edits, at a terminal or in the home, as a pack's import writes them; a git depot's repository flow's stage files ride the depot bead of section 3.3, where a review sees the diff, and a dir depot's directory flow's stage files are edited at a terminal in the folder beside their flow, where nothing reviews them first. A type's flow (the depot's flow for one bead type) is drawn in slice A and edited nowhere in the window's first version: it is the rarer edit, its door is the same `flow set` card or depot bead once the depot's own flow has proved them, and the second flow shape is open question 5's neighbour, left until use asks.
- **Editing a dir depot's directory flow from the window.** Slice A shows a `repo (directory)` flow whole, with its directory named, and slice C offers it no Stages control: changing it stays at a terminal, by editing the file in the folder, where it applies on the yard's next read with no review in front of it and no version kept (sections 2.1, 3.3 and 3.5). No mail from the window files such an edit, and no card carries it in the first version — open question 4 asks only about the route and store-flow cards. The cost is that a depot whose line the operator most often reads in the window must still be walked to a terminal to change its stages; the door that stands is the folder itself, and a later version that wants a window edit for it must first decide, as its own question, whether that edit takes a card, a bead-like review the dir kind does not have, or the applies-at-once rule with its eyes open.
- **A card that carries the resolved text of a relative prompt.** Slice B's Edit stands only on a prompt file under the yard's home, because that is the only text the existing card shows whole (`promptBefore` in `internal/store/runask_strong.go`). Extending the card so it resolves a depot's own relative `roles/<name>.md` — reading the file `readPrompt` would give a session, in that depot at its base, and showing that text whole on the card — is no part of the first version and needs no yard change today only because it is left out: it would be a yard change to the card's before-text, with its own stale check against the depot file it resolved. Until it is built, a depot's own role file shows Read in the window with no card Edit, and changes by a bead in the depot through its review, as section 3.2 states; the cost is the slower door for the prompts a depot keeps for itself.
- **Editing a pack's flow in place, and editing a flow any bead pins.** A pack's flow and roles are reviewed where the pack is kept and reach the yard by applying the pack, whose card shows every object and changed file whole; the window names that door and offers no local edit that the next apply would silently take back. A flow a bead pins (`--meta flow=`) is that bead's lifecycle, not the depot's line, and the window does not offer it.
- **A version history to revert from.** Section 2.4 keeps what each home keeps: git for a repository, the digest files and the cards' take-back commands for the yard's own, and nothing per save in the store. The window shows the last route change and offers the take-back each card names; it does not build a history list, a per-save version table in the store, or a one-tap revert across doors, because each door's undo already exists and a fourth record of the same edits is a second source of truth beside the events.
- **The filing call of footplate's own, and an approval surface in the window.** Slice B files by mail to the yardmaster, with the costs section 3.2 states, and every approval happens in Decide where the cards stand. A dedicated filing call — a `Line`-neighbour that takes a proposed prompt text and files its card in one write, in the shape of `UninviteTeammate` — and approving the card without leaving the window are both left to open question 1 and to use: mail and Decide carry the first version with no new write path at all, which is the point of the slice.
- **Footplate on a phone, and any phone layout.** The window is desktop footplate's, at desktop widths, with a mouse and a keyboard. footplate-ios and footplate-android gain no Line window, no stage detail and no prompt editor, and nothing here is drawn small: a phone that needs the line reads the timetable it has. The yard-side read is one call either app could take later, and the phone window is a design of its own against a landed desktop one.
- **The web view, chat and MCP.** `/flows` and the yard panel gain no editing controls, `yardr chat` gains no line window, and no MCP tool reads or files a line edit. The question names footplate; the yard-side read is one call any of them could take later, and each new surface is a design of its own rather than a flag here.
- **What a group burns and who may join it.** A manual group's members, a group's limit, its env file and its subscriptions stand where they stand: shown in A where the read carries them (members, limit), changed at a terminal or on the cards that already carry them, and not given controls here. The window edits what serves a stage and what the server is told; it is not a second group form.

## 5. Open questions

Questions the yard's standing rules answer are answered here; one is the operator's. So each question below says whose it is. Questions 1, 2, 3 and 5 are answered here, with the pick this document takes standing as the decision the yardmaster sends on; only question 4 is the operator's, and it holds yardr-0snd, and footplate-6hnm behind it, alone. Each gives its options, what each costs, and the one this document would take. The proposal above is written under the recommended answer to each; where the other answer is taken, the bead it changes says how it grows, and no other part of the proposal moves.

**1. How does footplate file an edit: by mail to the yardmaster, or by a filing call of its own? Answered here; not his.** Section 3.2 files prompt edits, and section 3.3 files repository-flow edits, as mail the yardmaster turns into a card or a bead. Option A: keep the mail. It adds no write path, the text travels whole and is shown whole again on the card, and its costs are the two stated there: the text stands in the mail log, and the card waits for the yardmaster's pass. Option B: a filing call per edit kind, in `OperatorCalls`, in the shape of `UninviteTeammate` — it files the one fixed ask and answers its bead and ask, so the window shows the card's bead at once and no agent stands between the editor and the card. It costs a new operator write per kind (prompt, route, flow), each with its own in-the-clear and stolen-device reckoning, for an errand whose frequency nobody has measured. This document would take A: the card is the safety, not the filing, and B can be added per kind later without changing what the operator approves.

**2. Who may read the line: the operator alone, or any user who may see the depot's beads? Answered here; not his.** Section 3.1 puts `Line` in `OperatorCalls`, so a member's device is answered as for a method the yard does not have. Option A: keep it the operator's. A `cmd`, a prompt and an env file's path are told to the operator's device alone today, and a role prompt may carry a depot's standing rules. Option B: serve the read to any viewer the beads are served to, as `Flows` is, withholding only the env file's path. It costs a second judgement per field about what a prompt discloses, on a view whose purpose is editing, which only the operator does. This document would take A; a member who needs to know what serves a stage has the timetable, which already shows the group, the seats and who works the bead.

**3. Does a repository flow's edit from the window travel as a bead the yardmaster files, or does the window file the bead itself? Answered here; not his.** Under section 3.3 the mail asks the yardmaster to file it. Option A: keep that. The bead's body is written by the crew member who knows the depot's flow, its review and its stranded-bead rule, and who says in it to move a removed stage's beads out first. Option B: the window files the bead directly, with the proposed files as its body. No call files a bead with a body today — `AskNew` files an ask on a new bead, not a work bead with instructions — so B is a new write with its own reckoning, bought to save the yardmaster a filing it already does for process designs. This document would take A, for the same reason as question 1, and notes the bead is an ordinary bead either way: reviewed, landed, revertible.

**4. May what serves a stage, and a store flow's stages, be proposed on cards at all — and if so, at what weight? His: a new door for what runs.** The prompt cards of slice B stand already; the route and flow cards of section 3.3 do not, and adding them is a new door through which what runs on a yard changes, which is the kind of decision that stays his. It holds yardr-0snd, and footplate-6hnm behind it, alone: slices A and B and their beads are sent without it. Option A: no new cards; what serves a stage and a store flow's stages stay at a terminal, and the window shows them and offers neither picker nor stage controls. Option B: the two cards as section 3.3 draws them, each weighty `code` and strong, for an add, a remove and a reorder alike — a reorder changes which stage a bead enters first and where a stranded bead rejoins, and a card whose weight depends on a diff's shape invites the shape to be argued at approval. Option C: the two cards, but a card that changes no stage's outcomes and no membership weighs nothing, as an `effort` card does; it costs the yard a proof that a diff is reorder-only, held at approval as the stale check is, and buys a lighter approval for the rarest of the three edits. This document would take B, and not because every card of a row weighs the same — they do not: a group-set card already varies by field, an effort-only change weighing nothing where a prompt or `cmd` change weighs `code` (`groupSetWeight` in `internal/store/runask_groupset.go`). The honest difference is what moves. An effort change moves no routing; a reorder does — it changes which stage a bead enters first and where a stranded bead rejoins — so it stands with the edits that move routing rather than with the ones that move none. And C's lighter card is not free: proving at approval that a diff is reorder-only and nothing more is new machinery on the approval path, built for the rarest of the three edits. The strong doors, meanwhile, are the ones the operator already uses for prompts. Under A, yardr-0snd is closed unbuilt and footplate-6hnm shrinks to its Last change line; under C it carries the reorder proof in its done-when.

**5. Does slice C edit a type's flow in its first version? Answered here; not his.** Section 3.3 shows a type's flow and edits only the depot's own. Option A: keep it so; the depot's flow carries nearly every bead, and the second flow shape doubles the window's pickers and the flow card's cases for the depot's rarer lifecycle. Option B: every flow the window lists is editable by the same two doors. It costs the flow card a type dimension and the route card a flow dimension it does not otherwise need, since a route already matches by type. This document would take A, and would let the first depot that asks for its train or design flow from footplate grow the card then, against a real flow rather than a guessed one.
