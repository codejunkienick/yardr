# A shared page frame, carried by a pack

Design yardr-7434, proposed 2026-11-02. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

A yard is one installation of yardr: its store, its crew and its depots. A depot is a git repository or a plain directory beads are worked in; a bead is one durable piece of work. A pack is one yard's way of working as a directory (`pack.yaml` and the files it names), imported into a depot or into the yard itself. A page is one self-contained HTML file kept as a blob and attached to a note or to mail. A frame is the shared HTML, CSS and JavaScript skeleton a page is made inside: tokens, a title block, tiles, tables, charts and tabs, copied into the page when the page is made. The operator is the person who runs the yard; a crew member is an always-on agent of the yard. See `docs/glossary.md` for all of yardr's words. This design builds on `docs/design/2026-10-14-yardr-x4t5-board.md` (pages as blobs, static first and scripted second, the reader opting into scripts per open) and names the file or function each claim rests on. Where a number appears it was measured in this worktree on 2026-11-02, not estimated.

## 1. The question

Yard pages should start from a shared HTML, CSS and JS frame, as claude.ai artifacts do, and the frame should come as a pack with base templates, so a person or company can have their own, to their corporate design. Today every page is one whole file its author writes: width, colours and charts are redone each time, and only the yardmaster holds a template (the files `tpl.html`, `gen.py`, and `yard-report.html` as the worked page). The cost of building it, in landing order, is: bead 1, a pack may carry a page frame (`difficulty:2`, `size:medium`); bead 2, the default page frame (`difficulty:2`, `size:medium`); bead 3, which frame applies, recorded (`difficulty:3`, `size:medium`); bead 4, a bead note dresses a fragment, with `yardr page show` (`difficulty:2`, `size:medium`); bead 5, rebuilding pages already made with the frame that now applies (`difficulty:3`, `size:medium`, held until the notes trial is judged); bead 6, mail dresses a fragment (`difficulty:2`, `size:small`, held with bead 5); and bead 7, the frame in the yard's documents (`difficulty:1`, `size:small`, held with beads 5 and 6). Only beads 1 to 4 are to be built now, tried through one depot's notes, before mail, before rebuilding and before any second pack is written. Bead 4 already keeps each framed page's fragment, title and frame apart from its dressed blob (section 3.7), so the held rebuild bead can be built later without changing what bead 4 stored; pages made before that keeping exists cannot be rebuilt. Section 6 gives each bead's goal, where to look and done criteria. Section 5 records the decisions as made, including how a rebuild is started; no question is left open.

Settled before this draft, and not reopened here: a pack carries the frame and yardr brings a default one; the frame is copied into each page when the page is made, so a page stays one self-contained blob and `pagePolicy` and `scriptedPolicy` (`internal/web/beads.go`) stay as they are, with no shared URL, no web fonts and no outside CSS, JavaScript or images; and a frame change can reach pages already made, because yardr keeps each framed page's content and title apart from its frame and can rebuild the page with the new frame (section 3.7). Pages are never loaded with a live frame, and a page made as one whole file is never rebuilt.

## 2. What exists today

### 2.1. Pages are blobs, attached whole, and opened inert or by a reader's `run`

The yard keeps a file in its home under `blobs/` by the SHA-256 of its bytes, written once and never changed (`Store.PutBlob`, `blobType` in `internal/store/blobs.go`). The type is read from the bytes with `http.DetectContentType`: a page is `text/html; charset=utf-8` (`blobPage`, `BlobRef.Kind` and `IsPage` in the same file), an image is a PNG or a JPEG, and everything else is a file that downloads. One blob is at most `blob_max_bytes`, 8 MiB unless the yard sets it (`BlobMaxSetting`, `DefaultBlobMax = 8 << 20`, measured at `internal/store/blobs.go:49`), and one note or mail carries at most 64 files (`MaxNoteFiles = MaxMailFiles = 64`, same file). A blob nothing names is pruned past one hour's grace (`BlobGrace`, `pruneBlobs`).

An agent makes a page today by writing the whole file and attaching it: `yardr bead note <id> "words" --file page.html` (`internal/cli/bead_note.go`, which puts each file with `putFiles` in `internal/cli/crew.go` and then calls `AddNotedAs`), or `yardr mail <name> "words" --file page.html` (`mailCmd` and `putFiles` in `internal/cli/crew.go`). The note still needs its words. There is no wrapping, no title argument and no fragment: what is attached is exactly what the author wrote, so every author redoes the width, the colours and the chart boilerplate the question names.

The web view serves a note's page top-level under `pagePolicy` (`internal/web/beads.go:611`, 299 bytes as written): the sandbox with no `allow-scripts`, `script-src 'none'`, `default-src 'none'`, and only `data:` images and inline style allowed beside the markup. The same hash opened with the reader's `run` action is served on the sandbox origin under `scriptedPolicy` (`internal/web/beads.go:623`, 317 bytes): `sandbox allow-scripts` with `script-src 'unsafe-inline'`, `connect-src 'none'`, no frames, workers, forms or popups, and the origin answering no yard route at all (`pagesRoutes` and `PagesHandler` in `internal/web/server.go`). That split, and the reader opting in per open, are decided in yardr-x4t5 and do not change. A mail's page is kept and shown as a row; opening mail attachments in the browser still follows the mail-viewing rule of yardr-x4t5 section 3.3, which this design does not reopen.

### 2.2. Packs carry flows, roles, scripts, stage files and declarations, and refuse an unknown key

A pack is `pack.yaml` plus the files it names, read by `pack.Load` in `internal/pack/pack.go`. The root keys a pack may write today are exactly `name`, `api`, `kind`, `setup`, `flows`, `groups`, `crew`, `sources` and `presets` (the allowed list in `reader.pack`, `internal/pack/pack.go:657`); any other key is refused as `unknown key` naming the known ones (`reader.entriesMatching`, same file), and `yardr pack check` names every mistake with file, line and key before exiting 1 (`docs/packs.md`, "What a pack is refused for"). The files a pack names today are the roles and scripts of its groups and crew (`Pack.Files`, `internal/pack/pack.go:1874`), the stage files of its flows (`Stage.File`), one setup file (`Pack.Setup`, at most `MaxSetup = 64 KiB`), and the declaration files of its sources with the programs those declarations name (`Pack.Declared`, `programs` in `internal/pack/digest.go:78`).

Planning and applying are separate. `planner.files` in `internal/pack/plan.go:937` turns each named role or script into a file object copied to `<home>/packs/<pack>/…` and each used stage file into one copied to `<home>/flows/<pack>.<flow>/<stage>.md`; `install` in `internal/pack/apply.go:751` writes the bytes the plan hashed, and `prune` in the same file removes a dropped object only when the import is told to, in the order routes, pointers, flows, groups, subscriptions, maps, sources, files (`pruneOrder`). `Export` in `internal/pack/export.go` is the inverse: it writes a depot's flows, groups, roles and scripts back out as a pack and lists in `Exported.Left` what the depot has that no pack carries. The digest is one SHA-256 over `pack.yaml` and every file the pack names, in path order, each as its path, a NUL, its length, a NUL and its bytes (`named` and `digest` in `internal/pack/digest.go:54` and `:101`), so one changed byte or one renamed file is another digest, and `pack apply --sha256` refuses any other before it asks or writes anything. The plan also names the pack's programs, the scripts its groups run and the programs its declarations name, in one line above the digest (`Plan.Programs`, `internal/pack/plan.go:95`), because applying a pack authorizes yardr to run those files as the user who runs the yard (`docs/pack-api.md`, "What applying a pack runs").

No existing file kind carries an HTML frame. A role is an agent's prompt, installed with `{{operator}}` and crew placeholders filled (`Fill` and `placeholderErrors` in `internal/pack/pack.go`) and read as instructions, so its braces and its prose are the wrong shape for markup a browser runs. A script is copied byte for byte and made executable because a `run:` group names it (`Pack.Filled`), and it is counted in `programs`, so holding a frame there would authorize it as code yardr runs and print it as such. A stage file is markdown tied to one stage of one flow, must have something in it, and is shown to whoever works a bead there. The setup file is a single markdown file printed after the plan (`docs/packs.md`, the `setup` row), not a set of files an import installs for later reading. A declaration is YAML a source is defined by, held to `DeclarationKeys` or `SourceDeclarationKeys`. Each was checked against the frame's needs — several files read later by a command that wraps a page, never run by yardr, never shown as a prompt — and none fits without bending its meaning. Section 3.1 therefore adds the smallest new seam instead of reusing one of these.

### 2.3. The pack API is at 3, and an older yard refuses a newer pack before reading it

`pack.API = 3` in `internal/pack/pack.go:39` is the highest pack API this yardr reads, and `docs/pack-api.md` lists what each number added: API 1 is everything first marked stable, API 2 added one call parameter type, `secret-file`, and API 3 lets a defaulted call parameter stand anywhere a required parameter may. The number rises by one in the release that adds anything stable — a key, a value, a variable, a command or a flag — and a pack says the lowest number whose list holds everything it uses with the optional `api` key, a pack without it being API 1. `reader.later` in `internal/pack/pack.go:638` runs before any other key is read: a pack naming a higher number than the yard reads is refused with that one mistake alone, `this pack is written for pack API N, and this yardr reads up to M: upgrade yardr (yardr upgrade)`, instead of the unknown-key blame an older yard gave before the key existed. A pack fetched from a URL is one GET per named file, at most 1 MiB and 10 seconds each, over HTTPS or plain HTTP to this machine alone, with a redirect staying on its host (`docs/pack-api.md`, "The files"); the bytes an import installs are the bytes its plan hashed, never a second download.

### 2.4. Which pack governs what is recorded per depot, and nothing records a frame

The store keeps one record per pack and depot, `<depot>\x00<pack>` to `PackImport` in `internal/store/packs.go:13`, with the yard itself as an empty depot for a pack of kind `source`. `PackImport` (`internal/store/packs.go:26`) holds where the pack was read from, the flow the depot follows, whether it carried setup notes, the name mappings and the objects the import brought, so a later import can tell what the pack has since dropped. `RecordPack` in the same file writes that record at the end of an import (`internal/pack/apply.go:282` builds it and `:298` records it), and deliberately leaves the record and its `At` untouched when an import changed nothing and the record it would write is the same as the stored one (`internal/store/packs.go:236`): an unchanged re-apply is a no-op in the store today, a fact section 3.2's selection rule is built around rather than on. A depot itself (`Depot` in `internal/store/depots.go:30`) is a name, a path, a kind, a base and a test command: it names no pack and no frame. Yard-wide settings are single values by key (`internal/store/settings.go`), among them `default_pack`, the pack a new depot starts from. So today, if two packs in one yard both carried frames, nothing in the store would say which one dresses a given depot's pages, and a bead with no depot (`Bead.Depot` may be absent) would have nothing to fall back to but a yard-wide choice that likewise is not recorded. Section 3.2 adds exactly that recording and nothing else.

Applying into the yard itself is narrow today. `planImport` in `internal/cli/pack.go:813` refuses `pack apply` without `--depot` for every pack but `kind: source`, and a source pack carries sources alone and must declare at least one (`internal/pack/pack.go:725`). Planning without a depot does exist for a wider shape: `Pack.YardWide` (`internal/pack/plan.go:670`) is a pack with no flows, groups or crew, and `buildWithoutDepot` (`internal/pack/plan.go:788`) plans such a pack's yard-wide parts for `pack check`; it plans no file copy, and `Apply` is never reached for it through the command. A frame-only pack is `YardWide` by that definition, so the check-side path is there to extend; the apply-side gate and the file planning are what section 3.2 adds, and no new kind is needed.

### 2.5. Prime is always loaded, and the web view's frame and the worked page are measured

An earlier measurement on 2026-11-02, before this bead's later notes were written, had `yardr prime --bead yardr-7434` at 105 lines and 8,119 bytes (measured with `wc`); prime has grown since with the bead's history, and the figure is that snapshot, not today's output. Everything prime prints is paid by every session that starts on a bead, so a catalogue that changes with the frame a depot happens to use does not belong there; section 3.3 puts discovery behind a command an author runs when making a page.

The web view's own frame is the nearest measured relative of a page frame. Its one stylesheet is 38,217 bytes (`internal/web/assets/yard.css`, 10,599 bytes gzipped as measured) and its one script 4,879 bytes (`internal/web/assets/yard.js`, 1,995 gzipped), 43,096 bytes together, for the whole application: rail, columns, talk, config and every page type. The design tokens it is built from, in the yardr design repository beside this one, are smaller: `tokens/colors.css` 2,378 bytes holding the dark theme and the `data-theme="light"` light theme, `tokens/typography.css` 1,141 bytes, `tokens/spacing.css` 566 bytes — 4,085 bytes for colour, type and spacing — and `tokens/components.css` 8,173 bytes for the panel's buttons, fields and rows, 12,258 bytes in all. A bead page template is 9,055 bytes (`internal/web/templates/bead.html`). These are the numbers section 3.4 budgets a page frame against.

The worked page is measured, not described from memory. Its three files are kept as blobs with the question that prompted this design and were measured on 2026-11-02 without reading the report's figures into this document: the finished report is 14,962 bytes, the template it was made from is 10,854 bytes, and the generator is 3,063 bytes. Inside the finished report, the inline style is 4,155 bytes and the inline script is 8,242 bytes (12,397 bytes together, so most of a worked page is already frame), its content column is `max-width: 1120px`, and it holds two inline SVGs, three buttons and four `@media` blocks, with no external asset (no `http` source or link). The template carries the same 4,155-byte style, a 4,610-byte script, and placeholders for its data, tiles and stamp, which is the shape section 3.3 keeps — an author supplies content, a frame dresses it. Two comparisons follow for section 3.4. First, the worked column, 1120 px, is wider than the web view's reading column, 880 px (`--reading-width` in `internal/web/assets/yard.css`): the default takes the worked page's 1120 px (decision 7 in section 5), responsive below it and checked at phone width. Second, a whole worked page at 14,962 bytes sits inside the default frame's 16 KiB budget for the frame alone (section 3.4), so the budget is not tight against the one real page the yard has. Bead 2 (section 6) still checks the built default frame visually against this page; the measurements here settle its size and width, and that check verifies the look. The Artifact page contract the bead names is the one yardr-x4t5 already adopted: one self-contained HTML file, style and any script inline, images as `data:` URLs or none, no fetch of anything external, opened top-level and inert unless the reader runs it. The later artifacts design (`docs/design/2026-10-26-yardr-0tkn-artifacts.md`, section 3.3) dresses pages at serve time by injecting a shared stylesheet and script held with the web view's assets; the settled decision on this bead is the opposite point in the page's life — the frame is copied in when the page is made, so the blob itself is the dressed page on every surface that ever serves it, including a peer yard's — and this design follows the settled decision.

### 2.6. A note, a mail and a blob record different things, and only one of them can be rewritten

A bead's note is a record in the `notes` bucket (`bNotes` in `internal/store/store.go:83`, `Note` in `internal/store/graph.go:784`), written by `addNotedNotifySession` (`internal/store/graph.go:1174`) and read back by `Notes` (`internal/store/graph.go:1216`). Its `Files` are the `BlobRef`s (`internal/store/blobs.go:89`) of the blobs it carries, each no more than a hash, the type the bytes say, a byte count and a name. A note record is rewritten in place today, but only for its telling flags: `AckNote`, `MarkNoteTold` and `MarkNoteUntold` each read the note, change one flag and `put` it back under the same bead and sequence (`internal/store/graph.go:988`, `:1038`, `:1074`). Its files are never rewritten after the note is written, and the `noted` event (`addNotedNotifySession`) carries only the note's sequence, never its files, so no second copy of a note's file list exists to keep in step.

Mail is different again: it is an event of the append-only log (`Event` in `internal/store/events.go:17`, `Mail` in `internal/store/crew.go:933`), whose files stand in the event's own data as `BlobRef`s (`EventFiles` in `internal/store/blobs.go:342`). No code rewrites an event's data after `w.event` writes it. A page that left as mail, on this yard or to a peer, is therefore a letter already sent, and section 3.7 treats it so.

Three facts about blobs govern what a rebuild may keep and what it costs. First, a blob is written once and never changed (`PutBlob` and `keepBlob` in `internal/store/blobs.go:396` and `:432`): new frame, new dressed bytes, new blob, new hash. Second, a blob lives only while something names it: `pruneBlobs` (`internal/store/blobs.go:680`) keeps the hashes a mail event, a hook delivery or a note names, plus any blob put within `BlobGrace`, one hour, and removes the rest, taking the putter record (`bBlobPuts`) with the file. A fragment kept only as a hash nobody's file list names would be swept within the hour, so whatever keeps a fragment must teach that sweep its name, in the same bead that first keeps one. Third, a blob is served only while a letter names its hash: `NoteBlob` (`internal/store/blobs.go:503`) answers a hash only when some note's `Files` name it, `MailBlob` likewise for mail, and `handleBlob` (`internal/web/beads.go:642`) serves what those answer under `pagePolicy` or, on `run`, `scriptedPolicy`. An old dressed hash that a rebuild replaces in a note's `Files` would stop being served at that moment unless the serving lookup also honours the page's kept versions (section 3.7). The pack side already records the hash a rebuild needs to name a frame by: a file object of an import is recorded as a `PackObject` with the SHA-256 of the bytes installed (`Ident` in `internal/pack/plan_drop.go:88`, `PackObject.SHA256` in `internal/store/packs.go:97`), and `planner` already reads every import's record (`planner.all`, `internal/pack/plan.go:654`) when it must say what another depot still uses, as `gone` does for a group and a source (`internal/pack/plan_drop.go:208` and `:325`), holding a dropped object with a `Held` reason that `prune` then will not remove (`internal/pack/apply.go:840`).

## 3. The proposal

The smallest version is: one new `pack.yaml` key naming one frame file, installed like a role and pinned by the digest like every named file; one embedded default frame pack; an explicit active-frame record saying which installed frame dresses each depot and the yard, with a yard-wide apply for a frame-only pack; one wrapping step in the two commands that already attach pages, taking a fragment and a title instead of a whole file; and, on the page that step makes, a record of the fragment, the title and the frame it was made with, kept apart from the dressed blob so a later bead can rebuild the page under a new frame (section 3.7). No new store table, no new server, no new serving origin, and no change to how a finished page is served. In landing order the build is seven beads (section 6): the pack seam, the default frame, the resolution with its store record and yard-wide apply, note dressing with `page show`, rebuilding, mail dressing, and the docs. Only beads 1 to 4 are to be built now; beads 5 to 7 wait until the notes trial is judged. The cost in one line: the store changes are two fields on `PackImport` in the resolution bead and one optional framed-page record on a page's `BlobRef` in the authoring bead (with the blob sweep and the page lookup taught to honour it, and two store calls in the held rebuild bead), the authoring change touches two commands (the second of them only in the held mail bead), and everything else is one HTML file, one small command group and documentation. No bead in the first four touches the serving path, because pages are dressed before they are blobs; the held rebuild bead touches only which blob a note names and which hashes that note serves, never a policy.

### 3.1. The pack seam: one `frame` key, one file, API 4 (bead question 1)

A pack may name one frame file at its root:

```yaml
name: brand
api: 4
kind: git
frame: frames/page.html
```

`frame` is a slash path relative to the pack's directory, as a role or script path is, and it names one regular HTML file in the pack. A pack names at most one: the singular key is deliberate, because naming several templates would need a way to choose among them at authoring time, a resolution rule for the choice, and a discovery surface for the list, none of which the first frame needs. A pack without the key is unchanged in every way.

Reading it is a small extension of what `reader.pack` already does. `frame` joins the allowed root keys, and its value is read with the same `rel` check a role path gets (`reader.rel` in `internal/pack/pack.go`): an absolute path, a path leaving the pack, a missing file, a file that is not a regular file there, and an empty file are each refused with file, line and key, as a stage file is today. A pack of kind `source` that names a frame is refused beside its other alone-rules (`internal/pack/pack.go:725`): a source pack carries sources alone, and the yard-wide frame pack of section 3.2 is a separate, frame-only pack, not a source pack. Two refusals are new: a frame over 256 KiB is refused, naming its size; and a frame that does not meet the title contract of section 3.3 is refused, naming what is wrong — not exactly one `<!--yardr:title-->`, not exactly one `<!--yardr:content-->`, not exactly one `<title>` element in its head, its title marker standing inside that `<title>` element, or either marker standing where section 3.3's structural rules forbid it — so a frame with no title marker, or with nowhere for the document title to go, must not pass while silently dropping the title the authoring contract requires. The bound is measured, not guessed: the token files a frame is built from total 12,258 bytes (section 2.5) and the web view's whole stylesheet is 38,217 bytes, so 256 KiB holds a generous corporate frame with headroom for extensive components or an inline chart helper, while keeping the per-page tax of section 3.4 at 3.13% of the blob limit at the bound. The bound is set high because hitting it while adopting a real frame costs more than the bytes it saves; leaving a frame unbounded was considered and not taken, because `pack check` is the one place that can stop a frame taxing every page made under it. The default frame's own tighter budget, 16 KiB, is in section 3.4. Braces in the frame are its own, as a script's are: the frame joins `Pack.Files` so `planner.files` copies it, `Pack.Filled` returns false for its path so no placeholder is filled in it, and `placeholderErrors` skips it, so a `{{…}}` in its JavaScript is not mistaken for a pack placeholder (section 3.3 reserves two markers of a different shape). One path may not stand for two things: a `frame` path that is also named as a role or script file (any path in `Pack.Files`, from a group's `agent` or `run` or a crew member's `role`, `internal/pack/pack.go:1874`), as a stage file, as the setup file, or as a declaration file or one of its programs (`programs` in `internal/pack/digest.go:78`) is refused at reading, naming both names the path carries, because the two readers would treat the same bytes two ways — `Pack.Files` is deduplicated and `Pack.Filled` spares only a `run:` path (`internal/pack/pack.go:376`), so an alias to a role would be placeholder-filled before it was ever wrapped in, and an alias to a run file would join `programs` and be installed executable (mode 0755 in `planner.files`, `internal/pack/plan.go:995`). The frame is read as a frame or not at all. Filling and executability are separate in consequence and must be separate in the code: `planner.file` (`internal/pack/plan.go:995`) today makes every unfilled file executable, which is true of a script and false of a frame, so the frame's file object takes mode 0644 explicitly there rather than inheriting the unfilled rule, and its absence from `programs` (above) is what keeps it out of the plan's program line, never its mode.

Applying a pack copies the frame where it copies roles: `planner.files` gains the frame as one more file object, from the pack file to `<home>/packs/<pack>/<its path in the pack>`, mode 0644, hashed as the installed bytes are for a role, so a hand edit of the installed copy is detected and reported exactly as a role's is (`file` in `internal/pack/plan.go:986`, `Edited` on the plan). It is recorded among the import's objects (`store.PackObject`, kind `file`, with the SHA-256 of the installed bytes, as `Ident` records a file at `internal/pack/plan_drop.go:88`) by the same loop that records roles at `internal/pack/apply.go:291`, so dropping `frame` from a later version of the pack reports the installed file as dropped, an import leaves it unless told to prune, and pruning removes it with the other files — except while another scope still uses it, as section 3.2 holds it: a dropped frame file that some depot's or the yard's active record still names is held, not removed, with the plan saying which scopes hold it. Nothing runs it: the frame does not join `programs` in `internal/pack/digest.go:78`, because yardr never executes it — a reader's browser does, and only on a `run` the reader chooses — so `pack check` must not print it in the `runs N programs of the pack as you` line. It gets a line of its own in the plan, beside the digest, so the consent an apply gives is informed about the right thing (section 3.6):

```text
frame frames/page.html (11,842 bytes): copied into each new page made under this pack; its script runs in a reader's browser only when the reader chooses run
```

The frame does join `named` in `internal/pack/digest.go:54`, so the digest pins its bytes as it pins a script's: one changed byte in the frame is another digest, and `pack apply <pack> --sha256 <digest>` refuses a pack whose frame is not the frame that was read, before asking or writing anything. Export in this bead is only the no-silent-drop half: where a depot's packs carry a frame the exporter cannot yet write as the depot's effective frame — that writing needs the resolution of section 3.2, which is bead 3 — it lists `frame: <source pack>` in `Exported.Left`, rather than dropping it unsaid, which is the exporter's standing rule. Bead 3 replaces that line with the written file where the effective frame came from a pack, and keeps the `Left` line where it came from the embedded default and so has no pack file to copy.

The key takes pack API 4. It is an addition to what `docs/pack-api.md` marks stable, and that page's rule is that the number rises on every such addition, so `pack.API` becomes 4 in the release that reads `frame`, API 4's entry lists the key, and a pack that carries a frame says `api: 4`, the lowest number whose list holds it. An older yardr reading up to API 3, given such a pack, refuses it before any other key is read with the single line `reader.later` already produces — `this pack is written for pack API 4, and this yardr reads up to 3: upgrade yardr (yardr upgrade)` — and never reaches the `frame` key to call it unknown. A pack that carries a frame but forgets `api: 4` is still refused by that older yard, as an unknown key, which is safe if less kind; the check in the new yardr does not need to enforce the pairing, because the digest and the plan line make the frame visible either way. Template packs, including the skeleton under `packs/template`, gain nothing to copy: a frame is not a declaration, and the source-pack skeleton is untouched.

The pack yardr brings is a new embedded pack, `packs/pageframe`, carrying only `pack.yaml` (`name: pageframe`, `api: 4`, no kind) and `frames/page.html`, the default frame of section 3.4. It is never imported to serve as the fallback: resolution (section 3.2) reads its frame straight from `packs.FS`, so the fallback needs no import, no depot and no kind fitness. Its name joins the `//go:embed` line in `packs/packs.go`, so `pageframe` names the pack with no checkout at hand, as `starter` does; naming it to `pack apply` without `--depot` is allowed by the frame-only yard-wide path of section 3.2 and merely records the default as the yard's chosen frame. The starter and `dir` packs do not carry a frame: carrying the same file in two packs would let the copies drift, and the resolution rule below already reaches the embedded default where no depot pack names one.

### 3.2. Which frame applies: the depot's, then the yard's, then the embedded default (bead question 2)

Two fields record the choice, and neither is read as a timestamp. `PackImport` gains `Frame string`, the absolute path of the installed frame the import brought, empty for an import whose pack names none, and `FrameActive bool`, whether that import's frame is the chosen one for its scope (its depot, or the yard where `Depot` is empty). `planner` sets `Frame` from the frame file object, the record built at `internal/pack/apply.go:282` carries both, and no migration is needed — a record written before the fields reads back with them empty and inactive, which is the truth about that import. This is the resolution bead's store change, and the first of the design's two: the second, the framed-page record a page carries, is in the authoring bead (section 3.7), not in the pack seam of bead 1. Resolution answers more than a path: the read that sections 3.3 and 3.7 use (`frameFor`, in the pack package beside `planner`, so the store is never asked to read a pack file) returns the pack's name, the installed path and the SHA-256 of the frame bytes it read, the same sum the import recorded on its file object (section 3.1), so a page can name the frame it was made with by digest and not only by the path that held it.

Selection is written, never inferred from `At`. The record built at `internal/pack/apply.go:282` sets `FrameActive` wherever the plan carries a frame, and `RecordPack` (`internal/store/packs.go:204`), in the one store write that records the import, clears `FrameActive` on every other record of the same scope before it puts its own; a record that carries no frame is built inactive and, for any other pack, leaves that scope's selection untouched, so applying a pack without a frame never changes a depot's look. The unchanged-re-apply no-op at `internal/store/packs.go:236` is respected, not bypassed: `old.same(rec)` compares the whole record but `At`, `By` and the source, so an unchanged re-apply of a pack whose frame is already active is the same record and stays `pack_unchanged`, while an unchanged re-apply of a pack whose frame was displaced by a later import is built active against a stored inactive record, differs in `FrameActive` alone, and is therefore written and logged `pack_applied` even though `Apply` wrote no file (`Result.Wrote` in `internal/pack/apply.go:153` stays false and the result says so). Concretely: import frame pack A into a depot, then frame pack B — B is active; re-apply A unchanged — the plan prints `frame: depot web would use brand-a's frame (was brand-b's)` and the apply makes A active again. That case is a named test of bead 3. The plan's frame line is computed from the scope's active record before anything is written, never from the newest `At`, and an apply that only moves the selection shows that line as its change.

How a yard-wide frame record comes to exist at all is the second half of this section. A frame-only pack — `frame` and, beside `name` and `api`, nothing but an optional `setup`: no flows, groups, crew, sources or presets — is `YardWide` (`internal/pack/plan.go:670`), so `pack check` already plans it without a depot through `buildWithoutDepot` (`internal/pack/plan.go:788`). Bead 3 extends that path in two places: `planImport` in `internal/cli/pack.go:813` allows `pack apply` without `--depot` for a frame-only pack beside `kind: source`, and `buildWithoutDepot` gains the frame as its one file object, copied and recorded exactly as `planner.files` copies a depot pack's frame, with the digest pinning it as in section 3.1. A pack that carries a frame beside flows, groups, crew or sources is not frame-only: it is applied per depot as today, or its frame is split into a frame-only pack for the yard. There is no new kind and a source pack still carries no frame (section 3.1).

Resolution is then a read for the active record, in this order:

1. The depot's frame: the `Packs()` record for the bead's depot with `FrameActive` set, its `Frame` path. Applying a pack with a frame into a depot therefore chooses that frame, printed in the plan before anything is written, in the frame line of section 3.1: `frame: depot web would use brand's frame (was pageframe's)`. An import is the operator's deliberate act, taken with the digest in view, as setting the flow a depot follows already is; there is no second command and no silent path.
2. The yard's frame: where the depot has no active frame, the record with an empty depot and `FrameActive` set. An operator who wants one frame everywhere applies a frame-only brand pack once with no `--depot`, and depots with no frame of their own fall back to it.
3. The embedded default: where neither scope has an active frame, the frame of the embedded `pageframe` pack, read from `packs.FS`. This step cannot fail for want of an import, so every page can always be made.

Two cases the bead names follow from the same three steps. A bead with no depot skips the first step and takes the yard's frame or the default. A crew member's mail page likewise has no depot — mail names a person, not a depot — and takes the yard's frame or the default, resolved in the sender's yard at sending time, because that is where the page is made into a blob. Two packs with frames in one yard are settled by the active flags, not by presence or import time: at most one record per scope is active, a pack that merely sits imported into some other depot dresses nothing, and switching back is the re-apply case above. When the active pack is next imported without a frame, that import's record carries no frame, clears its own scope's selection with it, and promotes no other pack: resolution falls back a step, and the plan shows the frame file as dropped for that scope. Pruning that dropped file is another matter, because the file is one copy shared by every scope (below): the planner's dropped-object read (`gone` for a file, `internal/pack/plan_drop.go:185`) holds the file, in the `Held` field `prune` already honours (`internal/pack/apply.go:840`), while any other record in `planner.all` (`internal/pack/plan.go:654`) with `FrameActive` set names the same installed path, exactly as `gone` holds a group or a source another import still names (`internal/pack/plan_drop.go:219` and `:341`). The plan says so, naming the scopes that hold it — for example `file frames/page.html: kept, depot web's active frame names it` — and the importing scope still falls back, because holding the bytes is not holding the choice. Only when no active scope names the path does a prune remove it, and a held file left behind is one installed file, reported as left on every later plan of that pack until its last user falls back. A frame file edited by hand in `<home>/packs/<pack>/…` is used as it stands, as an installed role is: the edit is the operator's, and the next `pack check` reports it as edited, as it does for roles. A rebuild never needs a superseded frame file back: it dresses a page in the frame that applies now (section 3.7), and a page's old look is kept as its old dressed blob, not as the frame that made it.

One installed copy serves every scope, as it does for every other pack file. `planner.files` copies a pack's files to the one place `config.At(home).Pack(name)` names, `<home>/packs/<pack>/…`, with no per-depot copy, so applying a changed version of a pack under the same name replaces the bytes every scope's active record for that pack points at. That sharing is intended, not a side effect to be designed away: pages already made keep the frame copied into them until they are rebuilt (section 3.7), new pages in each affected depot take the update at once, and a rebuild under the pick in section 5 reaches the affected depots together, because they share the bytes that changed. Because the reach is wider than the depot named on the command, the plan for such an apply names it before anything is written: beside its frame line it lists the other depots, and the yard where it applies, whose active frame record names the same pack, read from the store's `PackImport` records (`Packs` in `internal/store/packs.go`). An operator who does not want the other depots to move does not apply the changed pack until they are ready; there is no versioned or per-depot copy in this design.

Resolution happens where the page is made, in the command that wraps it (section 3.3), reading the store's `Packs`, the bead's depot and the home layout through `config.At(home).Pack(name)` — never by fetching a URL. A pack read from a URL was installed by its apply from the bytes its plan hashed, so the installed copy is the only copy wrapping ever reads, and a pack server that changes what it serves afterwards changes nothing until the pack is applied again.

### 3.3. The authoring contract: a fragment and a title in, one dressed page out (bead question 3)

What an agent gives yardr is a content fragment and a title. The fragment is the page's body content — headings, prose, tiles, a table, a chart's inline SVG — written against the frame's components (section 3.4), not a whole HTML document. The title is one line of plain text. What the frame gives back is one complete, self-contained HTML document, made from the frame by three substitutions and no others: the title marker is replaced by the title, the content marker is replaced by the fragment as markup, and the document title element's content is replaced by the title. The frame file reserves exactly two markers, chosen so they cannot collide with a pack placeholder or with ordinary prose:

```html
<!--yardr:title-->
<!--yardr:content-->
```

The title contract, which a frame author and the wrapper must agree on, is this. A frame provides exactly one `<title>` element in its head, exactly one `<!--yardr:title-->` in its body where the visible title block stands (in the default frame, inside the page's one `<h1>`), and exactly one `<!--yardr:content-->` where the fragment stands. The title marker must not stand inside the `<title>` element: the two title places are separate, and one marker cannot fill both by standing in one of them. The wrapper fills both from the single `--title` value: it replaces the marker with the title escaped as HTML text, and it replaces whatever the frame put between `<title>` and `</title>` with the same title escaped as element text, so the browser's title and the page's heading can never disagree and neither needs a second argument. Counting the markers is not enough, because a marker's bytes can appear where no substitution belongs. Each marker must be a real HTML comment standing alone — the exact comment `<!--yardr:title-->` or `<!--yardr:content-->`, not part of a longer comment, not bare text, and not inside a tag or a quoted attribute value — found by a small scanner in the pack package that tracks tags, quoted attribute values, comments and the raw-text elements (`script`, `style`, `textarea` and `title`), so no new parser dependency is taken. Its position must also be one the substitution is safe in. The title marker stands in the body, inside an element that holds text (the default frame's `<h1>`), with no `head`, `script`, `style`, `textarea`, `template` or `title` element open around it: it is replaced by escaped text, so it must stand where text stands. The content marker stands in the body where flow content stands — as a child of the body or of a flow container such as `main`, `section` or `div` — with no `head`, `script`, `style`, `textarea`, `template`, `title`, heading, paragraph, `button`, link, list or table-internal element (`table`, its rows and cells, a list or its items) open as its parent, because the fragment is substituted as markup and a fragment carrying headings, tiles or a table cannot be a child of any of those. A marker inside a `script`, a `style`, an attribute value or a `textarea`, a title marker in the head, and a content marker inside a paragraph or a button are each refused by name, at `pack check` and again at wrapping time; bead 1 carries each of those as a test row beside the counting refusals, and bead 4's wrapping step runs the same check on an installed frame edited by hand.

A minimal frame head and title block therefore look like this, with the frame's own words between the title tags replaced at wrapping time:

```html
<head><title>untitled</title></head>
<body><h1><!--yardr:title--></h1><!--yardr:content--></body>
```

A `frame` file that misses this contract — the title marker or the content marker missing or repeated, no `<title>` element or more than one, the title marker inside the `<title>` element, or either marker failing the structural rules above (not a standalone comment, or standing in a script, a style, an attribute value, a textarea, the head, a paragraph or another place its substitution does not belong) — is refused by `pack check` with file and line, beside the refusals of section 3.1, and the wrapping step in this section checks all of it again and refuses the same way, because an installed frame may have been edited by hand since its import was checked. No frame that drops the required `--title` on the floor can pass either gate. There is no data argument and no templating language in the first version: a chart's figures are computed by the author, as `gen.py` computed the yard report's, and written into the fragment as inline SVG and table rows. The frame's script may read `data-*` attributes the fragment carries, which is data enough for tabs and highlighting without yardr learning a template language it would have to hold stable.

The command is a flag on the two commands that already attach pages, not a new command. `yardr bead note` and `yardr mail` each gain `--page <fragment>` and `--title <title>` (the note flag lands first, as bead 4 in section 6, and mail follows it as bead 6 through the same wrapping):

```sh
$ yardr bead note yardr-9c2k "Yard in October: throughput and the two held landings." --page yard-fragment.html --title "Yard in October"
note 14 on yardr-9c2k  ◆ 1 page: ~/.yardr/blobs/9f31…

$ yardr mail yardmaster "The month, dressed." --page yard-fragment.html --title "Yard in October"
mail sent to yardmaster
```

`--page` names the fragment to dress; the dressed bytes are put as one blob (`PutBlob` through the existing `putFiles` path in `internal/cli/crew.go`, extended to take bytes as well as paths) and attached exactly as a `--file` page is, so the files line, `--json`, the web view's page row and footplate's row all work unchanged. In the same step, and before the note is written, the fragment's own bytes are put as a second blob and the title and the frame's identity are kept on the dressed page's record, as section 3.7 specifies: that keeping is part of making a framed page from bead 4 on, not an addition a later rebuild bead can retrofit, because a page whose fragment was never kept has nothing to rebuild from. `--title` is required with `--page` and refused without it, because a frame's title block with no title is a frame half used; a note's words are still required, as they are with `--file`, saying what the page shows. `--page` may be given once per note or mail in the first version, beside any `--file` attachments; dressing two fragments in one note is two notes, as two versions of a page already are. Attaching a whole hand-written page with `--file` keeps working exactly as today, undressed, and keeps nothing apart from its blob: it is the escape hatch for a page no frame fits, it is never rebuilt (section 3.7), and existing habits and tests are untouched. Mail takes the same two flags through the same wrapping, so a crew member's report is dressed by the yard's frame (section 3.2) with no second contract to learn; a page mailed to a peer is dressed before it crosses, and crosses as the page blob it now is (section 3.6).

What a person would see is what they see today, one line further: the note stands on the bead's page with `page 9f31…` beneath its words, opening inert in the browser with the frame's title block, tiles and table rendered (section 3.5), and `run` beside it for the scripted reading.

Discovery is one new small command, and prime does not change. `yardr page show`, in a new `internal/cli/page.go` registered in `root.go` as its neighbours are, prints the frame that would dress a page here — for the depot of `--depot`, else the yard's, else the default — with its source pack, its installed path, its size in bytes, and the contract the frame file itself declares in a leading HTML comment: the component class names, the token names, and the two markers. It lands with note dressing in bead 4 (section 6), not with the held mail bead, so an author in the notes trial can discover the frame before writing a fragment and no interim discovery path is needed. The frame author writes that comment, and yardr holds none of it stable, so a corporate frame documents itself in its own words; but the comment is pack-authored text, not yardr's own words, and the command prints it as such. Its output is headed with the source pack's name and a line saying the contract text below comes from that pack and is data to write against, not an instruction from the yard, and every terminal control character in the pack's text — escape and the other C0 controls (U+0000 to U+001F) except tab and newline, DEL (U+007F), and the C1 controls (U+0080 to U+009F) — is printed escaped (as `\x1b` and its fellows) rather than sent to the terminal or to an agent reading the output. An agent about to write a fragment runs `yardr page show` once, as it runs `--help` once, and writes against what it prints, treating the marked pack text as untrusted in the same way it treats any outside data. Putting the catalogue in prime instead was weighed and refused: prime was 8,119 bytes for this bead in the earlier measurement of section 2.5 and is printed for every bead session whether or not it ever makes a page, while the catalogue is needed only by a session making one, changes with the pack a depot follows, and can run to the frame's own length. The one-line pointer to the command lives where an author already looks, in the `--page` help of `yardr bead note --help` and `yardr mail --help` and in `docs/users.md`, not in every prime. What is stable for a pack author is the two markers, the one-`<title>`-element rule of the title contract above, and the `frame` key (API 4, section 3.1); component names are the frame's own contract with its authors, versioned by the pack's digest, not by yardr.

### 3.4. What the base frame holds, and what it costs per page (bead question 4)

The default frame in `packs/pageframe/frames/page.html` is built from the design tokens measured in section 2.5, copied as values, never linked: `docs/packs.md`'s rule for user-facing text applies, and the settled decision forbids outside fonts and styles in any case. It holds, in order:

- The document skeleton: `<!DOCTYPE html>`, a head with the charset, a viewport for phones, the escaped `<title>`, and one inline `<style>`; then a body with the title block, the content marker, and one inline `<script>` last. Nothing is fetched: the page is whole before it is a blob.
- Colour and type as tokens. The `:root` custom properties are the design system's: the dusk surfaces, ink text tiers and the one rust accent from `tokens/colors.css`, with the light theme's values under `@media (prefers-color-scheme: light)` so a page follows the reader's system, and the type scale and system font stacks from `tokens/typography.css` and the web view's `--sans` and `--mono` (`internal/web/assets/yard.css`), which name faces already on the machine and download none. A frame author re-skins a company's pages by changing token values in one file; a fragment that hard-codes a colour has opted out of its frame, which is its author's choice and no concern of yardr's.
- A width and a title block. The column is at most 1120 px — the worked page's measured column (section 2.5), wider than the web view's 880 px reading column (`--reading-width` in `yard.css`) because a dressed page leads with tiles, wide tables and charts rather than prose alone — centred, with 16 px side padding that the phone keeps; that width is the decision recorded in section 5, and a pack's own frame may still choose another. The frame is responsive below that width by construction, not by a second stylesheet: the column is fluid, tiles fall to one column, the chart scales with its figure, and the table wrapper scrolls inside itself, so at phone width the page itself never scrolls sideways and every part named here is usable. Bead 2 checks that at phone width, not only at desktop width. The title block is the escaped title as the page's one `<h1>` (the title marker of section 3.3 standing inside it, with the same title in the document's `<title>` element), a meta line under it for the fragment's own byline or date where it writes one, and a hairline rule; a fragment writes no `<h1>` of its own.
- Tiles: a `.tiles` grid of `.tile` blocks — a figure, a label and a caption — laying out in as many columns as fit and one column on a phone, for the counts and headline numbers a report leads with.
- Tables that survive a phone: a `.table` wrapper that scrolls sideways inside itself, so the page never scrolls sideways; cells wrap, numbers right-align under a `.num` class, and the header row repeats its meaning by staying visible while the wrapper scrolls. A table too wide for a phone is usable on it, not merely present.
- Charts: a `.chart` figure holding inline SVG, the SVG scaling to the column's width with its aspect kept, a visible caption under it, and the figures also present as a table or list in the fragment where they matter, so the chart is never the only copy of its numbers (section 3.5). The frame styles charts; it does not draw them, and it ships no chart library — a library inlined in every page would be paid by every page, and the worked pages' charts are SVG an author or a generator writes.
- Tabs: a `.tabs` block of buttons and panels, enhanced by the frame's script and readable without it (section 3.5), for a report whose sections a reader switches among rather than scrolls.

Size is a per-page tax, because the frame is copied into every page. Measured against the parts: the token values total 4,085 bytes for colour, type and spacing, the panel's component stylesheet is 8,173 bytes for far more components than a page frame carries, and the web view's entire application stylesheet is 38,217 bytes. Measured against the worked page (section 2.5): its template is 10,854 bytes for skeleton, style and script together, and its finished page is 14,962 bytes with 12,397 bytes of that in style and script, so a real report's frame already costs most of its page and the author's content is the smaller part. The default frame's budget is therefore set at 16 KiB (16,384 bytes) uncompressed for the whole file — skeleton, style and script — which the builder bead measures with `wc -c` and holds with a test, as pack tests hold the skeleton pack. At that size a dressed page of a 20 KiB fragment is about 36 KiB of blob, of which the frame is 0.20% of the 8 MiB blob limit (`DefaultBlobMax`); even the 256 KiB check bound of section 3.1 is 3.13% of that limit, and a page at the limit is refused by the existing blob rule with the existing words, frame included in the count, since the dressed bytes are what `PutBlob` is given. Gzip is not the measure: a blob is stored and served as its bytes, so the uncompressed size is what the yard keeps and what a peer link carries, where a page crossing to another yard is held to that yard's `peer_file_max_bytes` and the 32 MiB message bound (`MaxPeerFile` in `internal/store/peerfiles.go`) exactly as a page crosses today. The frame's cost is paid once per page made, never per reading; a rebuild pays it once more per page rebuilt, and keeps the superseded dressed blob beside it, so a page rebuilt twice holds three dressed blobs and its one fragment (section 3.7).

### 3.5. Static and scripted: the frame reads whole with scripts off (bead question 5)

A page opens static and runs only on the sandbox origin; that is yardr-x4t5 as landed and it does not change. The frame is therefore written enhancement-first. Its script, where it runs under `scriptedPolicy`, does three things and nothing the reading depends on: it marks the document as scripted, switches tab panels, and adds hover highlighting to chart and table rows. With scripts off — every static open, where `pagePolicy` sets `script-src 'none'` and the frame's script is present but unrun, exactly as a page's own script is — the document must read whole:

- Tabs read as stacked sections. The panels are all visible in document order, each under its own heading, unless the script has marked the document scripted and hidden all but the chosen one; the tab buttons are the same headings, so nothing is reachable only by clicking, and no content waits behind a hover. What hover would have shown as a tooltip is written beside what it describes, as a caption or a note in the text.
- Charts read as the SVG and its caption, with the numbers in the table or list the fragment carries beside it (section 3.4); the script's highlighting is an overlay on that reading, never the reading.
- Tiles, tables and the title block are style alone and read identically in both readings.

So one blob serves both readings with no marker on the page and no second file: the static open is the document, and `run` is the same document with its enhancements alive. A frame author who writes content that only script can reach has broken the frame's contract, which `yardr page show` prints and the docs state; yardr cannot detect it mechanically, and does not pretend to — the security review of section 3.6 checks the default frame against it, and a corporate frame is its author's responsibility, as a pack's role prose already is.

### 3.6. Trust: a frame's script is a pack's script, amplified (bead question 6)

A third party's frame script is inlined in every page made under it, so the question is what that script can reach when a reader runs the page, and the answer is exactly what any page's script can reach today, because the policies do not change. Under `scriptedPolicy` (`internal/web/beads.go:623`) on the sandbox origin, which serves no yard route (`pagesRoutes` in `internal/web/server.go`), a running script can read and change its own document, read what the reader types into that document, and — this is the limit yardr-x4t5 section 3.5 records and its later note corrects the approval on — navigate the top-level page itself away, carrying the page's own words and the reader's input in the address, since a document opened top-level can always navigate itself whatever its sandbox flags say; and it can attempt WebRTC peer connections, which no released browser blocks with the `webrtc 'block'` directive the policy carries (probed in HeadlessChrome 155 on 14 Oct 2026). It cannot reach the yard: the sandbox has no `allow-same-origin`, so the origin stays opaque and holds none of the yard's cookies (the origin sets none) and cannot call the yard's API; `connect-src 'none'` refuses fetch, XHR, WebSocket and EventSource; frames, workers, form posts and popups are refused; and a nested page cannot navigate its top frame or open a window over the yard. A reader who types into a page from a frame they did not write trusts that frame's author exactly as they trust a page's author today, and the docs say so in those words.

Two things are new, and both are about reach, not about a wider hole. The first is amplification: today a page's script is one author's, in one page, read by whoever opens that page; a frame's script is in every new page a depot or yard makes under it, so a bad frame — careless or hostile — dresses many pages before anyone notices. The second is that the frame arrives by pack, and a pack's arrival already has a trust shape this design reuses rather than invents. Applying a pack authorizes its programs to run as the user who runs the yard, with nothing fencing them in (`docs/pack-api.md`); the yard's answer is disclosure and pinning, not a sandbox: `pack check` prints the programs, and the digest pins the bytes. A frame script is weaker than a pack script in what it can reach — a browser under `scriptedPolicy`, not the yard's machine — and the design holds it to the same disclosure: it is in the digest (section 3.1), so `--sha256` pins it; the plan names it and its size on its own line; and it is installed on apply and never fetched at page-making time, so a pack server that changes what it serves changes no yard's frame until that pack is applied again.

Across a peer link, nothing new crosses. A dressed page is a page blob, and it crosses under the existing `file` kind as pages already do: the sending yard checks the link carries `file` and the receiving yard checks the bytes against their hash, reads the type from the bytes and holds them to its own `peer_file_max_bytes` (`takeFile` in `internal/store/peerfiles.go`); the frame is already inside the bytes, inert in transit, and only the receiving yard's own `pagePolicy` or, on its reader's `run`, `scriptedPolicy` ever renders it. No frame, pack or template crosses as itself, and no consent beyond the `file` consent an operator already gave is asked, for the reason yardr-x4t5 gave: bytes cross inert either way, and the receiver's sandbox is what protects it.

Whether a frame from a URL pack needs more than a pack's scripts do: no, provided the two holdings above land with it — digest membership and the plan line. A URL pack's every named file is already fetched one GET at a time under the limits of section 2.3, installed from the plan's hashed bytes and never re-fetched by apply, so a frame gets exactly a script's protection by being a named file; what it must not get is a script's label, because yardr never runs it and an operator reading `runs N programs` should not count a browser frame among programs running as them, nor miss it. The plan's separate frame line is that distinction. And as the bead's constraint requires, a security review of the rendering path is part of done for every bead that follows this design (section 6): the frame widens who writes the script in a page, so the review confirms in a real browser, not only in headers, that a framed page under both policies reaches nothing section 3.5 of yardr-x4t5 says it cannot, including script-triggered navigation and WebRTC egress, named as the residuals they are.

Rebuilding (section 3.7) widens the same hole in time rather than in reach, and the trust answer changes in three named ways. First, a rebuild puts a frame's script into pages it was not in when they were written, including pages by other authors — agents, crew members and people who wrote their fragment against an earlier frame, or against the default, and never saw the new one. The consent that covers that is not the page author's: it is the operator's, given when they applied the frame pack and again when they run `yardr page rebuild` (decision 11 in section 5) — the one trigger there is, a command and not a side effect of applying a pack or a pass of the daemon — and the rebuild's preview, its `--dry-run` list, is where that consent is informed, naming each page's bead, note and author and the frame it moves from and to. A page author who does not want a later frame in their page has the whole-file `--file` path, which is never rebuilt. Second, a reader who bookmarked a page meets the new script at the note's reference without any act of their own; what protects them is unchanged — the same two policies, the same residuals named above — but the docs bead (section 6, bead 7) must say that a framed page's look and script can change after it was written, where a whole-file page's cannot. Third, nothing about a rebuild crosses a peer link: a page already sent to a peer is that yard's blob, named by that yard's mail, and a rebuild on the sending yard changes no byte there (`takeFile` in `internal/store/peerfiles.go` keeps what it took under its own hash, and no frame or rebuild message kind is added to the link). The peer's copy keeps its frame for good; dressing it in the new frame takes a new mail carrying the rebuilt page, which the receiving yard keeps as a new letter beside the old one. The rebuild bead's security review therefore covers a rebuilt page in a real browser as it covers a newly made one, with the added case that the fragment was written against a different frame than the one now dressing it.

### 3.7. Keeping a framed page apart from its frame, and rebuilding it

What yardr keeps for a framed page, beside the dressed blob every surface already serves, is three things: the fragment, the title, and which frame dressed it. The fragment's bytes are kept as a blob of their own, put with `PutBlob` in the same step that puts the dressed bytes (section 3.3), so the yard holds two blobs per framed page before any rebuild — for the worked page's shape (section 2.5) a fragment of about 2,565 bytes beside a dressed page of 14,962 bytes. The title, the frame's identity and the fragment's hash are kept on the dressed page's own record: `BlobRef` (`internal/store/blobs.go:89`) gains one optional field, a framed-page record holding the fragment's hash, the title as the author gave it, the pack's name, the frame's path in its pack and the SHA-256 of the frame bytes actually read at wrapping time, and the list of superseded versions, each holding the full identity of the version it keeps: its dressed hash, the pack's name, the frame's path in its pack and the SHA-256 of the frame bytes that made it — the same three-part frame identity the standing record carries, never the hash and sum alone, so a version made before a pack moved its frame path still names the frame that actually made it. `BlobFile` (`internal/store/blobs.go:117`), the form a caller hands `AddNote` and `Mail`, gains the same record, and `noteFiles` and `mailFiles` (`internal/store/blobs.go:655` and `:629`) copy it onto the `BlobRef` they build, refusing a framed record whose fragment blob the yard does not hold, as they already refuse a file the yard does not hold. A record written before the field reads back without it, which is the truth about that page: it was not framed, and it cannot be rebuilt. Measured as JSON, such a record with one superseded version carrying its full identity is 426 bytes for the framed record in the example measured for this draft (64-hex hashes, pack `brand`, path `frames/page.html`, a 15-byte title; a whole `BlobRef` carrying it, 578 bytes), paid once in the note's record in the store file, against the 8 MiB each of its blobs may hold; no new bucket and no migration are needed, as none were for `PackImport`'s new fields (section 3.2). Each blob is still held to `blob_max_bytes` as it is put (`PutBlob`, `internal/store/blobs.go:404`): fragment and dressed page are counted separately, the dressed bytes frame included, exactly as a whole-file page is counted today, and a rebuild that would dress a page over the limit is refused by that same rule, naming the new size, and leaves the page as it was. The fragment is never served as a page: it is named by no note's or mail's file list, only by the framed record, so `NoteBlob` and `MailBlob` never answer its hash and no surface offers it.

Keeping the fragment only as a named hash would lose it within the hour (section 2.6), so the same bead that first keeps one teaches the sweep its names: `pruneBlobs` (`internal/store/blobs.go:680`) counts, beside each file hash it counts today, every framed record's fragment hash and every superseded dressed hash, for notes and for mail alike. That counting lands in bead 4 with the keeping itself, before any rebuild exists, because a trial page made in the morning must still have its fragment when the rebuild bead is written months later; a rebuild bead that arrived to find the fragments swept could not be built at all. Pages made before bead 4, and every page made with `--file` in any bead, have no framed record and no fragment kept: they stay as they are, for good, and saying so plainly is part of the contract — a rebuild reports them as not framed and never guesses at splitting a dressed page back into fragment and frame, a split the two markers make ambiguous the moment a fragment itself contains them.

A rebuild dresses a kept fragment again, in the frame that applies to its scope now (section 3.2), never in the frame recorded on the page: the recorded pack and sum say what a page was made with, so a rebuild can say what changed, and resolution says what it is made with next. The scope is the bead's depot for a note page, through the same three steps an authoring note takes; a page whose bead has no depot takes the yard's frame, then the default. The wrapping is the one function of section 3.3, run on the kept fragment and title, and its result is put as a new blob: identical frame bytes and fragment give identical dressed bytes, the same hash `keepBlob` already holds, and the rebuild of such a page is a no-op that reports itself unchanged and keeps no new version. What starts a rebuild is decided (decision 11 in section 5): an operator runs `yardr page rebuild` as its own command, `--depot <depot>` narrowing it to one depot and `--dry-run` showing, for every page it would rebuild, its bead, note, author and frame-from-and-to, and the counts of pages it cannot, while writing nothing. Applying a pack rebuilds nothing by itself; the plan of a pack whose frame bytes changed counts the framed pages under the packs it touches and prints the rebuild command, so the reach is visible at apply time and the act itself stays separate. A rebuild's own reporting names, per page, its bead and note sequence, its author, and the frame it moves from and to by pack, path and short frame sum, and counts the pages it cannot rebuild beside the ones it can, so no page changes uncounted and no failure is silent. A rebuild covers every scope the changed bytes reach: because one installed copy serves every depot and the yard that name it (section 3.2), a rebuild run for that pack reaches each of those scopes' pages, listed by scope in its reporting, and a run narrowed to one depot leaves the other depots' pages in the old frame until a run reaches them, which the reporting also says. Two store calls carry the rewrite, both in the held rebuild bead and neither changing what bead 4 stored: one lists the yard's framed note pages by bead (a scan of `bNotes` through `Notes`, `internal/store/graph.go:1216`, filtered to pages with a framed record), and one replaces a note page's dressed hash under a check that the note still names the hash the rebuild read, in the manner `AckNote` rewrites a note under its bead and sequence (`internal/store/graph.go:988`) — a note changed since the list was read is left alone and reported, never overwritten. The wrapping itself stays outside the store, in the command, reading the frame file `frameFor` names: the store is never taught what a frame is, and `internal/pack` importing `internal/store` already fixes that direction.

Old versions are kept, because a new frame can break an old page — a class renamed, a component dropped — and the page must not be unrecoverable at the moment that is discovered. When a rebuild replaces a dressed hash, the superseded hash, with the full identity that made it — pack, frame path and frame sum — joins the framed record's version list before the new hash stands in the note's `Files`, and `pruneBlobs` keeps every hash in that list (above), so no version is swept while its note stands. A person gets one back with `yardr page revert <bead> <note sequence>`, in the `internal/cli/page.go` command group bead 4 opens with `page show`: it prints the page's versions (dressed hash, pack, frame path, frame sum, and which stands now), and with `--to <hash>` it makes that version the one the note names and restores that version's full frame identity (pack, path and sum) as the page's standing frame identity, moving the version it replaces into the list with its own full identity in its turn, so a revert is itself reversible, a later rebuild reports the true frame it moves from even where a pack has since moved its frame path, and no act of rebuilding or reverting destroys a version. Two things follow for links, and both are stated rather than left to discovery. The reference from the note — the web view's page row, footplate's row, the files line — follows the version that stands now, so opening the page from its note after a rebuild shows the new frame, and after a revert shows the old one again. A direct link to a blob by hash, the `/blobs/<hash>/…` form `handleBlob` serves (`internal/web/beads.go:642`), keeps serving the bytes of that hash: `NoteBlob` (`internal/store/blobs.go:503`) is taught to answer a hash a note names in its version list as it answers the one in its `Files`, under the same policies, so a bookmark to the old look still opens the old page, and a bookmark to the new one opens the new. Nothing is served under a name no note any longer holds in either place.

What a rebuild does not touch is as much the design as what it does. A whole-file page made with `--file` is never rebuilt, as above. A mailed page is never rebuilt in place: mail is an append-only event (section 2.6), so the framed record a mailed page carries (bead 6) exists so that a later mail can be made from the same fragment, not so that a delivered letter changes, and a page already sent to a peer never changes on the peer (section 3.6). A page whose fragment blob is somehow missing — swept before bead 4's counting, or its file removed by hand — is reported by name and left in its current frame, as is a page whose scope's frame file cannot be read or fails the title contract at wrapping time, as section 3.3 already refuses a hand-edited frame. And a rebuild never rewrites a note's words, its author or its place: only the dressed hash in its `Files` and the version list on that page's record change, in one store write per page, so a bead's history reads as it did, with a page that looks new.

## 4. Left out

Live or saved state in a page, Claude in the page, connectors, shared mutable pages, a visual theme editor, and inline pages in the web view or footplate are out, as the bead names them: the frame is copied at making time, so state in a page would be state copied into a blob nothing can update, and a theme editor is a surface for editing one file an author can already edit in the pack. Rewriting a page that was not made through a frame is out in the same way (section 3.7): a whole-file page keeps no fragment apart from its blob, so there is nothing to dress again, and no heuristic split of a finished page is attempted. Rebuilding a framed page automatically — as a side effect of applying a pack, or in the daemon's pass — is out: the rebuild is the operator's own `yardr page rebuild` command (decision 11 in section 5), and nothing else starts one. Multiple named templates in one pack (a report frame beside a letter frame with a choice at authoring time) are out of the first version: one `frame` per pack is the smallest seam that carries the need, and the choice machinery is added only when a second template is actually wanted. A data argument or template language beyond the two markers is out: the generator that made the worked page computed its figures itself, and yardr learning a templating language would put that language on the pack API's stable list forever. Dressing at serve time, as the artifacts design proposed for its own pages, is out here by the settled decision: it would dress only pages served by this yard's view, while a made page also travels by peer link and is read from the blob itself. A `yardr page make` command that writes a dressed file without a note or mail is out of the first version: the two flags cover making for a bead and for a person, and a file-only maker is a small later bead if the generator habit asks for it. Person authoring in footplate (picking a fragment file on a note) follows the note path once it exists and is not designed here. Changing `pagePolicy`, `scriptedPolicy`, the sandbox origin or any serving route is out entirely: the settled decision holds them, and no bead in section 6 touches them.

## 5. Decisions, as made

These were the draft's open questions. All eleven are decided now, on 2026-11-02, and this section records the decision taken for each, with the alternative that was not taken and what it would have cost. No question is left open, and no builder is to reopen a decision here without a new decision on the bead.

1. One frame per pack. Decided: one `frame:` file per pack, as section 3.1. Not taken: a `frames:` map of name to file with `--frame <name>` at authoring time, which would have cost a selection rule, a resolution rule for a missing name and a discovery list, to buy one pack carrying two looks. Nothing asks for a second template yet, and the map can join a later API without disturbing this decision's packs.
2. A depot follows a second pack's frame by applying that pack. Decided: the plan shows the change and the apply sets it, as section 3.2 — applying a frame pack makes its record the scope's active one (`FrameActive`), printed before it happens, and re-applying an earlier pack unchanged moves the choice back, because the selection is the explicit flag and not the import time. Not taken: an explicit depot frame command the import never touches, which would have cost a new command and a second place the choice lives, to buy an import that can never change a depot's look as a side effect.
3. The yard-wide fallback is a frame-only pack. Decided: a frame-only pack applied with no `--depot` under the new allowance of section 3.2 — not a `kind: source` pack, which carries sources alone — resolved from its active record. Not taken: a `page_frame` setting naming an installed file path, which would have cost a setting to validate and a file the yard did not install and cannot hash, to buy a frame with no pack at all. A brand that also carries flows or sources splits its frame into its own pack for the yard scope.
4. Authors use flags, and discover the frame with `page show`. Decided: `--page` and `--title` on `yardr bead note` and `yardr mail`, plus `yardr page show` for discovery, as section 3.3. `page show` lands in bead 4 with note dressing, so the notes trial is self-contained. Not taken: a `yardr page make <fragment>` command printing a blob or file that a second command attaches, which would have cost two steps for every page and a dressed file left in a worktree, to buy dressing without a bead or a recipient; that file-only case remains the later possibility named in section 4.
5. A frame may be at most 256 KiB. Decided: refuse a frame over 256 KiB at `pack check`, with the default frame held to 16 KiB or under by test, as sections 3.1 and 3.4. The draft proposed 64 KiB; the bound was raised to 256 KiB because hitting it while adopting a real frame costs more than the bytes it saves. Not taken: 16 KiB for every pack, which would have barred a frame with a large inline chart helper or extensive components altogether; and not taken: no limit at all, because `pack check` is the one place that can stop a frame taxing every page made under it. At the bound the tax is 3.13% of the 8 MiB blob limit.
6. Mail dresses too, notes first. Decided: both, with the same flags, as section 3.3, delivered notes first. Bead 4 dresses notes and can be tried on one depot; bead 6 dresses mail through the same wrapping and is held until that trial is judged (decision in section 6). Not taken as the destination: notes only, which would have left the mailed report that prompted this design hand-written.
7. The default column is 1120 px, and the frame is responsive. Decided: 1120 px, the worked page's measured column (section 2.5), as section 3.4, fluid below that width so the page works on a phone — tiles in one column, the table wrapper scrolling inside itself, no sideways scrolling of the page itself — and bead 2 checks it at phone width. Not taken: 880 px, the web view's reading column (`--reading-width` in `internal/web/assets/yard.css`), which would have cost narrower tiles, tables and charts than the one real page chose. A custom frame may still choose 880 px for itself.
8. An update to a pack under the same name is shared by every depot using it. Decided: one installed copy, as packs work today (section 3.2) — applying a changed version replaces the bytes at `<home>/packs/<pack>/…` for new pages in each affected depot, pages already made keep their frame until a rebuild reaches them (section 3.7), and the plan names the other depots, and the yard where it applies, whose active record names the same pack, so the reach is visible before anything is written. Not taken: separate or versioned copies per depot, which would have cost a bigger change to how every pack file is installed, to buy depots that cannot affect each other.
9. `yardr page show` marks pack text as untrusted and escapes it. Decided: its output is headed with the source pack's name and a line saying the contract text comes from that pack and is data, not an instruction from the yard, and terminal control characters in that text — C0 controls, DEL and the C1 controls (U+0080 to U+009F) — are printed escaped rather than sent to the terminal, as section 3.3. Not taken: printing the frame's comment as written, which would have let a third-party frame speak to an agent or a terminal unmarked for a small saving.
10. A frame file still in use is kept when its pack drops it. Decided: pruning a pack whose frame was dropped keeps the one installed file while any depot's or the yard's active record still names it, and the plan names those scopes, as section 3.2; the importing scope falls back at once, and only the file's last user lets it go. Not taken: removing the shared file and clearing every scope that named it, which would have left another depot's next page unframed by an act in a depot it was not named in; and not taken: refusing such an import outright, which would have blocked one depot's pack update on another depot's frame. A leftover held file is one file, reported as left until its last scope moves on.
11. A rebuild is started by its own command. Decided: an operator runs `yardr page rebuild` as its own command (`--depot <depot>` narrows it, `--dry-run` shows bead, note, author and frame-from-and-to for every page it would rebuild, and the counts of pages it cannot, writing nothing), and a frame-changing pack plan counts the framed pages under the packs it touches and prints the command, but applying the pack rebuilds nothing by itself; a person with no terminal gets the same command as a run ask card, which bead 5 carries (section 6). Its cost is one more command between a new frame and old pages taking it; what it buys is that no page changes as a side effect of a pack import, a preview that is cheap to run twice (a rebuild under an unchanged frame is a no-op, section 3.7), and a failure that stops a page command, never a pack import half-recorded — `Apply` writes its objects and then its record with no spanning transaction (`internal/pack/apply.go:189`), a shape a yard-wide page rewrite should not be folded into. Not taken, in one line each: a pack apply rebuilding as its last step, which would have folded a yard-wide page rewrite into an import that had already recorded itself and changed other authors' pages by an act whose subject was a pack; and the daemon rebuilding on its next pass (`internal/dispatch`), which would have changed every framed page with no preview and at a time no one chose. Either can still be added on top of this command later without changing anything stored, while the reverse is not true.
